# ai-company 프런트엔드

마스터가 목표를 말하고 PM과 팀을 정하며, 진행을 이해하고 필요한 결정을 내릴 수 있게 만든다. 매번 같은 카드 배치를 재생산하지 않되, 익숙한 조작을 독창성만을 위해 깨뜨리지 않는다.

## 먼저 확인할 것

- 현재 작업 브랜치의 웹 코드, 변경하려는 화면과 상태, 기존 브라우저 검사를 읽는다. 저장소 캡처·시안·공개 운영 화면을 구별한다.
- 이번 일이 작은 수정인지, 구조 개편인지 판단한다. 오타·간격·한 버튼 수정에 전체 시안 비교를 요구하지 않는다.
- 기존 사용자 선택과 실행 범위를 확인한다. 이미 받은 승인이나 디자인 선택을 반복 질문하지 않는다. 불명확한 취향은 우선 비교할 수 있는 시안으로 구체화한다.
- 최초 개편 또는 방향 재검토 때 [프로젝트 설계 메모](../../../docs/product-experience/frontend-redesign-2026-09-16.md)를 읽는다.
- 진행 그래프를 작업할 때는 후속 [역할·업무 그래프 명세](../../../docs/product-experience/graph-workspace-2026-09-16.md)를 먼저 따른다. 사용자가 선택한 그래프 방향을 초기 세 시안 선택 대기로 되돌리지 않는다.

## 구조 개편의 산출물

1. **짧은 설계 메모:** 주 사용자 과제, 현재 불편, 첫 화면에서 보일 정보와 행동, 보존할 동작, 바꿀 시각 규칙.
2. **구조 비교:** 방향이 정해지지 않은 큰 개편은 서로 다른 2~3개 작동 시안을 비교한다. 이번 최초 개편은 매니저 작업실·팀 작업대·결정함 세 안을 비교한다. 동일한 핵심 사용자 과제·한국어 내용·상태를 서로 다른 배치와 우선순위로 보여 준다. 서로 다른 페이지 세 개나 색상만 바꾼 복제안을 세 방향으로 세지 않는다.
3. **작은 완성 구간:** 추천 방향의 핵심 동선부터 로컬 또는 별도 미리보기로 만든다. 이미 선택이 있으면 그 선택으로 진행한다. 선택이 아직 없으면 추천안임을 표시하고 비교 가능한 결과까지 준비하며, 그것을 마스터가 확정한 디자인으로 기록하지 않는다.
4. **실제 검수:** 아래 수용 조건과 비교 화면으로 결과를 판단한다. 전체 교체에 필요한 방향 선택은 구체적인 시안을 제시한 뒤 한 번에 받는다. 되돌릴 수 있는 시안 작업을 승인 대기로 멈추지 않는다.

## 화면별 판단 기준

- **프로젝트:** 이름, 최근 의미 있는 변화, 내 다음 행동으로 찾게 한다. 반복되는 계획·PM·실행 메타데이터를 모두 같은 무게로 나열할 필요는 없다. 정확한 상태 상세에는 계속 접근할 수 있어야 한다.
- **매니저:** 현재 질문·제안과 그 이유, 대화 입력을 우선한다. 팀·기술 설정은 맥락에 맞게 보인다. 목표를 입력하기 위해 파일명이나 명령어를 알아야 하지 않게 한다.
- **진행:** 실제 역할·책임·담당 모델·현재 일·전달물을 연결한다. 병렬 행, 작업 목록, 관계 그림 중 현재 규모와 화면에 맞는 표현을 택한다. 예정된 역할과 실제 동시 실행을 구별한다.
- **승인:** 결정 대상, 바뀔 것, 영향·비용·복구, 근거와 선택을 읽는 흐름으로 만든다. 작업 진행과 승인함은 각각 찾을 수 있게 한다. 긴 문서는 목록-본문, 요약-상세 등 읽기 중심 배치를 고려한다.
- **보고:** 무엇을 달성했고 무엇이 남았으며 어떤 결정이 필요한지 먼저 쓴다. PM 작성물·시스템 집계·번역 출처를 혼동시키지 않는다.

## 시각 판단

- 내용의 관계를 먼저 정하고 행·문서·타임라인·패널·카드를 고른다. 카드는 독립 선택·그룹·강조에 도움이 될 때 사용한다. 카드 사용을 전면 금지하지 않는다.
- 화면마다 동일한 작은 라벨→제목→설명→카드 격자를 자동 반복하지 않는다. 공통 탐색과 같은 행동의 표현은 일관되게 유지한다.
- Light·Black 모두 지원하되 기존 색·모서리·열 수를 영구 제한으로 취급하지 않는다. 선택한 방향에서 글자·간격·상태색·표면 규칙을 일관되게 정한다.
- 한국어 글꼴의 실제 렌더링, 문장 줄바꿈, 장문, 숫자·영문 혼합을 확인한다. 영문 웹폰트 이름만으로 한국어 서체 적용을 주장하지 않는다.
- 핵심 대화·본문은 16px, 행동·중요 상태는 14px 이상을 프로젝트 출발점으로 삼고 확대·기기 검수로 조정한다. 미관을 위해 오류·비용·승인 범위를 작은 글씨나 낮은 대비로 숨기지 않는다.
- 주요 터치 영역 44px, 표시와 입력에 충분한 대비, 키보드 초점과 읽는 순서를 보존한다. 이 일부 조건만으로 접근성 인증을 주장하지 않는다.
- 움직임은 실제 전달·상태 변경을 이해시키는 데 쓴다. 의미 없는 반복 입자·맥박·가짜 작업 애니메이션을 넣지 않는다. 줄인 동작 설정에서도 내용과 조작이 유지되어야 한다.
- 현재 HTML·CSS·JavaScript 모듈을 우선한다. 디자인 스킬 때문에 React, CDN, 폰트 서비스, 아이콘 라이브러리, 새 프레임워크로 전환하지 않는다.

## 보존할 제품 계약

자연어 목표, PM 제안과 직접 계획 확정, 명세 저장과 실행 승인 분리, 정확한 프로젝트·계획·실행 연결, 멱등 재시도, 원문/번역 권한, 요청 모델/관측 모델 구별을 유지한다. 보기 좋은 상태를 만들려고 운영 값·승인·실패·검사 근거를 바꾸지 않는다. 예시 데이터에는 예시 표시를 붙인다.

스킬 도입은 기존 pilot 파일 허용 범위를 넓히거나 운영 배포·병합·추가 모델 호출을 승인하지 않는다. 실제 UI 작업을 자동 에이전트에게 배정할 때는 그 작업의 승인된 명세에 UI 경로와 검사를 연결한다. 범위 불일치는 원래 정책 안에서 보고한다.

## 완료 증거

- 변경한 사용자 과제를 기존 화면과 새 화면에서 같은 내용·상태로 비교한다. 미감 개선은 판단임을 밝히고 구체적 차이를 설명한다.
- 영향을 받는 화면의 정상·빈 화면·대기·오류·장문·확인 요청을 검수한다. 연결 끊김·권한 상태는 변경 영향이 있으면 포함한다.
- 구조 개편은 Light·Black, 320/390/1440px와 키보드·확대·모바일 재배치를 확인한다. 작은 수정은 영향 범위의 검증으로 좁힌다.
- 작성 중 갱신, 초점 복구, 중복 제출, 기존 프로젝트 탐색, 계획 확정과 승인 대상 연결에 관련된 회귀를 유지한다.
- 구조 개편·핵심 흐름 변경은 작성자와 별도 검수자가 화면을 보고 핵심 조작을 확인한다. 작은 수정은 기존 검수 정책과 영향 범위에 맞춘다. 기능 CI가 초록색이거나 작성자 점수가 높다는 이유로 필요한 시각 검수를 생략하지 않는다.
- 가능한 로컬/원격 격리 브라우저에서 검증한다. 환경 문제로 실행할 수 없으면 미검증 범위와 가능한 다음 수단을 적고, 검증을 위해 격리 설정을 해제하지 않는다.
- PR에 변경 이유, 비교안·선택/추천 상태, 실제 캡처, 조작 결과, 남은 제약을 연결한다. 시안·제품 코드·CI·실기기·운영 적용을 각각 구분한다.

이 문서는 작업 지침이며 실행을 차단하는 프로그램은 아니다. 자동 배정기에 연결할 때는 읽은 스킬 버전과 검수 증거를 그 작업에 묶어야 하며, 문서 추가만으로 연결 완료라고 보고하지 않는다.

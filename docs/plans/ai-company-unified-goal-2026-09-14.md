# AI Company 통합 목표·서버 Codex 작업 지시

기준일: 2026-09-14 · v1.0

이 문서는 PR #5의 복구·이관 기반과 마스터가 요청한 역할별 병렬 운영·UI 목표를 합친 후속 작업 지시입니다. 현재 구현된 기능과 앞으로 구현할 제품 요구사항을 구분합니다. 목표 통합 문서이며 PR 병합이나 운영 배포 결과가 아닙니다.

## 1. 최종 목표

**hyungwon.cloud에서 마스터가 GPT-6 Astra Ultra 프로젝트 매니저와 대화하여 프로젝트의 목표·역할·실행 규칙을 정하고, 역할별 에이전트가 병렬로 구축·검증·수정하며, 진행 보고와 실행 승인을 분리해서 관리하는 시스템을 완성합니다. 모바일 웹을 기반으로 Android TWA도 제공합니다.**

각 역할은 프로젝트별 책임·하네스·작업 큐를 가지며, 실행 담당 모델과 세션은 교체할 수 있어야 합니다. 특정 에이전트의 한도 소진이나 중단이 다른 독립 작업과 관리 화면 전체를 멈추게 해서는 안 됩니다.

## 3. 역할별 병렬 운영

마스터는 PM과 목표·역할·완료 기준·승인 범위를 합의합니다. 역할 목록은 프로젝트마다 바꿀 수 있어야 하며, 아래 네 역할은 AI Company 구축 프로젝트의 예시입니다.

| 역할 | 병렬로 진행할 일 | 다른 역할과 주고받을 결과 |
|---|---|---|
| 화면 개발 | 매니저 대화, 역할별 진행, 보고서, 승인 화면 구현 | 합의한 API 규격을 받아 개발하고 화면 변경을 검증 역할에 전달 |
| 서버 개발 | 프로젝트·역할·작업·이벤트·승인 API와 기존 실행기 연결 | 응답 규격을 먼저 공유하고 구현·검사 결과를 전달 |
| 검증·독립 리뷰 | 규격을 기준으로 테스트 준비, 도착한 변경 검사, 독립 리뷰 | 문제를 해당 담당자에게 반환하고 통과 근거를 기록 |
| 운영 준비 | 격리·배포·도메인·TWA·되돌리기 계획과 검증 준비 | 배포 조건·영향·비용을 정리하고 승인된 실행만 수행 |

구현 원칙:

- 역할을 작업 단계의 다른 이름으로 만들지 않습니다. 각 역할이 자기 작업 큐에서 준비된 일을 계속 가져가는 구조로 만듭니다.
- 역할마다 책임, 입력·출력, 완료 조건, 허용 도구·경로, 검수 기준, 후보 모델, 하네스 버전을 정의합니다.
- 역할 큐는 기존 영속 저장소의 논리적 분리로 구현할 수 있습니다. 역할마다 별도 DB·상시 프로세스를 무조건 만들지 않습니다.
- 동시에 수정하는 작업에는 분리된 worktree 등 소유 범위가 명확한 작업 공간을 배정합니다. 공유 파일·API 규격 변경은 영향을 확인하고 조정합니다.
- 검증 준비는 구현과 동시에 시작합니다. 실제 변경 검증은 대상 산출물이 도착한 뒤 수행합니다.
- 필요한 산출물의 의존성만 기다립니다. 한 변경 묶음이 검수·승인을 기다린다고 다른 독립 작업까지 멈추지 않습니다.
- 통합 검사 → 독립 리뷰 → Astra Ultra 최종 검수는 준비된 변경 묶음에 적용합니다. 수정은 해당 역할의 큐로 반환합니다.
- 역할 수와 동시 실행 수를 구분합니다. 현재 서버 자원과 계정 한도를 확인해 실행 동시성·작업량 상한을 설정합니다.

## 4. 모델·세션·사용량 정책

| 논리적 역할 | 요청한 담당 구성 |
|---|---|
| 마스터의 대화 창구·프로젝트 매니저 | GPT-6 Astra Ultra |
| 개발·1차 검토 | GPT-6 Astra High 또는 Claude Code Opus 5 Ultracode |
| 독립 검수 | 해당 변경 작성자와 분리된 적격 세션 |
| 최종 품질 검수 | GPT-6 Astra Ultra |

위 구성은 제품 요구사항입니다. 표시된 이름만으로 실사용 검증을 통과한 것으로 처리하지 않습니다.

1. 역할과 작업 ID는 유지하고 담당 모델·실행 시도·세션을 별도로 기록합니다.
2. 사용량 제한은 역할 권한·계정 상태·예산·검수 독립성을 충족하는 후보가 있을 때만 자동 이관합니다. 같은 계정의 High·Ultra 전환을 새 한도로 취급하지 않습니다.
3. 제공자를 바꿀 때는 작업 명세·파일 변경·검사 근거·체크포인트를 전달합니다. 서로 다른 CLI가 동일 세션 ID를 이어 쓸 수 있다고 가정하지 않습니다.
4. `WAITING_RETRY`는 기존 정책대로 공유 계정 상태를 확인하고 원래 세션을 재개합니다. 일시 통신 오류를 곧바로 다른 제공자로 이관하는 이유로 사용하지 않습니다.
5. 적격 후보가 없으면 실행 상태와 예약 시각을 영속 저장합니다. 장시간 sleep으로 worker를 점유하지 않고 예약된 짧은 worker 실행으로 재확인합니다.
6. 모든 후보가 소진되면 해당 모델 작업은 실제로 기다려야 합니다. 이때도 스케줄러·상태 조회·저장된 보고서·기존 승인 처리는 동작해야 합니다.
7. PM이 대기 중이면 이미 합의한 계획과 정책 범위의 독립 작업은 계속합니다. 새 목표 해석·범위 확대·정책 변경·PM 판단은 PM 복귀를 기다립니다.
8. 최종 검수 담당은 Astra Ultra로 유지합니다. 한도 부족을 이유로 검수를 생략하거나 다른 모델의 최종 승인으로 바꾸지 않습니다.
9. 컨텍스트 부족은 사용량 제한과 분리해 체크포인트·새 세션 인계로 처리합니다. 인증·샌드박스 오류와 소유권 불일치는 무한 자동 재시도하지 않습니다.
10. 기존 generation·멱등 처리·자식 실행 종료 확인·늦은 결과 차단·사용량 집계 복구를 유지합니다. 결과가 불확실하면 재조정 상태로 남깁니다.

## 5. 하네스와 관리 화면

프로젝트별 문서에는 목표·완료 기준·역할별 책임·협업 규격·승인 정책·후보 모델을 둡니다. 파일 이름은 기존 저장소 규칙에 맞추되 `project.md`, `roles/*.md`, 승인 정책 문서처럼 책임을 나눕니다. 초안과 활성 버전을 구분하고, 실행에는 당시 적용한 버전을 기록합니다.

| 화면 | 필수 기능 |
|---|---|
| 매니저 | 마스터와 Astra Ultra PM의 대화, 목표·역할 배치 제안, 계획·하네스 변경 검토. 다른 에이전트와의 직접 대화를 요구하지 않음 |
| 진행 → 역할별 흐름 | 역할을 병렬 칸으로 표시. 담당 모델·세션, 현재·다음 작업, 필요한 결과, 대기 이유, 이관 이력, 수정 요청과 합류 관계 |
| 진행 → 보고서 | 목표 대비 완료·진행·차단·다음 행동, 변경·검사·CI 링크. 실제 근거와 예시·미검증 상태 구분 |
| 승인 | 승인 요청만 모아 대상·변경·환경·비용·영향·되돌리기·유효 조건·검수 근거를 보여주고 승인·반려·수정 요청 기록 |
| 프로젝트 | 역할 구성, 하네스 초안·활성 버전, 모델 후보·공유 계정 그룹, 자원·예산 정책 확인 |

추가 조건:

- 기본 진행 화면은 역할별 병렬 배치로 만듭니다. 전체 작업을 하나의 긴 단계 순서로 표시하지 않습니다.
- PM이 응답하지 않아도 저장된 진행·보고서·승인 요청을 읽고 처리할 수 있어야 합니다. 시스템이 정리한 상태 보고를 PM이 작성한 판단으로 표시하지 않습니다.
- 모델 검수 통과와 마스터의 실행 권한을 분리합니다. 기존 승인 범위의 작업은 계속하고, 범위 밖의 배포·결제·호스트 변경 등은 구체적인 실행안을 제시합니다.
- 승인은 작업 대상·커밋 또는 산출물·환경·비용·기한에 연결합니다. 대상을 바꿨으면 재검토하고, 다른 변경에 이전 승인을 재사용하지 않습니다.
- 새로고침·연결 끊김 후에도 서버의 영속 상태로 복원합니다. 브라우저가 큐나 승인 상태의 유일한 원본이 되어서는 안 됩니다.
- 기존 Python 실행기·SQLite 큐를 우선 확장합니다. 화면을 위해 별도 실행 엔진이나 중복 큐를 새로 만들지 않습니다. API와 상태 이벤트 규격을 합의한 뒤 화면·서버 개발을 병렬 진행합니다.

## 6. 도메인·모바일·운영 보존

- 서비스 주소는 `hyungwon.cloud`를 목표로 합니다. DNS·TLS·로그인·권한을 검증한 뒤 공개합니다.
- 반응형 웹을 먼저 완성하고 Android TWA를 연결합니다. `HyungwonPark/edward-talenta`의 실제 TWA 구성·서명·배포 절차를 읽어 재사용 가능한 방식만 가져옵니다.
- 앱 식별자, 서명 키, 도메인 연결, 비밀 정보는 새 프로젝트의 소유 범위로 분리합니다. 기존 앱의 자격 증명을 복사하지 않습니다.
- 웹 manifest·서비스 워커·Digital Asset Links 등 필요한 연결 요소를 확인하고, Android 설치·도메인 검증·로그인 유지·승인 화면 사용을 검증합니다.
- 기존 `talenta-edward.life` 서비스의 도메인·프록시·컨테이너·포트·자원과 새 서비스를 구분합니다. 실제 충돌 여부는 서버에서 확인합니다.
- 기존 운영 타이머·큐를 자동 이전하거나 덮어쓰지 않습니다. 새 실행 경로는 별도 검증 후 전환·되돌리기 계획을 갖춥니다.

## 7. 후속 작업 순서와 병렬 분담

### 공통 준비

현재 브랜치·변경을 보존하고 AGENTS.md, PR #5 검증 기록, 기존 실행기·정책·큐·CI 문서를 읽습니다. 아래 작업 간 API 규격·이벤트·산출물·소유 파일을 먼저 정합니다.

### A. 실제 실행 차단 해소

- 같은 worker 경로·계정·격리 설정에서 오류를 재현하고, 현재 검토된 bwrap/AppArmor 전용 조치를 확인합니다.
- 패키지·프로필·실행 경로의 정확한 변경안과 영향·검증·되돌리기 방법을 준비합니다. 기존 승인 범위를 확인하고, 범위 밖 호스트 변경은 구체적인 실행안이 준비된 뒤 승인을 요청합니다.
- 전역 격리 설정을 끄는 방식으로 완료 처리하지 않습니다. 조치 후 최소 명령 성공뿐 아니라 작업 범위 밖 쓰기·허용되지 않은 네트워크 차단·cgroup 종료가 유지되는지 검증합니다.
- 요청 옵션 수용, CLI 적용 설정, 실제 주 모델, 실효 effort/Ultracode, 동적 Workflow 증거를 별도로 수집합니다. 증거가 없으면 미검증으로 남기고 자기 설명으로 대체하지 않습니다.

### B. 역할별 병렬 실행·관리 API

- 기존 실행기를 역할별 작업 배정·산출물 의존성·독립 검수·이관에 연결합니다.
- 프로젝트·역할·작업·실행 시도·계정 그룹·하네스 버전·보고·승인을 연결하는 데이터/API 규격을 구현합니다.
- B는 A의 실사용 복구를 기다리는 동안 모의 실행으로 검증할 수 있습니다. 기존 복구·CI 출처 검증을 보존합니다.

### C. 역할별 UI·보고·승인

### 통합 검증

A의 실제 실행 조건과 B·C의 연결이 준비되면 작고 되돌릴 수 있는 작업으로 실제 개발 → 검사 → 독립 검수 → Astra Ultra 최종 검수 흐름을 완료합니다. 동일 후보 변경의 승인된 원격 CI 출처·head·실행 회차·필수 검사 근거를 확인합니다.

## 8. 완료 기준

1. 기존 148개 테스트를 포함한 관련 회귀 검증이 유지되고, 중단 복구·공유 한도·CI 출처 결함이 재발하지 않습니다. 테스트 개수 증가 자체를 완료 근거로 사용하지 않습니다.
2. 서로 독립된 두 역할이 실제로 동시에 진행한 실행 기록이 있고, 필요한 산출물 의존성만 기다리는 것을 확인합니다.
3. 사용량 제한·worker 중단을 통제된 모의 상황으로 주입했을 때 작업·하네스·사용량·소유권이 보존되고, 중복·늦은 결과가 차단되며 이관 또는 예약 재개됩니다. 실제 계정 한도를 고의로 소진하지 않습니다.
4. `WAITING_RETRY`가 공유 계정의 DISABLED/UNKNOWN/COOLDOWN을 지키고 회복 후 원래 세션을 재개합니다.
5. 같은 worker 환경에서 샌드박스 제한을 유지한 실제 개발과 검사·독립 검수·Astra 최종 검수를 완료합니다. CLI exit 0이나 모의 `DEMO_READY`만으로 통과하지 않습니다.
6. 요청 모델·effort와 확인된 실제 적용 증거를 구분합니다. Ultracode·동적 Workflow를 포함한 필수 미검증 요구사항은 해결하거나 마스터가 명시적으로 요구사항을 조정하기 전까지 남겨 둡니다.
7. PM 한도 대기와 브라우저 재접속 상황에서도 역할별 상태·저장된 보고·기존 승인 요청이 유지됩니다. 특정 승인 대기가 무관한 작업을 막지 않습니다.
8. 승인한 변경과 실행 대상이 일치하고, 변경·만료·비용 초과는 실행 전에 차단됩니다. 검수와 승인 기록을 동일 산출물에 연결합니다.
9. `hyungwon.cloud` 로그인·역할별 진행·보고·승인이 실제 연결 상태에서 동작하고, Android TWA 설치·도메인 연결·로그인 흐름을 확인합니다.
10. 기존 커플 서비스·타이머·큐의 영향 여부와 되돌리기 절차를 확인합니다.

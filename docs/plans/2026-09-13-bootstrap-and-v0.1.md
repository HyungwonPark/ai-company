# ai-company 서버 연결 및 v0.1 구축 계획

기준일: 2026-09-13  
문서 버전: v1.2  
상태: 실행 전 계획 초안  
대상 저장소: HyungwonPark/ai-company

**ai-company의 목적은 승인된 목표와 완료 조건을 기준으로 기존 코딩 에이전트의 구현·검증·검수·수정을 자동으로 반복하고, 검증 근거가 갖춰진 병합 준비 또는 사유가 명확한 중단 상태로 끝내는 개발 작업 운영 시스템을 만드는 것입니다.** LangGraph는 이 반복을 제어하는 수단이며, 기존 Codex·Claude Code의 실행 기반을 활용합니다.

이 문서는 2026-09-13 대화에서 수용한 방향을 실행 단계로 구체화한 제안입니다. 서버 접속·설치·배포를 완료했다는 보고가 아닙니다. 기존 두 설계·인수인계 문서는 원문 확보 후 이 계획과 대조합니다.

## 목적과 범위

이 프로젝트에서 루프 엔지니어링은 에이전트 실행 바깥에서 작업의 전달·관찰·판단·수정·종료·복구를 설계하는 일로 정의합니다. 특정 모델이 모든 하네스 문제를 해결했다는 가정에 의존하지 않습니다. 모델의 설계 능력과 실제 권한·실행·상태 복구의 검증은 별도로 확인합니다.

| 구분 | 적용 범위 |
|---|---|
| 활용하는 기반 | Codex CLI·Claude Code가 제공하는 코드 탐색, 도구 실행, 대화 맥락 관리와 권한 제어 |
| 직접 만드는 핵심 | 고정된 작업 명세, 다음 단계 결정, 독립 검수, 자동 수정, 반복 한도, 완료·중단 판정, 재시작 복구 |
| 필요한 연결 작업 | CLI 어댑터, 작업별 맥락 묶음, 작업 공간 분리, 실행 식별자·증적과 인증 연결 |
| 이후 확장 | 실제 업무에 필요한 역할·에이전트를 같은 계약으로 추가하고, 측정 결과에 따라 동시 실행을 확대 |

v0.1의 우선순위는 개발자·검수자 두 역할의 반복을 완주하는 것입니다. 다른 에이전트의 추가는 공통 인터페이스로 가능하게 두되, 역할 수 자체를 완료 기준으로 삼지 않습니다.

완료 여부는 다음을 기준으로 확인합니다.

1. 작업 접수 이후 구현 결과·반려 사유·수정 요청을 사용자가 중간에 복사해 전달하지 않습니다.
2. 병합 준비는 동일한 작업 명세·정책과 현재 커밋에 대한 필수 검사·검수 근거가 일치할 때만 성립합니다.
3. 반려 후에는 실제 수정·재검증을 수행하며, 수정·시간·사용량 한도를 넘기면 사유를 기록하고 중단합니다.
4. 중복 접수·늦은 결과·재시작 시험에서 잘못된 합격과 중복 외부 작업을 차단합니다.
5. 사람이 목표·정책을 판단해야 하는 경우에는 필요한 질문과 근거를 명시합니다.

## 현재 확인한 범위

- 계획 작성 직전 main은 README.md만 있는 초기 상태였으며, 기준 커밋은 `2a4754ec9597066804ece8825e1a09f07439a726`입니다.
- 대화의 실행 환경은 Oracle 서버와 연결되지 않은 별도 환경입니다. Oracle에 명령을 실행한 사실이 없습니다.
- 서버 사양은 사용자 설명상 2 core / 12GB입니다. 운영체제, CPU 구조, 남은 자원, 접속 계정, 설치된 CLI 버전과 인증은 아직 실측하지 않았습니다.
- 기존 운영 서비스와 금융 프로젝트의 보류 상태를 유지하는 범위에서 별도 시험 작업으로 검증합니다.
- 동시 실행 1개, 최초 구현 이후 자동 수정 최대 3회, 첫 완료 지점은 병합 준비를 초기 제안값으로 사용합니다. 실행 시간·사용량 상한은 시험 전에 정합니다.

## 1. 서버에 연결하는 방법

**기본 작업 경로는 사용자가 이미 쓰는 SSH + tmux + 서버 CLI 방식입니다.** 사용자는 서버의 tmux 세션에서 Claude Code를 실행·로그인해 작업하고 있다고 설명했습니다. 이 환경에 Codex CLI를 추가해 구축을 이어갑니다. 데스크톱 앱의 SSH 연결은 선택 사항이며 초기 구축의 선행 조건으로 두지 않습니다.

최초 준비 순서는 다음과 같습니다.

1. 기존 SSH 경로로 Oracle에 접속하고 현재 Claude Code의 실행 계정과 작업 경로를 확인합니다.
2. ai-company용 Codex tmux 세션을 별도로 준비합니다. 기존 작업 세션은 유지합니다.
3. 해당 계정의 Codex 설치·버전·로그인 상태를 확인하고 필요한 준비를 수행합니다.
4. ai-company의 분리된 작업 디렉터리 또는 worktree에서 Codex CLI를 실행합니다.
5. 서버의 Codex가 PR #1의 계획 문서와 현재 저장소 상태를 읽고 환경 점검부터 시작합니다. 초안 문서는 `docs/bootstrap-plan-2026-09-13` 브랜치에 있습니다.

Codex CLI는 실행한 서버의 터미널에서 코드 탐색·수정·명령 실행을 수행할 수 있습니다. tmux는 세션을 분리했다가 다시 연결할 수 있게 합니다. [A급·OpenAI CLI 공식 문서](https://learn.chatgpt.com/docs/codex/cli), [A급·tmux 공식 문서](https://github.com/tmux/tmux/wiki/Getting-Started)

현재 이 ChatGPT 대화에는 Oracle의 tmux를 직접 조작하는 연결이 없습니다. 서버의 Codex CLI는 별도 실행 세션이며, 이 대화의 맥락은 계획·작업 명세·결정 기록·대상 커밋을 통해 전달합니다. 서버에서 로그인하는 것만으로 이 웹 대화가 그 세션에 접속하거나 자동 승계된다고 가정하지 않습니다.

헤드리스 서버의 Codex 로그인은 환경이 지원할 경우 `codex login --device-auth`를 사용할 수 있습니다. 설치된 CLI와 계정에서 지원되는지 확인한 뒤 사용합니다. 초기 개발의 대화형 인증과 상시 자동화의 인증·사용량 처리는 각각 확인합니다. 키·토큰·인증 파일을 채팅이나 Git에 붙이지 않습니다. [A급·OpenAI 인증 공식 문서](https://learn.chatgpt.com/docs/auth)

## 2. 최초 접속 이후의 작업 방식

| 구간 | 사용자 | 이 대화의 Codex | 서버 실행 주체 |
|---|---|---|---|
| 최초 준비 | 기존 SSH·tmux 접속, 필요한 CLI 로그인 | 환경에 맞는 준비 절차와 Git 계획 제공 | 사용자 SSH·tmux 세션 |
| 환경 조사·구축 | 서버 CLI에서 작업을 시작하고 필요한 인증 처리 | 설계·작업 명세 정리, Git 변경 검수 | 서버의 Codex CLI·Claude Code |
| 자동화 시험 | 작업 명세와 결과 확인 | 실패 분석, 기준 검수, 보완 | LangGraph 조정기와 어댑터 |
| 상시 운영 | 작업 접수, 정책 판단, 최종 결과 확인 | 요청 시 설계·검수·운영 지원 | systemd로 실행하는 조정기 |

초기에는 서버 CLI에 이 계획을 읽도록 전달하고, 구현 결과는 Git 커밋과 PR로 공유합니다. LangGraph가 준비되면 등록된 작업의 구현·검사·검수·수정 전달을 조정기가 처리합니다. 이 대화의 모든 메시지가 자동으로 작업 접수되는 기능은 별도 연결이 필요한 기능입니다.

tmux는 구축·점검용 대화형 세션에 사용합니다. 완성된 조정기는 systemd로 운영해 접속 종료·프로세스 종료·서버 재시작을 각각 검증합니다. tmux 세션 유지와 작업 상태 복구는 별도로 처리합니다.

조정기의 어댑터는 작업별로 `codex exec`와 `claude -p` 등의 비대화형 실행을 시작하고, 구조화된 결과·종료 코드·실행 기록을 수집합니다. 기존 대화형 터미널 화면에 문자를 보내 결과를 추측하는 방식은 채택하지 않습니다. [A급·OpenAI 비대화형 실행 공식 문서](https://learn.chatgpt.com/docs/non-interactive-mode), [A급·Claude Code 공식 문서](https://code.claude.com/docs/en/headless)

기획 에이전트는 추후 작업 분해와 담당 추천을 맡을 수 있으며, 허용 범위·의존 관계·한도 확인은 조정기가 담당합니다.

## 3. 최초 서버 점검

연결 직후에는 상태를 조회합니다. 조회 결과를 이용해 설치 방식과 자원 한도를 정합니다.

- 호스트·계정·현재 경로, 운영체제와 CPU 구조
- CPU·메모리·디스크 여유, 기존 서비스의 사용량
- Python·Git·Claude Code·Codex의 설치 경로와 버전
- 로그인 셸과 systemd 실행 환경의 차이
- GitHub·모델 서비스 접근과 사용할 인증 방식
- 작업 경로의 소유권과 실제 적용 가능한 실행 격리

예시 조회 명령은 다음과 같습니다. 설치·서비스 변경·재시작은 수행하지 않으며, 조회 자체에 대한 되돌리기 작업은 없습니다.

~~~bash
hostname
id
pwd
uname -m
cat /etc/os-release
nproc
free -h
df -h /
command -v git
command -v python3
command -v claude
command -v codex
~~~

출력 예시는 `uname -m`의 `aarch64` 또는 `x86_64`이며, 실제 결과로 패키지를 선택합니다. 명령 조회 결과가 없으면 현재 PATH에서 찾지 못한 상태로 기록하고 실제 설치 유무를 별도로 확인합니다. 인증 파일과 전체 환경변수 출력은 점검에 포함하지 않습니다.

전용 계정·작업 공간·프로세스 자원 한도를 구성합니다. Git worktree는 코드 작업 공간 분리에 사용하고, 실행 권한 격리는 별도 계정 또는 검증된 격리 환경으로 확보합니다. 구축 과정에서 필요한 관리자 작업은 작업 내용과 영향을 구체화해서 처리하며 상시 실행 계정에는 광범위한 관리자 권한을 부여하지 않습니다.

## 4. 단계별 구현 계획

| 단계 | 작업 | 결과물·완료 조건 |
|---|---|---|
| 0. 연결과 조사 | 기존 SSH·tmux 활용, 서버 Codex CLI 준비, 조회 중심 환경 점검 | Oracle의 올바른 계정·경로에서 명령을 실행하고 설치·자원 계획을 정함 |
| 1. 프로젝트 기반 | 기준 문서, 공통 작업 규칙, Python 환경, 의존성 잠금, 검사 명령 정리 | 새 작업 공간에서 같은 환경을 재현하고 기본 검사를 실행함 |
| 2. 작업 규격 | 작업·검수 결과 규격, 역할 등록부, 실행 식별자, 정책 버전 정의 | 누락·잘못된 결과·범위 이탈을 거부하고 에이전트별 출력을 공통 형식으로 변환함 |
| 3. 가짜 실행기 | LangGraph 흐름, 체크포인트, 실행 기록, 재시작 시 상태 확인 | 외부 모델 호출 없이 반려·수정·중단·중복·늦은 결과를 검증함 |
| 4. 실제 실행 연결 | Claude Code·Codex의 비대화형 실행, 결과 수집, 종료·취소·인증 검사 | 각 CLI를 단독 실행하고 성공·실패·시간 초과를 구분함 |
| 5. GitHub 통합 | 작업 접수, 브랜치·PR, CI 수집, 대상 커밋별 검수 | 실제 원격 변경과 필수 검사를 근거로 병합 준비를 판정함 |
| 6. 운영 시험 | systemd 실행, 사용량·시간 한도, 중단·복구·백업 절차 | 시험 작업의 자동 수정과 재검수를 완료하고 접속 종료 후에도 상태를 확인함 |

단계 1~3의 문서·코드 작성과 로컬 검증은 서버 연결 전에도 진행할 수 있습니다. 서버 설치·인증·자원 격리 검증과 단계 4~6의 Oracle 실행은 연결 이후에 진행합니다. 작업량과 일정은 단계 0의 확인 결과를 반영해 산정합니다.

각 구현 단위는 별도 브랜치와 PR로 기록합니다. 검수 대상 커밋을 고정하고, 수정 커밋이 생기면 관련 검사와 검수를 다시 수행합니다. 서버의 Codex·Claude Code 세션이 같은 작업 파일을 동시에 수정하지 않도록 작업 공간과 담당을 배정합니다.

## 5. 코드 구성안

아래 경로는 앞으로 만들 구성안이며 현재 구현 파일이 존재한다는 뜻이 아닙니다.

| 경로 | 담당 |
|---|---|
| `docs/` | 설계, 결정 기록, 운영·복구 절차 |
| `schemas/` | 작업 명세와 검수 결과의 형식 |
| `config/` | 비밀정보가 없는 역할·프로젝트·한도 설정 |
| `src/ai_company/workflows/` | LangGraph 단계와 분기·합류 |
| `src/ai_company/adapters/` | 가짜 실행기, Claude Code, Codex |
| `src/ai_company/runtime/` | 실행 시작·조회·취소, 시간 초과, 재시작 시 상태 확인 |
| `src/ai_company/policy/` | 완료 조건, 정책 변경, 필수 검증 판정 |
| `src/ai_company/integrations/` | GitHub 작업 접수·PR·CI 확인 |
| `src/ai_company/storage/` | 체크포인트, 실행 기록, 결과 파일 참조 |
| `tests/` | 상태 전이, 실패·복구, 어댑터·GitHub 통합 검증 |
| `deploy/` | 검증 후 적용할 systemd 설정과 운영 절차 |

어댑터의 공통 계약은 상태 점검, 실행 시작, 실행 조회, 취소, 결과 수집으로 둡니다. 실제 지원 능력과 인증·격리 상태를 등록부에 기록하고, 기능을 지원하지 않는 에이전트에는 그 기능이 필요한 작업을 배정하지 않습니다.

LangGraph는 단계·분기·체크포인트를 담당하고, 외부 CLI 프로세스와 GitHub 변경의 실제 완료 여부는 실행 관리 코드가 담당합니다. 파일 기반 체크포인트는 단일 서버 시험 단계에서 검증하며, 다중 서버·병렬 처리 확대 시 저장소와 작업 대기열을 재평가합니다. [A급·LangGraph 공식 문서](https://docs.langchain.com/oss/python/langgraph/overview), [A급·상태 저장 공식 문서](https://docs.langchain.com/oss/python/langgraph/persistence)

## 6. 작업과 결과의 필수 정보

- 작업: 작업 ID, 명세 버전, 목표, 완료 조건, 대상 저장소·기준 커밋, 허용 변경 범위, 필요한 검사, 시간·사용량·수정 한도
- 실행: 실행 ID, 시도 번호, 역할·도구·버전, 작업 공간, 시작·종료 시각, 프로세스 식별 정보, 종료 코드
- 검수: 검수 대상 커밋, 승인·수정 필요·판단 보류, 지적 ID, 재현·검증 근거, 미해결 항목
- 증적: 정책·명세·환경의 식별값, 필요한 입력 자료 식별값, 실제 CI 실행과 로그·결과 파일 참조

흐름의 진행 상태는 LangGraph 체크포인트를 기준으로 관리하고, 프로세스·외부 작업의 사실은 실행 기록과 실제 조회 결과로 확인합니다. GitHub 표시 상태는 이를 바탕으로 갱신하며 독립된 두 개의 진행 상태 원본을 만들지 않습니다. 큰 로그와 비밀정보는 작업 명세나 공개 PR 본문에 넣지 않습니다.

## 7. 처음부터 검증할 실패 시나리오

1. 정상 작업: 구현 → CI → 검수 → 현재 커밋 확인 → 병합 준비.
2. 반려 후 수정: 같은 지적 ID의 해결 근거를 다음 검수가 확인.
3. 수정 한도 초과: 추가 모델 호출 없이 중단하고 사유 기록.
4. 정책·완료 조건 변경: 기존 작업의 합격으로 처리하지 않음.
5. 중복 접수: 같은 작업을 다시 접수해도 실행·PR이 중복 생성되지 않음.
6. 오래된 결과: 현재 실행과 다른 결과는 상태를 변경하지 못함.
7. 시간 초과: 실행과 하위 프로세스의 종료 확인 전 재실행 금지. 종료 여부를 모르면 판단 보류.
8. 재시작: 이미 만든 커밋·PR·실행을 확인한 후 이어가며 불확실한 외부 작업을 무조건 반복하지 않음.
9. 검수 후 코드·기준 브랜치 변경: 기존 검사·승인을 그대로 재사용하지 않음.
10. 인증·사용량 한도·실행 환경 오류: 코드 오류와 구분해 대기·중단하며 합격으로 간주하지 않음.

복구 시 오래된 실행을 막는 실행 식별자와 소유권 확인을 사용합니다. 체크포인트 저장 성공만으로 외부 명령이 정확히 한 번 실행됐다고 단정하지 않습니다.

## 8. GitHub 작업 접수와 CI

초기에는 정해진 형식의 작업 명세와 허용된 사용자의 접수만 처리합니다. 공개 저장소의 임의 Issue·댓글을 서버 명령으로 실행하지 않습니다.

서버가 GitHub 작업을 주기적으로 조회하는 방식으로 시작합니다. 조회 주기는 사용량과 요청 제한을 확인해 정하며, 이후 필요하면 이벤트 수신 방식을 추가합니다. 코드 테스트는 GitHub 관리 실행 환경부터 검토합니다.

검증 증적에는 PR의 대상 커밋, 기준 브랜치 커밋, 실제 검사 대상 커밋, 필수 검사 이름과 실행 결과를 함께 기록합니다. 검사 누락·건너뜀·취소는 통과로 처리하지 않습니다. 변경된 검사 정의나 승인되지 않은 정책으로 기준이 약화되지 않았는지도 확인합니다.

서버 인증 정보는 서버의 제한된 인증 경로에 두고 작업 코드·로그·PR로 전달하지 않습니다. 에이전트가 수정할 수 있는 작업 공간에서 실행 정책과 원본 증적을 직접 덮어쓰지 못하게 구성합니다.

## 9. 운영과 되돌리기

- 자동화는 전용 systemd 서비스로 운영하고 작업 접수 중지·실행 취소·상태 조회를 제공합니다.
- 실행 시간, 사용량, CPU·메모리, 디스크·로그 보존을 기록하고 확인 가능한 한도를 설정합니다. 시험 전까지 미정인 한도는 실제 실행을 시작하는 조건으로 확정합니다.
- 중단 시 신규 접수를 멈추고 진행 중 실행의 종료 여부를 확인합니다. 관련 없는 기존 운영 서비스에는 중단 명령을 적용하지 않습니다.
- 버전 반영 전 실행 상태를 정리하고 일관된 상태 DB 백업과 실행 버전을 보관합니다.
- 되돌리기는 호환 가능한 이전 코드·설정으로 수행합니다. DB 형식이 변경됐으면 대응 백업·이행 절차를 사용합니다. 이미 발생한 GitHub 변경은 실제 상태를 대조한 뒤 처리합니다.
- 초기 완료 범위는 병합 준비입니다. 자동 병합·자동 배포와 기존 금융 작업의 재개는 이번 시험에 포함하지 않습니다.

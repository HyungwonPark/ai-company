# UI·UX 작업 분담과 GitHub 검수 계약

상태: 후속 구현 지침 제안 · 2026-09-16 · v1.0 · [문서 안내](README.md)

이 문서는 새 역할을 자동 등록하거나 운영 권한을 부여하지 않는다. PM과 마스터가 확정한 범위에서 문서·디자인·코드·검수를 연결하는 작업 방식이다. 같은 조건의 승인을 반복 요구하지 않고, 새로운 운영 변경은 기존 승인 대상·범위와 대조한다.

## 1. 에이전트가 읽는 순서

1. 저장소 AGENTS.md와 현재 작업의 사용자 지시·확정 계획.
2. product-experience/README.md의 기준 상태·후속 범위.
3. 담당 UX 요구와 DESIGN 컴포넌트·상태 규격.
4. 자신의 작업 명세와 선행 산출물.

필요한 문서만 담당 작업에 제공한다. 서로 다른 사본에 상태를 임의로 적어 원본과 충돌시키지 않는다. PRD·UX 요구는 Git 문서, 승인된 실행 명세·현재 상태·모델 사용량은 기존 원장, 실제 검증 결과는 해당 실행의 증적을 기준으로 한다. 동기화 근거가 없는 수동 TASKS/JOURNAL을 두 번째 실행 원장으로 만들지 않는다.

## 2. 역할과 산출물

역할은 논리적인 분담이며 모두 별도 프로세스로 상시 실행할 필요는 없다. 기존 서버의 최대 병렬 수·예산·격리·자격 정책을 유지한다.

| 역할 | 산출물 | 읽는 입력 | 완료 조건 |
|---|---|---|---|
| PM · Astra Ultra | 목표·완료 조건·질문·팀·의존 관계·작업 명세 | 마스터 대화, 현재 기능·제약 | 과제 범위와 사용자 판단이 분명함 |
| UX·화면 설계 | 사용자 흐름·상태별 화면·문구·토큰 | UX 요구, DESIGN | 빈 상태부터 오류·승인까지 행동이 정의됨 |
| 화면 개발 | 접근 가능한 화면·반응형·실제 이벤트 연결 | 합의된 화면·API 계약 | 지정 UX 요구와 상태 표현이 동작함 |
| 서버 개발 | 필요한 조회·다음 행동 데이터·전달 이벤트 | 동일한 API·상태 계약 | 권한·원문·버전·중복 방지 보존 |
| 독립 기능·UX 검수 | 시나리오 결과·접근성 측정·화면 비교·결함 | 요구·후보 커밋·실행 근거 | 코드 작성자의 설명 없이 기대 결과를 대조 |
| 읽기용 번역 · Haiku | 한국어 읽기 자료와 원문 참조 | 제한된 원문과 용어집 | 권한·수치·부정·조건 보존, 실패를 숨기지 않음 |
| 최종 검수 · Astra Ultra | 목표별 판정·잔여 위험·근거 | 동일 후보의 독립 검수 결과 | 미검증을 완료로 합산하지 않음 |

개발·일차 검수의 모델 후보는 기존 Astra High·Claude Opus 5 역할 정책을 따른다. UX 담당도 적격성이 확인된 후보를 사용하며 별도 새 모델을 필수로 추가하지 않는다. Claude의 시험 성공과 운영 활성화를 구분하고, 현재 실행 설정에서 실제로 가능한 후보만 배정한다. PM과 최종 검수의 모델이 같아도 최종 검수는 별도 검토 맥락에서 작성 결과와 근거를 독립적으로 대조한다. 코드 작성자가 자기 변경의 독립 검수자가 되지 않게 기존 작성 이력을 사용한다.

## 3. 병렬 진행 방식

짧은 계약 합의 후 화면·서버·검증 준비를 병렬로 진행한다. 예를 들어 프로젝트 식별 오류 표시를 만들 때 화면은 존재하지 않는 프로젝트 화면, 서버는 해당 오류 응답, 검증자는 잘못된 링크·권한·선택 상태 시나리오를 독립적으로 작성한다. 같은 파일을 수정해야 하면 소유권을 정하거나 직렬 통합한다.

작업 명세에는 다음을 기록한다.

```yaml
requirement_id: UX-01
role: frontend
goal: 잘못된 프로젝트 링크가 다른 프로젝트로 바뀌지 않게 한다
owned_paths: [구현 전에 합의한 실제 파일]
inputs: [프로젝트 조회 결과, 오류 응답 계약]
outputs: [변경 코드, 상태별 화면, 검증 결과]
acceptance: [원래 ID 유지, 오류 표시, 다른 프로젝트 결정 버튼 없음]
dependencies: [오류 응답 계약]
limits: [기존 기록과 승인 상태 보존]
```

이 예시는 문서 서식이며 자동화에 바로 넣는 유효 설정 파일이라고 주장하지 않는다. 실제 등록은 기존 스키마와 마스터가 확정한 계획에 맞춘다. UX 문서를 이유로 pilot 파일 허용 범위를 몰래 확장하지 않는다. 앱 자체의 UI 개선은 현재 서버 Codex의 구현 작업으로 진행하고, 제품 안의 자동 개발 범위 확장은 별도 작업이다.

## 4. 작게 나눌 첫 작업

| 작업 | 연결 요구 | 구현 범위 | 검수 핵심 |
|---|---|---|---|
| A. 프로젝트 찾기 | UX-01 | 목록·검색·설정 진입·생성 재시도 식별·잘못된 ID 처리 | 다른 프로젝트 조작 방지, 같은 생성 의도 재시도 후 프로젝트·첫 PM 요청 각 1개 |
| B. 상태와 다음 행동 | UX-02·03·05 | PM 요청·계획·실행 구분, 확인 항목 진입점 | 확정 전 병렬 진행 오표시, 요청/관측 모델 오표시 제거 |
| C. 역할별 진행 | UX-04 | 카드·전달 목록·선택 관계·이관·독립 대기 | 실제 이벤트·산출물·담당 연결 일치 |
| D. 읽기와 결정 | UX-06·07 | 보고 요약·승인 종류·모바일 확인 배지·복귀 | 원본 승인·번역·PR #10 보존 |
| E. 시각 정리 | DESIGN | 토큰·폰트 위계·간격·모바일·상태 예제 | Light/Black, 접근성, 주요 행동 발견 |

A와 B를 먼저 완료한다. C·D·E는 공통 컴포넌트와 조회 계약을 합의한 뒤 파일 소유권을 나눠 병렬 작업할 수 있다. 이미 구현된 요구는 재구현하지 않고 부족한 동작만 이슈로 등록한다.

## 5. 검수는 숫자보다 사용자 과제

아래는 필수 실패 조건이다. 나머지 화면이 예쁘거나 점수가 높아도 통과로 상쇄하지 않는다.

- 없는 프로젝트 링크가 다른 프로젝트의 화면·결정으로 연결됨.
- 계획 확정 전 개발이 시작되거나, 예정된 역할을 실행 중으로 표시함.
- 모델 요청값·모의 이벤트·오프라인 기록을 관측된 실시간 사실로 표시함.
- 사용자가 현재 프로젝트·다음 행동·기다리는 이유를 확인할 수 없음.
- 승인 대상·비용·범위·원본 버전을 읽거나 올바르게 결정할 수 없음.
- 키보드 또는 320px 화면에서 핵심 조작이 불가능함.
- 재연결·응답 유실·반복 클릭으로 승인·실행이 중복됨.
- 번역·화면 갱신이 원문·권한·과거 기록·PR #10의 pending을 변경함.

관련 기능 회귀와 UI 검사는 유지한다. 테스트를 구현을 그대로 따라 쓰는 수준으로 늘리지 않고 위 실패를 실제로 잡는지 확인한다. 문서만 바뀐 PR은 링크·명세 일관성·변경 범위를 확인하고 전체 모델 호출·운영 시험을 불필요하게 실행하지 않는다.

### 근거 표

| 요구 ID | 후보 커밋 | 검사 종류 | 입력 상태 | 기대·관측 결과 | 근거 | 판정·제약 |
|---|---|---|---|---|---|---|
| UX-01 | 실제 SHA | 브라우저 모의 | 프로젝트 2개·없는 ID | 다른 프로젝트로 이동하지 않음 | 테스트·캡처 | 검증 후 작성 |
| UX-03 | 실제 SHA | 실제 마스터 조작 | 최신 제안 | 직접 확정 후 실행 1건 | 인증된 이벤트·실행 ID | 사용자 조작 전 미검증 |

종류는 문서 검토·단위 검사·브라우저 모의·격리 모델 호출·운영 관측·마스터 실기기로 구분한다. 보고에서 이 표의 빈 칸을 완료로 세지 않는다. 최종 후보 커밋과 CI·캡처·실행 ID가 서로 일치해야 한다.

## 6. GitHub 이슈와 PR 서식

아래 서식을 작업 본문에 사용한다. 문서를 읽었다는 이유로 사용자에게 같은 계획을 다시 승인받지 않는다. 승인되지 않은 새 운영 행동은 구체적인 변경안·검증·복구안까지 준비한 뒤 기존 권한과 대조한다.

### 이슈

```markdown
## 사용자 문제
누가 어떤 일을 하다가 어디에서 막히는가?

## 기대 경험
사용자가 할 행동과 화면에서 확인할 결과.

## 범위
요구 ID, 대상 화면, 담당 파일, 제외 항목.

## 수용 기준
입력 상태 → 사용자 행동 → 관측 결과.

## 근거와 의존성
현재 재현, 참조 문서, 선행 계약, 화면 자료.
```

### PR

```markdown
## 해결하는 문제와 변화
사용자가 무엇을 더 쉽게 할 수 있게 되는가?

## 변경 범위
요구 ID, 코드·문서·데이터 변경, 기존 계약 보존.

## 검증
후보 커밋, 검사 종류, Light/Black·모바일 화면, 필수 실패 조건 결과.
실제 사용자 확인과 모의 결과를 구분.

## 운영 적용
미적용/적용, 정확한 후보·영향·복구, 기존 승인 범위와 차이.

## 남은 일
미검증 항목, 담당자, 다음 행동. 전체 완료 여부.
```

디자인 스냅샷은 `docs/assets/<작업명>/` 등 기존 규칙에 맞춰 저장하고 실제 렌더링과 모의 데이터를 구분한다. 운영 비밀번호·로그인 토큰·서명키·인증 파일은 저장하지 않는다. 저장소 밖 문서를 전달해야 하는 경우 문서 본문·검토 가능한 자료를 Git에 남기되 비공개 운영 증거는 안전한 원본 참조만 남긴다.

## 7. 서버 Codex에 전달할 작업 지시

> docs/product-experience/README.md, UX.md, DESIGN.md, DELIVERY.md를 읽고 현재 구현과 요구 ID를 대조해 주세요. 먼저 ‘프로젝트 찾기’와 ‘실제 상태·다음 행동’을 개선하고, 화면·서버·독립 검증의 계약을 합의한 뒤 역할별로 병렬 진행하세요. 이름·목표만으로 PM과 시작하는 흐름을 유지하고, 사용자가 경로·하네스·함수 명세를 작성해야 하는 기본 화면으로 되돌리지 마세요. Light·Black의 역할 카드·업무 전달·모바일 상태를 실제 데이터 계약과 연결해 검증하세요. 기존 코드·준비된 운영 패키지·PR #10 pending을 보존하고 문서 요구를 새로운 배포나 자동 개발 권한으로 해석하지 마세요. 새 후보를 준비했다면 현재 승인 대상과 차이를 명확히 보고하세요.

마스터의 실제 앱 입력·계획 확정은 준비된 후보의 실사용 검증으로 남는다. 서버가 이를 대행한 결과를 사용자 경험 검증으로 표시하지 않는다. 문서 정리나 Claude 시험 성공을 이유로 실사용 전체 완료를 선언하지 않는다.

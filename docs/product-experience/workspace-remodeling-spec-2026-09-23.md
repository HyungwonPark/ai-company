# 전체 작업실 재설계 보충 명세 · 2026-09-23

사용자가 제안한 **업무 / 팀 / 기록 분리**와 **담당 모델이 바뀌어도 이어지는 업무**를 확인하는 격리 시안이다. 기본 추천은 순서형이며, 한눈형을 같은 자료로 비교한다. 사용자가 디자인을 최종 선택했거나 운영 화면에 적용했다고 기록하지 않는다.

## 근거와 범위

- 최초 작성 기준은 사용자 대화와 [작업실 통합 명세](integrated-workspace-ecc-archify-2026-09-16.md)다. 당시 Work 원문은 미게시 상태였으며 이 파일은 원문을 읽은 기록이 아닌 대화 기반 후속안이었다. 이후 [PR #23의 문서 안내](https://github.com/HyungwonPark/ai-company/blob/a446a5146f8cbb06a4f7575e64a17cf530c5ef49/docs/work-reviews/README.md)와 연결된 원문 3개를 직접 읽고 R1~R5 보완에 반영했다. 과거의 출처를 소급 변경하지 않으며 [이번 대조·검증 기록](pr22-review-followup-2026-09-23.md)에 차이를 남긴다.
- 기존 제품 대조 기준은 PR #21의 `f901f78`이며, 이번 시안은 별도 초안 PR #22다. 이 문서와 시안은 후속 검토 자료이며 기존 완료·운영 검증을 초기화하지 않는다.
- [컬리 원문](https://helloworld.kurly.com/blog/ai-orchestration-2/)은 요구·완료 기준을 정하는 계획, 작업 의존 DAG와 병렬 수행, 구현 후 검증, 세션 밖 기록의 참고다. **업무 / 팀 / 기록 화면 분리는 이번 제품 설계 제안**이며 원문의 UI 규칙이 아니다.
- 대상은 [격리 시안](../previews/task-workspace/index.html)과 그 `preview.js`, `style.css`다. 기존 제품 그래프·관리 API·DB·worker·운영 서비스는 이 시안으로 교체하지 않는다.
- 모델·플러그인 설치, 실제 모델 호출, pilot 허용 파일 확대, 금융 프로젝트 재개, 병합·배포는 이 작업에 포함하지 않는다.

## 풀려는 사용자 과제

현재 역할 그래프는 담당자와 전달 근거를 확인하는 데 유용하지만, 처음 쓰는 사람은 지금 해야 할 일과 기다리는 업무부터 알아야 한다. 역할명과 모델명이 바뀔 때 업무 자체가 새로 생긴 것으로 읽히지 않게 한다.

첫 흐름은 **프로젝트 → 계획 → 진행 → 승인 → 결과**다. 프로젝트 이름과 자연어 목표로 시작하고, 계획에서는 범위·완료 조건을 읽는다. 명세 저장, 새 계획 요청, 직접 확정, 후보 수용을 서로 다른 사건으로 유지한다.

| 보기 | 먼저 답하는 질문 | 중심 자료 |
|---|---|---|
| 업무 | 무엇을 하고, 무엇을 기다리는가? | 업무명·상태·선행 조건·전달물·다음 행동 |
| 팀 | 누가 어떤 일을 맡고 있는가? | 역할·현재 담당·요청 모델·관측 근거 |
| 기록 | 무엇이 언제 왜 바뀌었는가? | 배정·이관·검사·전달 이벤트와 원본 참조 |

업무 상세에서 팀·이관 근거로 이어지게 하되 모델·담당 역할을 업무 제목으로 쓰지 않는다. 검사·독립 검수·최종 검수는 같은 통합 업무의 단계로 표시하며 세 독립 업무로 중복 집계하지 않는다.

## 같은 내용으로 비교하는 두 배치

| 시안 | 구조와 추천 이유 | 확인할 부담 |
|---|---|---|
| 순서형 · 추천 | 상단 단계 탐색과 현재 단계 본문, 옆의 다음 행동·결정·기록 요약. 처음 쓰는 사람에게 순서를 설명하기 쉽다. | 여러 단계를 비교할 때 이동이 늘어나는가? |
| 한눈형 · 비교 | 왼쪽 단계 탐색, 상단 현재 행동, 본문과 요약을 함께 배치한다. 실행을 반복 확인하는 상황을 비교한다. | 요약과 본문의 중복이 핵심 행동을 가리는가? |

두 배치는 같은 프로젝트·업무·팀·기록·상태 함수를 사용한다. Light·Black도 동일한 내용의 테마다. 레이아웃 전환은 프로젝트나 선택 실행을 새로 만들지 않는다. 기존 A/B/C 시안과 역할 그래프는 비교·회귀 자료로 보존한다.

## 시안에 들어 있는 동작과 한계

- 가상 프로젝트에서 로그인 화면 개발과 오류 검사 작성을 병렬로 표시하고 두 결과가 모이는 통합 검수로 연결한다. 새 프로젝트에서 고정 예시 목표를 명시적으로 선택하면 같은 프로젝트의 대화·계획 수정·확정·진행·이관·검수·결정을 순서대로 체험한다. 임의 목표는 대화 초안으로 보존하며 고정 로그인 계획을 맞춤 응답으로 제공하지 않는다.
- 새 프로젝트 입력·PM 답변과 시안의 상태를 `sessionStorage`에 보관한다. 사용자 행동은 내용 정리 → 계획 확인 → 이 계획으로 시작이며 명세 저장·버전·계획 요청·직접 확정은 별도 예시 사건이다. 계획 준비 중·실패·재시도·수정 후 재검토에서도 직접 확정 전에는 실행이 없다. 실행 가능한 운영 명세와 실제 API·모델·검사 호출은 없다.
- 탭당 새 예시 프로젝트는 **1개**다. 다시 시작하면 기존 입력·확정 기록을 열어 원래 예시 프로젝트를 보존한다. 다중 프로젝트 생성이나 운영 저장을 구현한 것으로 보지 않는다. 예시 초기화는 해당 탭의 시안 상태만 초기화한다.
- `현재 · 2차 작업`과 `이전 · 1차 작업`은 서로 다른 예시 실행·계획 ID다. 이전 후보 승인 요청을 현재 실행에 섞지 않는다. 신규 프로젝트는 확정 전 실행 ID가 없다.
- 이관 예시는 동일 업무 ID를 유지하며 Astra에서 Claude로 담당 표시를 바꾼다. 계정 한도 원인은 작성된 예시이며 실제 이관 증거가 아니다. 관측 설정은 미확인으로 표시한다.
- 프로젝트 목록과 승인 화면은 이전 실행의 미처리 요청을 표시하고 정확한 실행으로 이동한다. 후보 수용·수정 요청·보류는 대상별 `preview_only` 기록이며 원래 예시 요청은 `pending`이다. 수정 요청은 의견과 다음 계획 정리를 안내하며 자동 개발 재실행을 약속하지 않는다. 보류는 제품 API 결정이 아닌 시안의 나중에 보기다.
- 일반·빈 목록·연결 끊김·긴 이름·모두 한도 대기·반복 실패를 비교한다. 한도 대기와 실패 상한도 예시다. 원인 조사 표시가 추가 개발·재시도 권한을 만들지 않는다.

## 실제 제품 자료와 연결할 때의 계약

기존 조회 응답·불변 명세를 원본으로 유지한다. 시안의 `example-*` 식별자·가상 시각·후보·digest는 실제 증거가 아니다.

| 내용 | 기존 소스의 실제 필드 | 연결 시 주의 |
|---|---|---|
| 업무 ID | `flow_tasks.task_id`, overview `tasks[].id` | 담당 이관은 같은 업무, 새 `execution_id`·`generation`·담당자다. |
| 업무 제목 | `specification.task.goal`, 확정 계획 `content.roles[].goal` | 자동 배정의 `tasks[].title`은 `role.name`일 수 있어 업무 목표와 구분한다. |
| 역할·현재 업무 | `run.role_ids`, `run.roles[key].task_id`, `tasks[].role_id` | 최신 시각·이름 유사도로 과거 실행에 현재 역할을 연결하지 않는다. |
| 선행 관계 | 계획 `roles[].depends_on`; 실제 `plan.dependency_artifacts` | 예정 의존과 실제 결과 전달은 구별한다. |
| 모델 | `assignment.requested`와 `assignment.observed` | 관측 `status/source/scope/backend_model_verified`를 함께 읽고 없는 값은 미확인이다. |
| 상태·대기 | `tasks[].status/stage/wait_reason/resume_at` | 한도·선행·판단 대기를 전체 목표 실패로 합치지 않는다. |
| 결과·근거 | `candidate_sha`, 전달 `artifact_refs`, 보고 `verification/review_reports/evidence` | 해시만으로 파일명·다운로드·검사 성공을 만들지 않는다. |
| 이관 | `ownership_transferred`, `previous_execution_id`, 세대와 체크포인트 | 실행 이력 배열 전체 길이를 이관 횟수로 세지 않는다. |
| 실행·승인 | `project_id/plan_id/plan_digest/run_id`, `run.approval_id`, `subject_digest/artifact_sha` | 같은 실행의 `approval_refs/report_refs`와 정확한 후보를 유지한다. |

출처: [조회 투영](../../src/ai_company/workspace_graph.py), [협업 근거](../../src/ai_company/collaboration.py), [업무 연결](../../src/ai_company/management.py), [실행 이관](../../src/ai_company/dispatcher.py), [역할·수정 실행 생성](../../src/ai_company/automation.py).

중요한 경계는 **이관과 수정 차수**다. 이관은 task ID를 유지하지만 수정 작업은 `run ID + role key + revision`으로 새 task ID를 만들고 `role_history`에 이전 작업을 남긴다. 후속 화면에서 이들을 연결해 읽을 수는 있으나 같은 불변 명세를 가진 하나의 실행으로 덮어쓰면 안 된다.

현재 그래프 응답은 역할·검사 단계 중심이며 업무 목표 전문, 완료 기준, 이전 모델, 구체적 이관 원인, 파일 산출물 목록이 충분히 노출되지 않는다. 이관 선의 일반 설명만으로 quota/context 원인을 특정할 수 없다. 실제 제품 연결에는 필요한 읽기 필드의 제한적 확장이 필요하며, 운영 원문·승인·실패 기록을 디자인에 맞춰 바꾸지 않는다.

## 검수 조건과 증거

아래는 시안의 수용 조건이다. 실제 수행 결과·검증 커밋·원격 CI·미리보기 산출물은 [PR #22 검증 기록](https://github.com/HyungwonPark/ai-company/pull/22)에 연결한다. 검사 코드의 존재나 이 문서만으로 PASS를 판단하지 않는다. 초보 사용자 사용성 시험과 마스터 APK 실기기 확인은 별도 미검증 항목이다. 기존 운영 상태·승인 범위는 그대로다.

- 두 배치 × Light·Black × 320/390/1440px의 프로젝트·계획·진행·승인·결과 렌더링, 긴 한국어와 넘침 확인.
- 키보드 접근, 대화상자 닫기·포커스 복귀, 터치 영역, 확대와 모바일 읽기 순서 확인.
- 새 목표 입력 → 고정 예시 선택 → PM 대화 → 내용 정리 → 계획 준비·수정 → 직접 확정 → 같은 실행의 진행·검수·결정에서 입력 보존·중복 확정·탭당 한 개 제한 확인. 새 탭 초기화, 준비 실패·재시도·오래된 계획 재사용 거부도 확인.
- 업무·팀·기록 전환, 담당 이관 전후 같은 task ID, 통합 단계 중복 집계 방지 확인.
- 현재/이전 실행 전환 시 계획·승인·결과 결속과 후보 선택의 `preview_only` 범위 확인.
- 빈 목록·연결 끊김·전체 한도 대기·반복 실패에서 가능한 읽기와 제한되는 조작 확인.
- 작성자와 별도 검수자의 실제 화면·핵심 조작 기록, 수정 내역, 남은 제약을 별도 증거로 추가.

## 다음 사용자 검수 · 세 과제

1. 이름과 목표로 새 프로젝트를 시작해 계획 확정까지 찾아간다. **명세 저장 직후 실제 작업이 시작되는지** 자신의 말로 설명한다.
2. 현재 실행에서 기다리는 업무, 계속하는 업무, 통합 검수의 선행 조건을 찾는다. 이관 예시를 보고 **같은 업무에서 무엇이 바뀌었는지** 설명한다.
3. 이전 실행의 결과와 후보를 찾아 근거를 읽고 선택 예시를 남긴다. **현재 실행과의 차이, 후보 수용과 배포의 차이**를 설명한다.

두 배치에서 같은 과제를 수행하며 막힌 위치·되돌아간 횟수·잘못 이해한 상태를 기록한다. 순서형 추천은 이 관찰로 다시 판단하며, 자동 조작 성공을 초보 사용자에게 쉽다는 증거로 바꾸어 적지 않는다.

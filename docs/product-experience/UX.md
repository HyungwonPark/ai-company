# 사용자 흐름과 화면 계약

상태: 후속 설계 제안 · 2026-09-16 · v1.0 · [문서 안내](README.md)

## 1. 기본 경험

마스터는 ‘무엇을 만들고 싶은지’ 말한다. PM은 부족한 조건을 질문하고 목표·완료 조건·팀·병렬 작업을 제안한다. 마스터가 계획을 확정하면 실행한다. 마스터는 PM과 대화하고, 다른 에이전트의 활동은 진행 화면에서 관찰한다. 각 에이전트에게 직접 메시지를 중계하지 않는다.

기술 입력을 숨기는 것만으로 편의성이 완성되지 않는다. 각 화면의 첫 영역에서 **현재 프로젝트, 현재 상황, 다음 행동**을 이해할 수 있어야 한다. 보고서는 결과를 설명하고, 승인은 사용자의 결정을 받는다.

## 2. 화면 구성

| 위치 | 기본 내용 | 주요 행동 |
|---|---|---|
| 공통 상단 | 프로젝트 이름·선택, 실제 연결 상태, 최신 확인 시각 | 프로젝트 목록 열기 |
| 프로젝트 목록 | 최근 프로젝트, 이름 검색, 목표 요약, 현재 상태, 내 확인 건수 | 프로젝트 열기 / 새 프로젝트 |
| 매니저 | 목표 한 줄, 다음 행동 카드, 대화·팀 | 메시지 보내기 / 계획 검토 |
| 진행 | 목표 대비 요약, 병렬 작업, 전달물, 대기 사유 | 역할·전달물 상세 보기 |
| 승인 | 미결정 항목, 대상·영향·선택지·기한 | 개별 항목 검토·결정 |
| 기록 | 종합 보고, 완료 결과, 과거 결정과 작업 기록 | 결과·근거 열기 |

주요 이동은 매니저·진행·승인·기록 네 곳으로 정리하는 제안이다. 기존 보고 화면은 기록에서 찾을 수 있게 연결하고 기존 링크는 보존한다. 프로젝트 선택은 모든 화면에서 가능해야 하며, 선택 영역에 ‘전체 프로젝트’와 ‘현재 프로젝트 설정’ 진입점을 제공한다. 기존 개요·하네스 고급 설정은 현재 프로젝트 설정에 둔다. 기존 `#project?project=<실제ID>` 링크는 같은 프로젝트의 설정으로 연결하고 목록의 별도 주소는 구현 계약에서 정한다. 모바일 승인 건수 배지는 숨기지 않는다. 메뉴 이름을 줄이더라도 접근성 이름과 보조 설명은 유지한다.

### UX-01 프로젝트 발견과 생성

- 처음 들어오면 ‘어떤 일을 맡기고 싶으신가요?’와 새 프로젝트 시작 행동을 표시한다. 사용 기록이 있으면 최근 프로젝트로 돌아가는 행동도 함께 제공한다.
- 새 프로젝트에는 이름과 목표 두 항목만 요구한다. 목표 예시는 사용자 언어로 제공하고, 함수 이름·파일 경로·하네스를 필수 입력으로 요구하지 않는다.
- 현재 두 파일 검증만 지원한다면 ‘현재는 제한된 검증 프로젝트를 실행할 수 있습니다’라고 생성 전에 표시한다. 일반 목표를 입력하면 PM이 실행 범위 차이를 설명한다. 내용을 몰래 pilot 목표로 바꾸거나 바로 개발하지 않는다.
- 성공 후 서버가 반환한 실제 프로젝트 ID로 이동한다. ‘프로젝트를 만들었습니다. 매니저에게 목표를 전달했습니다’와 지속적으로 사용할 프로젝트 링크를 제공한다.
- 생성 실패·중복 제출·응답 유실 때 입력을 보존한다. 같은 생성 의도를 재시도하면 프로젝트 1개와 첫 PM 요청 1개만 남도록 클라이언트와 서버의 멱등성 계약을 구현·검증한다. 현재 생성 폼이 재시도 식별자를 전달하지 않는 부분을 구현 과제로 포함한다. 식별자는 서버의 사용자·생성 의도에 결합하고, 성공 여부가 불확실한 같은 요청에서 새로 발급하지 않는다. 같은 이름이어도 별개 생성 의도는 별개 프로젝트다.
- 없는 ID, 권한 없는 ID, 삭제된 ID는 다른 프로젝트로 바꾸지 않는다. ‘프로젝트를 열 수 없습니다’와 목록으로 돌아가기를 표시한다. 오류 화면에서 다른 프로젝트의 승인 버튼을 제공하지 않는다.
- 인수인계에는 실제 프로젝트 이름·ID·링크·현재 단계가 있어야 한다. 미생성 예시는 ‘새로 만들 프로젝트’라고 표시한다.

### UX-02 목표 입력과 PM 대화

- ‘매니저와 시작’은 목표 저장과 첫 PM 요청을 한 번 기록한다. 요청 저장·접수·응답 작성 중·답변 도착을 구분한다. 저장 성공을 실제 모델 응답으로 표시하지 않는다.
- PM 질문은 한 번에 가장 필요한 소수의 질문부터 제공한다. 추천 답변은 입력을 돕지만 자동 전송·승인하지 않는다. 사용자는 자신의 말로 답할 수 있다.
- 답변의 맨 위에는 제안 요약, 결정이 필요한 내용, 다음 행동을 둔다. 긴 작업 명세는 펼쳐 읽는다.
- 팀 조정 중에는 어떤 제안이 최신인지 표시한다. 새 제안이 대기 중이면 이전 계획 확정이 차단된 이유를 버튼 근처에 설명한다.
- 뒤로가기·프로젝트 전환·재접속 때 초안을 프로젝트별로 보존한다. 민감한 입력을 공개 캐시나 다른 계정에 노출하지 않는다. 자동 복원된 초안을 전송하지 않는다.
- PM 응답이 오래 걸리면 실제 요청 상태와 마지막 갱신 시각을 표시한다. 근거 없는 완료 예상 시각이나 가짜 실시간 출력은 만들지 않는다.

### UX-03 팀 확인과 계획 확정

여기서 팀 카드는 확정 전 제안이며 역할명, 맡길 일, 완료 조건, 담당 모델, 준비 상태 순서다. 실행 중 역할 카드는 DESIGN의 순서를 따른다. 기본 화면은 최대 두 줄 요약을 제공하며 전문을 열 수 있다. 모델 요청 설정과 확인된 실행 설정은 각각 표시한다. 아직 실행 전이면 ‘예정: Astra · High’처럼 읽히게 한다. ‘적용 확인’은 해당 실행의 근거가 있을 때만 쓴다.

계획 확정 화면은 목표·이번 범위·하지 않는 일·역할·완료 조건·예산과 중요한 제한·다음 실행을 보여 준다. 경로·하네스·정책 digest는 상세에 유지하되 승인 대상을 판단하는 데 필요한 범위·비용·환경은 접지 않는다. 원문 보기와 번역 상태를 제공하고 원본 버전에 결합한 기존 확정 규칙을 유지한다.

버튼은 ‘이 계획 확정’처럼 결과를 설명한다. 확정 후 ‘실행 준비 중’과 같은 실행 ID에 연결된 진행 화면을 제공한다. 계획에 병렬 역할이 있다는 사실은 ‘독립 역할 2개 · 병렬 배치 예정’이다. 실제로 겹쳐 실행 중인 작업이 확인된 때에만 ‘2개 작업 진행 중’이라고 표시한다.

### UX-04 역할별 진행과 전달

- 역할 카드와 전달 목록은 [DESIGN.md](DESIGN.md)의 시각 규격을 따른다. 역할과 모델을 구분해 모델 이관 중에도 같은 역할·작업의 연속성을 유지한다.
- 독립 작업은 병렬로 보여 주고, 실제 의존 관계만 연결한다. 계획·설계상의 연결과 실제 전달 기록을 범례로 구분한다.
- 전달을 선택하면 ‘누가 → 누구에게 / 무엇을 / 왜 / 언제 / 어떤 결과’를 읽을 수 있다. 관련 산출물·검사·수정 요청으로 이동한다.
- 요약은 완료 조건 기준으로 제공한다. 산출물 3개 중 1개 검증 완료처럼 분모와 기준이 명확할 때만 비율을 사용한다. 알 수 없는 전체 진척률을 임의 계산하지 않는다.
- 독립 작업 한 개의 한도 대기와 전체 실행 차단을 구분한다. 모든 적격 후보가 없으면 실제로 기다린다고 표시한다.

### UX-05 ‘정체’ 대신 원인과 행동

아래는 새 DB 상태를 강제로 추가하는 목록이 아니라 기존 실행 사실을 사용자에게 설명하는 표시 계약이다. 구현 시 기존 상태값과 원인을 명시적으로 매핑한다.

| 사용자에게 보이는 상태 | 반드시 함께 표시할 내용 | 기본 행동 |
|---|---|---|
| 매니저 답변 대기 | 요청 접수 여부, 마지막 갱신 | 대화 보기 |
| 계획 확인 필요 | 최신 계획, 확정 후 시작되는 범위 | 계획 검토 |
| 적용 승인 필요 | 정확한 운영 변경 대상·영향·복구·후보 버전 | 적용안 검토 |
| 사용량 회복 대기 | 해당 역할, 대체 후보 확인 결과, 알려진 재개 시각 | 대기 상세 |
| 다른 에이전트로 전달 중 | 이전·새 담당, 이관 이유, 확인된 진행 | 전달 보기 |
| 앞 작업 대기 | 어떤 산출물을 기다리는지 | 앞 작업 보기 |
| 연결 확인 필요 | 마지막 확인 시각, 읽고 있는 기록의 시점 | 다시 연결 |
| 문제 발생 | 사용자 언어의 원인, 자동 복구 여부, 영향 범위 | 문제 보기 |
| 검증 완료·결정 대기 | 검증한 후보와 아직 남은 결정 | 결과 검토 |

자동 처리할 일과 사용자 결정이 필요한 일을 분리한다. 사용자가 승인할 대상이 없는 worker 일시 대기를 ‘승인 필요’로 만들지 않는다. 동시에 여러 미결정 항목이 있어도 각각 영향을 받는 작업만 대기한다. 나머지 독립 작업의 진행 여부는 실제 기록으로 표시한다.

다음 행동은 원본 상태·최신 계획·승인 요청에 근거해 계산한다. LLM의 안내 문장만으로 버튼을 활성화하거나 결정을 실행하지 않는다. 서버가 지원하지 않는 승인 종류는 ‘서버 적용안 확인’ 같은 읽기 안내로 제공하고 가짜 승인 버튼을 만들지 않는다.

### UX-06 보고와 승인

보고의 첫 부분은 ‘목표 / 이번 결과 / 남은 일 / 문제가 생긴 부분 / 내 결정’ 다섯 항목이다. 시스템 집계, PM 판단, 번역의 출처를 구분한다. 테스트 수만 나열하지 말고 사용자가 무엇을 할 수 있게 됐는지 설명한다.

승인은 종류를 표시한다: **계획 확정, 운영 적용, 비용 사용, 결과 승인**. 실제 백엔드가 지원하는 종류와 권한만 제공한다. 채팅의 ‘네’나 다른 단계의 승인을 포괄 승인으로 재사용하지 않는다. 이미 유효하게 승인된 같은 대상·범위·버전에는 중복 질문을 만들지 않는다. 대상이 바뀌면 무엇이 달라졌는지 비교해서 보여 준다.

승인 카드에는 대상 프로젝트, 바뀌는 것, 영향과 중단 가능성, 비용 상한, 되돌리기, 승인 후 행동, 대상 버전을 제공한다. 변경 핵심과 비용을 ‘상세’에 숨기지 않는다. ‘승인’, ‘수정 요청’, ‘나중에’는 서버가 실제 지원하는 처리와 연결한다. 목록 배지와 푸시는 안내이며 결정 자체가 아니다.

번역이 대기·실패한 경우 원문 보기와 번역 상태를 제공한다. 번역이 원문·권한·정책·승인 대상을 바꾸지 않는다. 경로·수치·버전 보존 검사와 의미 검토를 별도로 기록한다.

### UX-07 복귀·모바일·APK

기존 APK에서 같은 도메인 화면을 갱신하는 경우 새 APK가 필요한지 실제 배포 구성으로 판단한다. 웹 적용을 새 APK 배포라고 부르지 않는다. 로그인 후 목표 입력, 키보드가 열린 상태의 보내기, 뒤로가기, 팀 탭, 계획 확정, 진행으로 복귀를 실기기에서 확인한다.

오프라인에는 마지막 자료의 시점을 표시하고 승인·확정의 성공을 로컬에서 만들어 내지 않는다. 연결 복구 후 서버 결과를 대조해 같은 실행을 유지한다. 오래된 화면 버전은 갱신 안내를 하되 입력 초안을 잃지 않게 한다.

## 3. 사용자에게 요청하는 검증

계획 확정은 실제 마스터가 수행한다. 개발자는 그 전까지 열리는 정확한 링크·입력 예시·관찰할 결과를 준비한다. 로그인 비밀번호·토큰을 채팅에 요구하지 않는다.

| 관찰 과제 | 제안하는 사용성 목표 | 기록 |
|---|---|---|
| 설명 없이 프로젝트를 찾거나 새로 시작 | 30초 안에 진입점을 찾음 | 걸린 시간, 헤맨 위치, 도움 요청 |
| 자연어 목표로 PM 요청 시작 | 2분 안에 기술 필드 입력 없이 완료 | 실제 입력·요청 ID, 실패/재시도 |
| 현재 상태와 다음 행동 설명 | 화면만 보고 자신의 말로 설명 가능 | 사용자의 설명, 잘못 이해한 점 |
| 계획 확정과 운영 적용 구분 | 둘의 영향을 혼동하지 않음 | 설명과 실제 선택 |
| 기다리는 역할과 진행 중 역할 구분 | 자동 대기 때문에 전체가 멈췄다고 오해하지 않음 | 선택한 카드와 설명 |

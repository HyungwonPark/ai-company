## 문제 정의

사용자는 ‘상태 집계 검증’ 프로젝트의 위치를 찾지 못했다. 안내도 실제 생성 여부를 확인하지 않은 채 기존 프로젝트처럼 설명했다. 따라서 사용자가 다음 행동을 찾기 어려운 문제에는 화면 탐색과 안내의 사실성 모두가 포함된다. 이후 아래 세 가지도 소스·기존 화면 자료에서 점검 대상으로 확인했다. 실제 휴대폰 사용성 시험을 했다는 뜻은 아니다.

1. 프로젝트 선택과 현재 프로젝트 상세가 가깝게 묶여 있어 전체 목록·새 시작의 위치가 불분명하다. 잘못된 프로젝트 ID를 첫 프로젝트로 바꾸는 동작은 다른 프로젝트를 조작할 위험을 만든다.
2. 계획에 독립 역할이 있다는 이유만으로 ‘병렬 진행’이라고 표시하면 실행 전 준비와 실제 수행을 혼동하게 된다.
3. 모델·추론 요청값을 관측된 실행값처럼 읽게 만드는 표시는 신뢰를 떨어뜨린다. 반대로 기술 세부값을 전부 기본 화면에 노출하면 목표와 다음 행동이 묻힌다.

위 항목은 [기준 app.js](https://github.com/HyungwonPark/ai-company/blob/c1af888e8e5d6c7da9f26780ec06751a866147ea/src/ai_company/web/app.js), [manager-ui.js](https://github.com/HyungwonPark/ai-company/blob/c1af888e8e5d6c7da9f26780ec06751a866147ea/src/ai_company/web/manager-ui.js)를 기준으로 구현 전 재현하고 수정 전후를 비교한다.

## 우선 구현 순서

| 순서 | 사용자에게 생기는 변화 | 완료 기준 |
|---|---|---|
| P0 | 프로젝트를 찾고 올바른 프로젝트로 들어감 | 잘못된 ID의 조용한 전환 없음, 생성 직후 바로 열림, 목록·검색·최근 프로젝트 제공 |
| P0 | 현재 무엇을 기다리는지와 다음 행동을 이해함 | ‘확인 필요 / 자동 대기 / 문제 발생’ 분리, 해당 항목으로 바로 이동 |
| P0 | 자연어 목표에서 PM 대화를 시작함 | 함수·경로·역할 파일 입력 없이 생성, 요청 저장과 실제 응답 구분, 제한된 실행 범위 사전 표시 |
| P1 | 팀의 병렬 작업과 주고받은 결과를 이해함 | 실제 역할·작업·전달 이벤트에 연결된 카드·목록·선택 강조 |
| P1 | 읽기 쉬운 Light·Black과 모바일 화면 | DESIGN 규격과 필수 상태별 화면 검수 통과 |
| P2 | 지원 프로젝트 범위를 넓힘 | 별도 실행 계약·격리·한도·검증·승인 범위를 먼저 확장 |

P2를 이번 문서나 UI 구현만으로 완료하지 않는다. 새 설계 후보를 계속 추가하느라 이미 준비한 실사용 검증을 무기한 미루지 않는다. 승인된 후보가 있다면 그 범위의 적용·사용자 관찰을 진행하고, 발견한 개선을 작은 후속 PR로 연결한다.

## 검증 수준

‘요구사항 작성’, ‘코드 구현’, ‘모의 화면 검사’, ‘실제 서비스 관측’, ‘마스터 직접 조작’을 각각 기록한다. 321개 등 기존 회귀 수는 당시 코드 검사의 근거이며 이 문서의 사용성 검증을 대신하지 않는다. 숫자·모델명·진행률·성공 배지를 근거 없이 채우지 않는다.

접근성 수치의 공식 근거는 DESIGN에 링크한다. 참고 저장소는 구현 방식을 확인한 1차 코드 자료이며 사용자 편의성의 효과를 입증한 연구로 취급하지 않는다. 이 문서의 제품 선택과 목표 시간은 제안이고, 실제 사용자 관찰 후 조정한다.

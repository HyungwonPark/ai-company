## 승인 후 적용 순서

1. Work PM이 [검증 기록](journey-usability-validation-2026-09-25.md)을 대조한 뒤, 실제 웹 1개 교체만 구체적 후보로 승인받는다. 현재 이미지·revision·서비스 정의·소스 차이를 대조한다. 다른 후속 변경이 있으면 덮어쓰지 않는다.
2. 실제 직전 Compose 설정·이미지 ID·자원 해시와 SQLite 온라인 백업을 서버 비공개 경로에 보존한다. 인증 정보·운영 DB·대화·승인 원문은 공개 저장소에 넣지 않는다. DB 백업은 감사·분석용이며 되돌리기용 원장 덮어쓰기 권한이 아니다.
3. 처리 중 요청의 정상 종료를 기다리고, 기존 Compose의 웹 서비스 이미지 ID만 교체해 `docker compose ... up -d --no-deps <웹서비스>`로 재생성한다. 전체 down, worker 재시작, 프록시/타이머 전환은 하지 않는다. 기존 내부 네트워크·상태/카탈로그 mount·읽기전용 root·권한·자원 제한을 유지한다.
4. 60초 안에 healthy·재시작 반복 없음, 실제 HTTPS 루트/로그인·자원 해시·익명 private API 차단을 확인한다. Host·Origin·CSRF·Secure/HttpOnly/SameSite 계약을 유지한다. 검사를 위해 계정 비밀번호를 재설정하거나 사용자 대신 목표·계획 확정·후보 결정을 만들지 않는다.
5. 실제 읽기 화면에서 선택한 프로젝트·실행의 진행→승인 대상/영향→결과/근거와 뒤로가기를 대조한다. 결정할 요청과 조회 기록/범위, 만료 상세/목록, 글자/초점, 갱신 안내를 확인한다. 원장·사용량·큐·PR #10 pending에 이번 교체가 일으킨 예상 밖 변화가 없어야 한다.
6. 기존 탭의 입력과 처리 중 요청을 보존한다. 모듈 갱신 안내는 사용자의 명시적 재로딩 경로를 사용한다. 강제 skipWaiting·앱 데이터 초기화·전체 캐시 삭제·업무 요청 재전송으로 갱신을 통과시키지 않는다.

## 실패와 복구

다음 중 하나면 필수 검사 실패다: 고정 이미지/소스 불일치, 60초 안에 정상 가동 실패, 인증/권한 회귀, 다른 실행 표시, 만료 요청에 결정 가능 안내, 중복 결정/요청, 기존 기록의 예상 밖 변경, 필수 탐색/그래프/근거 접근 불가.

- 추가 적용을 멈추고 실패 로그·버전·현재 DB 기록을 보존한다. 새 웹 입력이 잘못된 요청을 만들 가능성이 있으면 해당 입력을 중단한다.
- 이번 교체만 되돌릴 수 있는지 설정 차이를 확인한 후 웹 컨테이너 1개를 **적용 직전 실제 이미지 ID**로 복구한다. PR #25 준비 이미지를 직전 운영 버전으로 가정하지 않는다.
- DB·WAL·실행·사용량·번역·승인 기록을 과거 백업으로 덮어쓰지 않는다. 새 웹에서 이미 정상 저장된 요청도 보존한다. 예상 밖 API/계약 변경이 확인되면 호환성을 검토하고 구버전을 무조건 재시작하지 않는다.
- 복구 웹의 건강·로그인·읽기·같은 실행 연결을 재검증한다. 실제 도메인/기기의 서비스워커 복구는 격리 Chrome 성공과 구분해 기록한다.

## 적용 이후 사용자 확인

기존 APK 아이콘 → `https://hyungwon.cloud/` → 필요 시 기존 계정 로그인 → 실제 존재하는 프로젝트 → 진행의 대상 선택 → 역할·전달선 → 같은 실행의 승인/결과. 승인에서는 결정 대상·영향·만료를 읽고, 결과에서는 요약과 역할별 내역·시스템 근거를 펼쳐 본다. Android 뒤로가기·Light/Black·앱 완전 종료 후 재실행을 확인한다. 이번에는 새 프로젝트 생성이나 계획 확정·후보 수용을 대신 수행하지 않는다.

실제 APK/운영 도메인 갱신·마스터 직접 조작·서명키 외부 복원은 별도 미확인 항목이다. 개발 검증이 끝났다는 보고와 운영/실기기 완료를 구분한다.

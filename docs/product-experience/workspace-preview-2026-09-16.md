# 작업실 구조 비교 · 2026-09-16

상태: 추천안의 작동 미리보기 제작 중. 사용자 디자인 선택·운영 적용·실기기 검증은 아니다.

PR #14 `7cc52fe`의 `ai-company-frontend` 스킬을 명시적으로 읽고 적용했다. CLI 자동 발견이나 운영 worker 탑재를 검증했다고 보고하지 않는다. 기반은 PR #13 운영 적용 기록 `f933391`; 별도 `feat/frontend-workspace-redesign` 브랜치에서 작업한다.

## 사용자 과제와 설계 판단

같은 이름·목표·현재 PM 질문·두 역할의 진행/대기·전달물·이전 후보 승인 요청을 세 안에 사용한다. 현재 실행과 이전 후보의 실행 ID를 구별한다. 비교 중 데이터는 바뀌지 않으며 조작 결과는 예시 상태로만 남는다.

1. 하던 프로젝트를 찾아 PM 질문에 답한다.
2. 두 역할의 현재 일·대기 이유·전달물을 확인한다.
3. 후보 승인 대상·영향·원문·근거를 읽고 선택할 위치를 찾는다.

기존 모바일 캡처에서는 프로젝트 판단 전 반복 헤더/메타데이터가 약 480px를 사용했다. 이름과 다음 행동 중심의 평면 목록으로 바꾸고 세부 실행 상태는 프로젝트 안으로 옮긴다. PM 대화는 16px 본문, 현재 질문과 입력을 함께 배치한다. 전면 카드 격자 대신 문서·행·목록-본문을 선택한다. 색상은 Light/Black과 절제된 녹색 강조를 공유하지만 첫 화면·정보 순서·조작 위치를 바꾼다.

| 비교안 | 기본 진입과 구조 | 같은 업무를 보는 방식 |
|---|---|---|
| A 작업실 · 추천 | 프로젝트 탐색 + 대화 본문 + 간결한 팀 요약 | PM 질문에 먼저 답하고 실행 범위를 이어 검토 |
| B 작업대 | 병렬 역할 행 + 전달 기록 + 선택 상세 | 역할과 대기를 먼저 파악하고 PM/결정으로 이동 |
| C 결정함 | 요청 목록 + 읽는 문서 | PM 질문·대기·후보 요청을 목록에서 골라 원문·영향을 읽음 |

A를 추천하는 이유는 목표를 PM과 구체화하는 일이 시작점이기 때문이다. B의 병렬 행과 C의 읽기 중심 승인 문서는 각 화면의 표현으로 활용한다. 이는 제작자의 추천이며 사용자가 선택한 디자인으로 기록하지 않는다.

## 핵심 동선과 보존 경계

이름/자연어 목표 → PM 제안 → 명세 저장 → 새 계획 요청 → 직접 계획 검토·확정 → 역할 진행 → 후보 검토를 예시로 조작한다. 명세 저장은 실행을 만들지 않는다. 새 계획은 저장 명세 버전/해시에 묶이며 다른 프로젝트·변경된 명세·잘못된 승인 대상에는 선택을 기록하지 않는다. 요청 모델과 관측 근거, 원문과 읽기용 번역을 구별한다.

미리보기는 별도 `workspace-preview/`의 HTML/CSS/JavaScript이다. 운영 UI·서버 계약·큐·계정·예산은 수정하지 않는다. `/api/` 요청과 모델 호출은 없으며 이 페이지의 예시 영수증은 운영 승인으로 사용할 수 없다. 기존 제품 회귀를 유지하고 실제 운영 작업·APK 직접 확정 검증과 분리한다.

## 검수 계획

Light/Black × 320/390/1440px. 한국어 실제 글리프와 장문 줄바꿈, 주요 44px 터치, 키보드/확대/줄인 동작, 빈 상태·PM 대기·오류·연결 끊김·읽기 권한, 갱신 중 초안/초점, 중복 제출과 응답 유실 후 재시도, 고정 명세·계획·승인 원문을 검수한다. 작성자와 별도 검수자가 캡처와 핵심 조작을 확인하고 지적/수정을 기록한다. 원격 브라우저 검증을 실제 Android 기기 검증으로 표시하지 않는다.

# 작업 특성에 따른 역할 선택과 후속 구현 지침

기준일: 2026-09-28 KST · 사용자 동의 반영 · v1.0

## 결정과 적용 순서

ai-company는 사용자가 정한 목표를 유지하고, 중단 뒤에도 작업·증거를 보존하며 검증된 결과까지 이어가는 실행 시스템을 목표로 한다. 역할을 등록하는 것과 매 작업에 해당 역할을 호출하는 것을 구분한다.

사용자는 글과 관련 프로젝트를 검토한 뒤, 작은 작업의 단일 개발 역할 허용·독립 작업만 병렬화·필수 독립 검수 유지·작업별 효율 측정 방향에 동의했다. 후속 설계와 비운영 구현 범위를 이 문서에 고정한다.

**현재 우선순위는 PR #36의 기존 복구 절차다.** 제품 검수 대상 PR #35 `1d54d3a0ea5a21c7c2dc588f824c6567231829b4`, 복구 후보 PR #36 `7ab76818758ef7cfa4828fd3578217da1d1dc257`와 패키지·검수 기록은 보존한다. [현재 한정 적용·수동 재개 지시](pr36-acceptance-7ab7681-2026-09-28.md)의 조건을 따른다.

이 문서에 대한 동의는 운영 설치·정산·tick·모델 호출·병합·배포의 추가 승인이 아니다. 현재 복구·검수 절차를 마무리한 뒤, 그때의 수용된 제품 기준에서 별도 후속 PR로 아래 구현을 진행한다. 고정 후보에 이번 설계 변경을 섞지 않는다.

## 확인한 현재 제약

PR #35의 고정 후보를 읽어 확인했다. 이는 코드 존재 확인이며 비용 실측 결과는 아니다.

- `src/ai_company/automation_contracts.py`: `PMPlanContent.roles`가 최소 2개이고, 선행 의존성이 없는 역할도 최소 2개 요구한다.
- `src/ai_company/harness/prompts.py`: PM 계획에 독립 역할을 최소 2개 구성하도록 지시한다.
- `src/ai_company/flow_graph.py`와 `shared_calls.py`: 상태 전이와 공용 예약·정산을 코드로 처리하는 기반이 이미 있다. 같은 기능을 다시 만들지 않는다.

## 공통 실행 원칙

| 항목 | 확정한 방향 |
| --- | --- |
| 작은 수정·순차 의존 변경 | 개발 담당자 한 명이 조사·구현·관련 검사·지적 수정·문서화까지 이어간다. 역할 한 개로 계획이 성립해야 한다. |
| 독립 작업 | 입출력·담당 경로·완료 증거·통합 담당을 설명할 수 있을 때만 병렬로 분할한다. 파일 수만으로 역할을 늘리지 않는다. |
| 독립 검수 | 개발 역할 수와 분리한다. 개발자의 자기 완료 선언을 검수 PASS로 취급하지 않으며 기존 PM·계획 검수·최종 검수·사용자 확정 조건을 유지한다. |
| 상태 관리 | 대기 시각·실행 종료·중복·장부·CI 상태처럼 규칙과 증거로 판정할 수 있는 일은 일반 코드가 처리한다. 상태 확인만을 위해 모델 역할이나 정기 호출을 추가하지 않는다. |
| 인수인계 | 목적·완료 조건·기준 커밋·산출물·미해결 항목·증거 위치를 먼저 전달한다. 필요한 원문은 조회하되 검수 대상 패치와 필수 증거를 요약으로 대체하지 않는다. |
| 비용과 용량 | 기존 공용 장부·계정 제한·예산·호스트 실행 수 제한을 유지한다. 역할 목록이 실제 동시 실행 수를 뜻하지 않는다. |

단일 개발 역할은 같은 작업·후보의 변경 책임자 기준이다. 서로 다른 작업이나 프로젝트까지 전역 직렬화하지 않는다. 이관·재시작은 기존 실행 종료·소유권을 확인하고 UNKNOWN에서 중복 실행하지 않는다. 병렬 작업 중 새 의존성이나 공유 경로가 확인되면 후속 배정을 조정하고 기존 실행의 종료·산출물을 확인한 뒤 순서대로 진행한다.

단일 개발 역할을 허용해도 [필수 Claude 독립 검수](pr-completion-review-policy.md)를 생략하지 않는다. 제품 안의 PM·최종 검수 모델 정책도 바꾸지 않는다. 서버 개발 모델 설정은 [개발 효율 지침](server-codex-efficiency-policy.md)을 따른다.

## 후속 구현 묶음

같은 목표의 조사 → 최소 구현 → 관련 통합 검사 → 지적 일괄 보완 → 최종 CI·필수 검수 → 문서·패키징까지 한 번에 처리한다.

1. **계획 계약과 PM 지시 정합성:** 새 계획은 1개 개발 역할로 성립할 수 있게 한다. 현재 최대 역할 수와 순환 의존·중복 키·경로 경계 검증은 보존한다. 여러 역할이라도 순차 의존 때문에 시작 가능한 역할이 하나인 정상 계획은 허용한다. 병렬성은 작업 특성으로 판단하며 가짜 역할을 추가해 개수를 맞추지 않는다.
2. **실행과 화면 연결:** 계획 제안·계획 검수·사용자 확정·배정·개발·검사·통합·독립 검수·보고에서 역할이 한 개여도 이어지는지 확인한다. 불필요한 개발자나 빈 작업을 만들지 않는다. 단일 기여물 처리에서도 후보 커밋 확정·필수 검사·작성자와 검수자 분리는 유지한다.
3. **기존 기록 호환:** 이미 승인된 계획·작업 ID·체크포인트·원본 영수증·해시·승인 범위를 재작성하지 않는다. 과거 실패를 새 규칙으로 소급 PASS 처리하지 않는다. 새 필드나 계약 버전이 필요한 경우에만 명시적으로 구분하고 기존 읽기·재개 경로의 호환성을 검증한다.
4. **좁은 검증과 보고:** 아래 수용 기준을 먼저 확인하고 안정화한 최종 후보에서 저장소의 필수 CI와 독립 검수를 수행한다. 실제 Claude 호출이 기존 조건상 불가능하면 코드·CI 결과와 검수 대기를 구분한다. 기존 성공 검사를 구체적인 이유 없이 반복하지 않는다.

## 수용 기준

- 작은 수정은 개발 역할 한 개로 계획 생성부터 최종 보고까지 모의 통합 흐름이 이어진다. 단계 누락이나 자기 검수로 통과하지 않는다.
- 독립적인 두 작업의 기존 병렬 배정은 유지되며, 순차적인 두 역할 계획도 선행 작업 완료 후 정상 진행한다.
- 빈 역할 목록, 순환 의존, 중복 키, 기존 금지 경로·경로 충돌은 계속 거부한다.
- 동일 공용 계정의 중복 호출과 호스트 용량 초과는 계속 차단한다. 등록 역할 수를 이유로 용량 제한을 완화하지 않는다.
- 개발자 결과·검사 결과·독립 검수 판정·사용자 승인·실행 종료·비용 정산을 구분한다. 검수 미완료·설정 미검증을 PASS로 처리하지 않는다.
- 기존 승인 계획과 체크포인트는 원본·해시·계보를 유지하며, UNKNOWN 및 미정산 사건은 기존 증거 기반 복구 조건을 따른다.
- 단일 역할 때문에 추가된 가짜 작업이나 빈 역할이 없고, 화면·보고의 담당/진행/검수 표시가 실제 실행과 일치한다.

## 실제 효율 확인

현재 복구와 후속 구현 검수를 마친 뒤, 기존 승인·호출 조건을 충족하는 작은 실제 작업부터 평가한다. 정상 업무 실행에서 아래 자료를 함께 수집하고 평가를 위해 같은 모델 호출을 불필요하게 반복하지 않는다.

| 측정 | 기록 기준 |
| --- | --- |
| 결과 | 수용 여부와 산출물·검사·검수 근거 |
| 사용량 | 작업의 계획·개발·검수·수정·재개에 연결된 관측 토큰/비용. 미관측값은 0으로 채우지 않는다. |
| 시간 | 실제 작업 시간과 한도 대기·사용자 승인 대기를 구분한다. |
| 재작업 | 지적 수정·재검수·중단 후 재개 횟수와 사유 |
| 사용자 개입 | 목표 결정·정상 승인과, 전달 누락·상태 오류·복구를 위한 개입을 구분한다. |

수용된 작업 한 건당 비용을 계산할 때 비교 기간의 실패·중단 비용도 보존한다. 구독 계정 전체 한도 감소나 공급자의 표시 비용을 해당 작업의 실제 청구액으로 단정하지 않는다. 비슷한 범위·품질 조건의 기존 작업과 비교하고 표본 수와 차이를 명시한다. 유효한 기준선이 없으면 이번 기록을 기준선으로 삼으며 절약률을 만들어 적지 않는다.

기존 기록으로 측정하고 새 비용 대시보드·과금 체계·자동 모델 라우터를 이번 묶음에 추가하지 않는다. 실제 측정 뒤 병렬 범위 확대나 외부 도구 도입 여부를 판단한다.

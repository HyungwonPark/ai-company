# PR #32 실제 요청 실패 후 스키마·평가 복구 일괄 지시

작성: 2026-09-27 KST · v1.0  
역할: Work PM의 검수와 서버 Codex 실행 명세. 제품 구현은 서버에서 진행한다.

## 현재 판단과 근거 범위

대상은 PR #32 HEAD `2e46e3717832e4a9433bbe240c4d38c7754cc160`, 제품 `0e34d2455c296d7f33977e43f0b1af5039826802`이다. 기존 PR #31 및 PR #32의 앞선 비운영 수용·회귀 해결 기록을 보존한다. 이번 실제 요청 실패는 별도 후속 결함으로 처리하며 실제 PM 판단 품질을 PASS로 보고하지 않는다.

서버 제출 보고상 고정 릴리스 적용 후 E1~E6의 요청 6건이 `invalid_json_schema`로 거부됐다. 모델 응답·계획·마스터 확정·개발 실행은 생성되지 않았고, 호출 종료·정산 기록은 보존됐다. 안전 중지 뒤 두 worker의 부팅 시 자동 시작 설정이 남았으며, 자동 승인 검토가 그 영구 해제를 기존 승인 범위 밖이라고 거부했다. **이 문서는 서버의 비공개 로그·현재 유닛 상태를 Work가 직접 확인한 증거가 아니다.** 자세한 운영 자료·식별자·인증 정보는 비공개 인수인계에 유지한다.

Work는 고정 공개 소스의 실제 스키마 생성 결과를 오프라인에서 검사했다. 핵심 두 파일을 해당 GitHub 커밋 원문과 대조했다. 실제 API·CLI 모델 호출·서버 운영 변경은 하지 않았다. 평가 반복/예산의 보조 진단은 원본 함수/루프를 AST로 추출하고 합성 상태와 실제 임시 장부를 사용했다. 전체 worker나 실제 모델 실행을 대신하지 않는다.

## 확인된 결함과 수정 원칙

### S1. 실제 전송 스키마의 열린 중첩 객체

검사 경로는 `codex_output_schema(PMPlanStageReport.model_json_schema())`이다.

| PM 응답 필드 | 현재 전송 스키마 | 수정 방향 |
| --- | --- | --- |
| `plan.execution_spec_proposal` | 자유 객체 허용 | 기존 ExecutionSpecSelection 의미를 보존하는 명시적 전송 구조. 내부 candidates·role_candidates 사전도 점검 |
| `plan.skill_selection` | 자유 객체 허용 | 서버가 관리하는 선택값임을 유지. 모델의 최초 지정은 막고 수정 시 기존 선택값 보존 |
| `plan.skill_recommendations` | 임의 역할 키→문자열 배열 | 명시적 역할·후보 객체 배열 등으로 전송하고 검증 뒤 기존 내부 사전으로 변환 |
| `requirements_feedback` | 자유 객체 허용 | 기존 PMRequirements의 타입·제약을 전송 스키마에도 반영 |

`session_cli.py`의 변환기는 properties가 있는 객체만 닫는다. `flow_contracts.py`의 PM override는 plan만 구체화하며, 그 내부에도 자유 사전이 남는다. 다른 세 report 유형에서는 같은 열린 객체 조건이 발견되지 않았다. **이 결과는 나머지 공급자 제약까지 모두 통과했다는 뜻이 아니다.**

[OpenAI 공식 Structured Outputs 안내](https://developers.openai.com/api/docs/guides/structured-outputs)는 객체의 추가 속성을 허용하지 않고 선언 필드를 required로 지정하며, anyOf 내부도 지원되는 스키마여야 한다고 설명한다. nullable·기본값·생략 의미는 별도로 보존해야 한다. 실제 서버에서 먼저 거절된 JSON 경로는 비공개 오류 원문과 대조한다.

단순히 모든 사전의 additionalProperties를 false로 바꾸거나 스키마를 제거하지 않는다. 의미 있는 키가 모두 금지되는 빈 객체 계약, 임의 문자열 JSON으로의 회피, 로컬 검증 약화는 수용하지 않는다. 전송 구조와 저장 구조를 분리해 v1 생략 규칙·기존 계획/승인 digest·원문을 보존한다.

### S2. 공통 요청 결함 뒤 사례 연속 호출

`evaluate_pm_behavior.py`는 environment_problem을 다음 사례 진행 상태에 포함한다. `session_cli.py`의 코드 분류에 invalid_json_schema가 없고, 오류 표현에 따라 unknown 또는 code_error로 흡수된다. 원본 사례 루프에 환경 오류를 입력한 오프라인 진단은 6개 사례 모두 진행했다.

공급자가 보낸 오류 envelope의 코드·유형·확인된 구조를 보존하고, 공통 스키마/요청 결함은 첫 발생 후 해당 평가 묶음의 추가 호출을 중단한다. 모델 본문이나 임의 stderr에 같은 문자열이 있다는 이유로 분류하지 않는다. 실제 CLI의 메시지형 오류만 있다면 저장한 원문 형식에 한정된 파싱·회귀 근거를 둔다.

오류 category를 추가한다면 공용 장부의 정산 허용 목록·기존 기록 읽기·UI 상태 전달도 함께 맞춘다.

실패한 PM 응답의 내용 수정, quota 대기, 인증 문제, 공통 요청 스키마 오류를 구분한다. 스키마 오류에 모델의 자동 수정 횟수를 소모시키거나 같은 입력 재호출·다른 에이전트 이관으로 우회하지 않는다. 과도한 공통 중단으로 독립적인 정상 내용 평가까지 막지 않도록 범위와 이유를 기록한다.

### S3. 새 평가 경로에 따른 누적 예산 초기화 방지

현재 평가 사용량은 trial-root에 속한 장부 owner 경로로 집계한다. 반면 고정 manifest는 제품·입력 변경을 거부한다. 수정 코드를 평가하려고 새 root만 만들면 기존 6건이 집계에서 빠질 수 있다. 임시 장부의 6건 정산 예시에서 원래 root는 6건·6초, 새 root는 0건·0초로 집계되는 것을 확인했다. **6초는 합성 검사값이며 실제 소요 시간이 아니다.**

새 후보 평가는 이전 평가를 가리키는 명시적 후속 revision/계보와 누적 사용량을 갖춰야 한다. 기존 manifest·실패 결과·종료·정산을 덮지 않는다. 승인된 평가의 기존 24호출·실제 실행 1800초·자동 수정 2회·호스트 병렬 제한을 유지하고, 이전 6건 및 다른 선행 예약/실행을 정확히 포함한다. 잔여 수치는 실제 장부 대조 후 산출한다. 별도 경로를 만들었다는 이유로 새 예산을 부여하지 않는다.

## 실행 묶음 A~F

### A. 재시작 위험 정리 — 필요한 승인만 분리

권고는 **이미 고정된 PM·번역 worker 두 유닛의 부팅 시 자동 시작을 해제하고 현재 중지를 유지하는 것**이다. 이는 일시 중지와 달리 재부팅 후 가용성을 바꾸므로 명시적 마스터 답변이 필요하다. 기존 자동 승인 거부를 우회하지 않는다.

마스터가 이 범위를 승인하면 실제 대상 두 유닛과 상태를 대조해 disable하고 inactive/disabled 및 알려진 다른 활성화 경로를 읽기 전용으로 확인한다. 타이머를 기다려 동작을 확인하더라도 모델 호출을 유도하지 않는다. mask·새 가드·다른 유닛 변경이 필요하면 승인된 disable과 동일하다고 확대하지 않는다. quota 가드 타이머·일정·웹·커플 서비스·전역 CLI·데이터는 유지한다. 테스트를 위한 실제 재부팅은 포함하지 않는다.

해제 전 상태와 재활성화 절차는 기록하되 지금 enable/start하지 않는다. A 답변을 기다리는 동안 아래 비운영 작업은 계속한다.

### B. 재현과 응답 계약 일괄 수정

1. 비공개 기록에서 첫 거절 및 나머지 요청의 구조화 오류·스키마 경로·실행 인자·스키마 바이트/해시·제품/설정/CLI 버전을 대조한다. 원문 보존 후 비밀정보를 뺀 최소 재현을 만든다.
2. PM 최초 제안·질문 피드백·계획 수정·계획 검수·개발·독립/최종 검수 등 실제 dispatcher가 내보내는 모든 report 유형을 열거한다. PM의 네 지점과 내부 사전까지 한 번에 수정한다.
3. 스킬 추천의 역할 존재, 중복 역할/후보 거부, 역할당 3개 상한, 순서 보존을 유지한다. 서버 소유 skill_selection을 모델이 변경하지 못하게 하고 계획 수정 시 기존 승인 선택을 보존한다.
4. v1 저장/생략/digest, 기존 확정 실행, 필수 질문·근거·별도 검수·마스터 확정 경계를 그대로 검사한다. 공급자 전송 DTO를 쓴다면 명시적 변환과 역검증을 둔다.

### C. 호출 전 검사와 첫 실패 중단

1. 실제 릴리스에서 CLI에 전달하는 **최종 스키마 파일**을 검사한다. Pydantic 원본만 검사하고 끝내지 않는다. 중첩 objects·arrays·anyOf·$defs/$ref·nullable·required·지원하지 않는 구조를 검사하고 스키마 해시를 기록한다.
2. 로컬에서 판단 가능한 스키마 결함은 프로세스를 시작하기 전에 차단한다. 가능한 한 예약 전 차단하며 예약 후 발견되면 미시작 취소를 정확히 정산한다. 호출 0인데 모델 사용량을 지어내지 않는다.
3. 공급자에서만 확인되는 공통 요청 거절은 첫 실제 호출 종료·정산 후 묶음을 차단한다. 남은 사례는 미실행/공통 오류 대기로 표시한다.
4. 중단 상태는 재실행·재부팅에도 보존한다. 모델/스키마/설정 해시와 오류 근거에 묶고, 무관한 정상 작업의 전역 계정 한도를 임의 차단하지 않는다. schema 수정과 검증 근거 없이 차단을 해제하지 않는다.
5. 다음 호출 직전 설치본·스키마 해시가 고정된 후보와 다른 경우에도 차단한다.

### D. 중복·재개·예산과 기록 보존

1. 기존 6건은 응답 없음/요청 거절로 보존한다. 공급자 실제 청구·토큰이 확인되지 않았다면 사용량 0이라고 단정하지 않는다.
2. 수정 후보의 후속 평가를 이전 계보와 연결한다. 실패 사례를 덮어쓰기, settled 삭제, 새 root로 예산 초기화, 같은 요청의 동시 재시도는 막는다.
3. invalid_json_schema 후속 시도는 quota의 동일 job/session 재개와 구분한다. 이전 시도 종료·정산을 확인하고 변경된 계약을 사용하는 후속 시도로 기록한다.
4. 기존 R31-1~4·R31-4b의 같은 사례/사례 간 두 번째 수정 재개, 새 세 번째 수정 차단, 미정산 대기, 중복 정산 방지를 유지한다.
5. UNKNOWN Claude 계정의 귀속 근거 확인은 읽기 전용으로 계속할 수 있다. 현재 로그인만 보고 과거 호출의 계정을 추정하거나 UNKNOWN을 AVAILABLE로 바꾸지 않는다.

### E. 통합 검수·릴리스·복구 준비

B~D를 후속 초안 PR 하나로 묶는다. 파일 소유권을 나눠 스키마 담당과 평가/장부 담당을 병렬 진행하고, 한 명이 통합하며 독립 검수자는 구현자와 분리한다.

다음 검증을 제출한다.

| 검증 | 수용 기준 |
| --- | --- |
| 기존 PM 스키마 결함 | 수정 전 네 지점 재현, 수정 후 최종 전송 파일에서 해결 |
| 실제 중첩 데이터 | 실행 명세·역할 추천·질문 피드백을 잃지 않고 내부 계약으로 검증·저장 |
| 서버 소유 필드·기존 계약 | 선택값 변조 차단, 기존 v1 digest/확정 기록·질문/승인 경계 보존 |
| 오프라인 사전 검사 | 잘못된 스키마에서 실제 프로세스 0, 예약/정산 일관성 |
| 공급자 요청 거절 | 모의 6사례 중 첫 호출 1회만 시작, 나머지 0, 재실행도 반복 없음 |
| 정상/내용 실패/한도 | 각 상태를 구분하고 정상 평가·기존 quota 재개 보존 |
| 수정 후보의 평가 계보 | 이전 6건 포함, 중복·동시 실행 및 경로 변경 예산 초기화 차단 |
| 실제 릴리스 | 서비스 권한·실제 로딩 경로·전용 CLI·가드의 무호출 사전 검사와 기존 회귀 통과 |

필요한 경계에는 property-based-testing·variant-analysis를 적용하되 관련 없는 전면 재작성이나 테스트 수 늘리기를 목표로 삼지 않는다. 최종 HEAD의 필요한 CI·독립 정적 검수·릴리스 해시·사전 점검·복구안을 고정한다. 계정 조건으로 실제 Claude 검수가 막히면 그 사실을 표시하고 나머지 비운영 작업을 마친다.

복구 기본은 검증되지 않은 worker의 중지 유지와 현 DB/장부/체크포인트 보존이다. 새 정산이 생긴 뒤 과거 DB를 복원하거나 결함 있는 릴리스를 정상 운영 후보처럼 자동 시작하지 않는다.

### F. 실제 재평가 준비 — 수정 후보 승인 후 실행

지금은 준비 범위다. 수정 릴리스의 정확한 파일/유닛/설정 변경과 재활성화, 아래 단계적 실제 평가를 **한 통합 적용안**으로 제출한다. 기존 고정 후보 승인을 새 코드 배포나 자동 시작 복원의 승인으로 해석하지 않는다. 같은 통합안이 명시 승인되면 범위 안의 단계별 승인을 다시 묻지 않는다.

1. 공용 장부·호출 경로·계정·누적 예산·설치 해시·독점 평가 소유권이 맞는지 확인한다.
2. E1의 PM 제안 **실제 모델 호출 1회**만 우선 실행한다. 현재 run_case는 검수/수정 호출까지 이어질 수 있으므로 'E1 한 사례'를 '한 호출'로 보고하지 않는다. 자동 검수·수정이 시작되기 전에 멈추는 검증 단계를 둔다.
3. 스키마 수용·응답 파싱·내부 계약 검증·종료/정산이 확인되면 같은 승인과 남은 누적 예산 안에서 E1의 후속 검수와 E2~E6을 이어간다. 첫 PM 호출 성공은 전체 E1 또는 PM 품질 PASS가 아니다.
4. 공통 요청 오류가 다시 발생하면 즉시 중단한다. 한도는 기존 영속 대기, 인증/권한/미정산은 해당 차단을 따른다. 임의 반복·계정 이관으로 요청 결함을 숨기지 않는다.
5. 실제 Astra 내용 평가는 구조 검사와 분리하여 E1~E6 기준으로 독립 검수한다. 마스터 직접 확정·실제 개발 실행은 대신하지 않는다. 현재 단계에서 APK 조작을 요청하지 않는다.

## 완료 보고와 승인 경계

A의 현재 상태, B~E의 코드/회귀/독립 검수/CI/고정 패키지, F의 준비·실제 실행 여부를 한 보고서에 구분한다. 각 항목은 완료·차단·다음 행동과 근거를 표시한다. 같은 승인 질문을 반복하며 독립 작업을 멈추지 않는다.

이번 Work 지시는 비운영 구현·검수·패키징을 구체화한다. A의 자동 시작 해제와 F의 새 릴리스 적용/호출은 별도 명시 범위를 따른다. 웹·커플 서비스·기존 운영 기록·PR #10 pending·서명키·병합 상태를 유지한다. 공개 문서에는 비공개 운영 원문·경로·계정 정보·환경변수·토큰을 올리지 않는다.

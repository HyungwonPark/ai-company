## 목표와 역할

마스터는 Work에게 의견 집계·판단·실행 지시를 맡겼다. Work PM은 요구 사항의 우선순위·작업 범위·수용 기준을 확정하고 결과를 검수한다. 서버 Codex는 구현·통합·검사·패키징을 맡는다.

이번 목표는 순서형 작업실에서 사용자가 **현재 상황, 기다리는 이유, 자신이 할 다음 행동**을 바로 알 수 있게 만드는 것이다. 아래 지시를 받은 서버 Codex는 추가 디자인 선택이나 단계별 착수 확인을 기다리지 않고 비운영 구현부터 최종 제출까지 진행한다.

상세 판단 근거는 [dec455e 재검수](ai-company-pr25-review-dec455e-2026-09-25.md)의 U1~U3과 수용 기준이다. 그 문서의 “후속 제안”은 본 지시로 이번 개발 작업의 확정 범위가 된다. 과거 검수 원문은 수정하지 않는다.

## 작업 배정과 순서

동시 작업 수와 자원은 기존 서버 정책 안에서 유지한다. 같은 파일을 여러 작업자가 동시에 수정하지 않는다.

| 담당 | 소유 범위 | 실행 지시 |
| --- | --- | --- |
| 서버 Codex 통합 담당 | `app.js`, `report-ui.js`, `workspace-graph-ui.js` 등 화면 동작과 연결 | U1을 먼저 고정한 뒤 U3을 구현한다. 공통 상태/범위 규칙을 만들고 U2에 필요한 DOM·초점 변경도 여기서 반영한다. |
| 화면 담당 | 기존 CSS·표시 규칙과 전후 캡처 | U2를 병행한다. 공통 DOM 변경은 통합 담당에게 요청하고 같은 JS 파일을 병렬 수정하지 않는다. |
| 독립 검수 담당 | 검사 시나리오·원본 대조·최종 화면 조작 | 구현 담당과 분리해 상태 경계와 같은 실행 연결, 키보드·모바일 조작을 검수한다. 새로 발견한 결함은 근거와 함께 통합 담당에게 반환한다. |

보조 에이전트를 사용할 수 없으면 동일 순서로 직접 진행한다. 추가 에이전트나 모델 연결을 기다리며 멈추지 않는다. 독립 검수는 실제 수행자와 방법을 기록하고 작성자의 자체 검사를 독립 검수라고 부르지 않는다.

### U1 — 승인과 상태 표시

- “결정할 요청 N건”과 “전체 요청/조회된 기록 M건”, “프로젝트 전체”와 “선택한 실행”을 구별한다. 모든 화면의 숫자를 억지로 같게 만들지 않는다.
- 목록·상세·배지가 같은 관측 시각과 범위의 표시 상태를 사용하게 한다. 만료 pending을 상세만 만료로 표시하는 불일치를 없앤다.
- 기한이 지난 요청의 승인·반려·수정 요청 버튼을 실제 서버 정책에 맞게 처리하고 다음 행동을 안내한다. 서버 검증과 원문 pending·기한·digest·승인 기록은 바꾸지 않는다.
- 알려진 상태는 한국어 설명을 먼저, 원문 코드는 상세에 표시한다. 알 수 없는 상태를 임의로 진행·완료로 분류하지 않는다.
- 갱신 패널은 분명한 복구 버튼을 유지하며 문구를 축약한다. 복구 성공이나 모든 임시 입력의 보존을 약속하지 않는다. R25-1b의 쓰기 차단·명시적 갱신·처리 중 요청 방어를 유지한다.
- 고정 미리보기의 만료 예시는 표시 문제를 재현하는 자료로 사용한다. fixture 기한 연장이나 원문 수정으로 실패를 숨기지 않는다.

### U2 — 가독성과 조작

- 중요 상태·행동 14px 이상, 핵심 본문 16px을 프로젝트 스킬 기준으로 적용하고 실제 줄바꿈·대비를 확인한다.
- 진행·완료·대기·확인 필요를 글자·형태로도 구분한다. 색만 바꿔 의미를 전달하지 않는다.
- 단계 이동 시 본문 전체에 생기는 불필요한 외곽선을 정리하되, 키보드 초점·본문 건너뛰기·이동 후 읽기 시작점을 보존한다. 전역 outline 제거는 하지 않는다.
- 빈 화면의 의미 없는 점 장식과 장황한 설명을 줄인다. 보고 없음이 완료나 실패를 뜻하지 않도록 한다.
- 머리글은 프로젝트 전환과 주요 탐색을 보존하면서 반복 행을 줄인다. 미리보기 안내 띠의 높이는 실제 제품 머리글과 별도로 평가한다.

### U3 — 진행과 결과 구조

- 통합 화면의 진행 제목과 실행 선택기를 각각 한 번만 표시한다. 독립 그래프 화면의 자체 선택 기능은 유지한다.
- 선택 실행·snapshot·계획 해시·깊은 링크·뒤로가기, 그래프 카메라·선택·도움말 상태를 보존한다.
- 결과 첫 부분에 현재 결론, 남은 일/차단, 다음 행동을 한 번씩 보여 준다.
- 0건 그룹은 한 줄 집계로 남기고 큰 빈 섹션을 반복하지 않는다. 역할별 내역·원문·검수 근거는 펼쳐 볼 수 있게 한다.
- 시스템 집계와 PM 작성 보고를 구별한다. 없는 PM 보고를 생성된 보고처럼 표시하지 않는다.
- 그래프의 “조회 순서” 같은 내부 정보는 상세로 옮긴다. 새로 보이는 요약은 실제 데이터가 보장하는 사실만 사용한다.

## 검수 기준

1. 만료 전·정확 경계·만료 후, 갱신 전후, 다른 실행/요청 없음/완료·반려 요청을 임시 API 또는 정확한 제품 함수로 검증한다. UI 표시는 원문·서버 권한을 변경하지 않아야 한다.
2. 같은 프로젝트·실행에서 **진행 이해 → 필요한 승인 발견 → 대상·영향 확인 → 결과·근거 열람**을 독립 검수자가 실제 조작한다.
3. 변경한 화면을 Light/Black × 320/390/1440px, 키보드·확대, 긴 이름·빈 상태·대기·오류·만료에서 검수한다. 기존 영향을 받지 않은 검사를 무의미하게 반복하지 않는다.
4. R25 혼합 모듈 4조합·업무 쓰기 차단·초안/주소/멱등 키, 상태 분류·정확한 실행 연결·응답 경합·G1~G3의 관련 회귀를 유지한다.
5. 같은 데이터·화면 폭·테마·펼침 상태의 전후 캡처를 제출한다. 페이지 높이는 보조 지표이며 내용을 삭제해서 목표 수치를 맞추지 않는다.
6. 최종 통합 코드에서 필요한 로컬 검사·원격 CI·독립 검수를 완료한다. 실패하면 원인을 수정한 뒤 영향 검사와 필수 CI를 다시 통과시키고 제출한다.
7. `ai-company-frontend`와 서버에 설치된 관련 스킬을 실제 영향 범위에 적용한다. 스킬 호출·CI 성공만으로 사람의 사용성 검수를 대신하지 않는다.

## 진행 원칙

범위 안의 수정·검사 실패·충돌·문구·배치 세부 결정은 서버에서 해결한다. 파일별 수정 완료마다 마스터의 허가를 다시 묻지 않는다. 이번 지시로 사용자 대신 실제 목표 입력·계획 확정·승인 결정을 생성하지 않는다.

부분 문제가 생기면 영향받는 작업만 차단으로 기록하고 독립적으로 진행할 수 있는 작업을 계속한다. 권한 밖 운영 변경, 자격 증명 접근, 승인 의미 변경, 되돌리기 어려운 원문 손상이 꼭 필요하다는 근거가 있을 때만 필요한 결정과 대안을 구체화해 보고한다. 이를 이유로 관련 없는 구현까지 모두 대기시키지 않는다.

PM 검수 요청 시 “전체 완료” 한 줄 대신 위 증거를 제출한다. Work PM이 수용 기준과 대조해 통과·수정 요청을 판정한다. 마스터에게는 취향 선택을 반복 요청하지 않고 실제 마스터 조작이나 운영 승인처럼 필요한 항목만 구체적으로 전달한다.

## 후속 적용·실패 복구 — 별도 운영 승인 필요

1. 고정 제품·archive SHA·설치 소스·Python·native CLI 버전/해시, 현재 릴리스 포인터, 두 worker `inactive/disabled`, quota 가드 일정, 기존 대기 목록·UNKNOWN 계정, 원본 E1 7건·체크포인트·현재 공용 사용량을 적용 직전 다시 대조한다. 평가 실행기는 archive marker만으로 승인하지 않고 **깨끗한 Git checkout의 정확한 HEAD와 채택 증빙**을 요구하므로 실행 경로를 별도로 고정한다. 격리 사본 검증은 같은 파일시스템의 스테이징 공간, 비활성 사본 연결, 내용 있는 WAL 부재를 확인한다.
2. DB·공용 장부·체크포인트의 일관 사본과 현 릴리스 포인터를 보존한다. 새 승인을 받으면 **PM·조정기 및 번역 worker가 쓰는 릴리스 포인터만** 새 archive로 바꾸고 단일 실행·로딩·계정/장부 채택을 확인한다. 웹·커플 서비스, 전역 CLI와 타이머 일정은 변경하지 않는다.
3. worker가 중지된 채 `apply-operating-and-canary`로 저장 원문을 재검증해 파생 계획 1건·revision·canary를 멱등 저장한다. 원래 PM을 다시 호출하지 않는다. 추가 예약이 이미 있다면 무조건 거부하거나 허용하지 않고 같은 job·계획·정산·예산 결속을 검증한다. 원본 7건·원래 실패·기존 예산을 대조한 뒤 승인 범위의 대기 작업만 단일 worker로 이어간다. 같은 계보와 남은 예산에서 E1 **별도 내용 검수**, 이어서 E2~E6을 진행한다. 계획 확정과 개발 배정은 이 명령이 수행하지 않는다.
4. 해시·기록·인증·예산 검사 실패, E1 저장/검수 실패, 공통 요청 오류나 예상 밖 호출이 있으면 두 worker를 중지하고 자동 시작을 해제해 `inactive/disabled`를 확인한다. 새 예약 전 단순 포인터 변경만 이전 릴리스로 되돌릴 수 있다. 파생 계획이나 새 예약이 생긴 뒤에는 DB·장부·체크포인트를 과거 백업으로 덮거나 구형 worker를 재가동하지 않는다. 현 상태를 보존해 진단하고 quota 가드·기록을 유지한다.

현재는 **운영 적용·worker 재활성화·실제 E1 내용 평가·E2~E6 호출·병합을 수행하지 않았다.** PR #10의 후보 승인은 `pending`으로 유지한다. 실제 운영 연결 범위는 Work PM의 이 후보 재검수 후 한 번에 판단한다.

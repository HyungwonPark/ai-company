## R25-1b 해결 근거

- `workspaceCompatible()`가 graph의 `getScope/selectScope`와 report의 `execution`을 확인한다. 미지원 조합에서는 scope 선택·그래프 조작·본문 렌더 대신 갱신 안내를 표시한다. 현재 계획이나 다른 실행으로 대신 표시하지 않는다.
- 버튼·submit·공통 API 경계에서 새로운 업무 쓰기를 막는다. 로그인·조회·로그아웃의 기존 경계는 유지한다.
- 갱신은 사용자 클릭으로만 진행하고, 처리 중 폼이나 열린 대화상자가 있으면 보류한다. 주소·저장된 초안·불확실 요청의 멱등 키를 지우거나 자동 재전송하지 않는다.
- Work의 독립 Node 검증은 정확한 Git blob의 실제 app 함수와 구/신 graph/report factory를 사용했다. 정상 1조합과 혼합 3조합을 확인했고, 혼합 조합별 24개 업무 쓰기 호출이 fetch 전에 차단됐다. URL·초안·저장소 모델 불변과 수동 갱신 조건도 확인했다. DOM/브라우저 전체 검증으로 확대하지 않는다.
- 서버의 [수정 전 실제 Chrome 실패](https://github.com/HyungwonPark/ai-company/actions/runs/36080550179) 로그에서 정상 인증 뒤 `selectScope is not a function`을 확인했다. 수정 후 검사·증적은 실제 임시 ManagementHTTPServer·인증·SQLite를 사용하며, 정적 파일 수신 SHA·v8 제어 탭 2개·v10 waiting·업무 쓰기 0·명시적 갱신 후 같은 실행과 초안 복구를 확인한다.
- Work에서는 저장된 Light 320 / Black 390 갱신 패널과 결과 화면 PNG를 직접 열어 대조했다. 이번 Work가 새 Chrome 세션을 실행하거나 APK를 조작했다는 뜻은 아니다.

### 승인 표시가 엇갈린 이유

고정 예시는 프로젝트 `pending_approval_count=1`과 요청 `status=pending`을 저장해 둔다. 이후 기한이 지나도 원문 fixture는 변하지 않는다. 반면 화면은 현재 `Date.now()`로 처리 가능 여부와 상세의 만료를 계산한다. 목록은 원문 상태를 표시하므로 한 파일 안에서 서로 다른 표현이 나온다.

실제 관리 API는 프로젝트 목록에서 미만료 pending만 세고, overview에서 만료를 expired로 투영하며, 결정 요청에서도 만료를 거부한다. 따라서 이 예시만 보고 “운영에서 만료 승인이 통과한다”거나 “서버 건수가 틀렸다”고 판단하면 안 된다. 서버 정상 응답 이후 시간이 지나는 경계도 후속 UI 검사에서 다뤄야 한다.

또한 현재 `전체 요청 N`의 N은 모든 기록이 아니라 `isActionableApproval`을 통과한 개수다. 이는 실제 데이터에서도 오해를 만드는 이름이다. 다음을 구별한다.

- **결정할 요청 N건:** 아직 유효하며 처리 가능한 요청.
- **전체 요청 M건:** 현재 조회 범위에 있는 과거·만료·처리 완료 기록까지 포함. 전체 목록이 아닌 제한된 응답이면 “조회된 요청”으로 범위를 드러낸다.
- **프로젝트 전체 / 선택한 실행:** 범위가 다르면 숫자가 다른 것이 정상이다. 같은 이름과 범위일 때에만 일치를 검사한다.

표시를 맞추려고 pending 원문·기한·기존 승인 기록을 수정하거나, 미리보기 날짜를 미래로 미뤄 실패를 숨기지 않는다. 읽기 전용 미리보기의 모든 업무 쓰기 차단도 유지한다.

### 갱신 패널

문구를 짧게 하자는 의견에는 동의한다. 다만 `h1`이라는 이유로 작은 경고 띠로 바꿀 필요는 없다. 실제 저장 캡처에서는 업무가 막힌 이유와 단일 복구 버튼이 잘 보인다. 차단 상태에는 명확한 주 콘텐츠가 적절하다.

“새 버전이 준비됐습니다. 다시 불러오면 이어서 볼 수 있습니다”는 통신 문제가 남아 있는 상태에서 성공을 약속하므로 피한다. 문구 후보는 다음과 같다.

> **화면을 다시 불러와 주세요**  
> 일부 화면 파일의 버전이 다릅니다. 다시 불러온 뒤 확인해 주세요.  
> 선택한 주소와 저장된 초안은 유지합니다. 이전 요청은 자동으로 다시 보내지 않습니다.  
> **[화면 다시 불러오기]**

“저장된 초안”을 모든 임시 입력의 영속 보존으로 확대하지 않는다. 토스트는 선택 사항이다. 동작을 붙인다면 “갱신 안내 보기”로 안내에 초점을 옮기거나 기존 `reloadWorkspace()`를 공유한다. 처리 중 요청·열린 대화상자를 무시하는 별도 reload는 만들지 않는다.

## 서버 구현용 후속 범위 제안

**PR #25 후보를 보존한 별도 후속 PR에서 U1~U3을 하나의 사용성 개선 구간으로 진행**하는 것을 권한다. 먼저 병합해야 시작할 수 있는 작업은 아니다. 원본 후보와 파생 브랜치·PR base를 명시하고, 이후 기준이 바뀌면 차이를 대조한다. 이 문서 게시만으로 서버 작업이나 운영 교체가 실행되지는 않는다.

### U1 — 상태와 승인 건수를 이해할 수 있게

1. 승인 목록·상세·배지의 표시용 상태와 만료 판단을 공유한다. 서버 원문과 승인 권한은 그대로 둔다.
2. 위의 처리 가능한 요청/전체 기록/조회 범위를 문구와 숫자에 함께 반영한다. 유효한 pending, 만료 pending, API expired, approved/rejected, 다른 실행, 오래된 응답, 기한 경과를 구분한다.
3. 이미 기한이 지난 요청에 불가능한 결정 버튼을 활성 상태로 보여 주지 않는다. 표시 개선이 서버 승인 검사를 대체하지 않는다.
4. 알려진 원문 상태는 한국어 요약을 먼저 제공하고, 알 수 없는 상태는 추측 없이 “상태 확인 필요”와 원문 상세를 제공한다. 원문 보고와 번역 출처는 유지한다.
5. 갱신 안내 문구를 줄이되 R25-1b의 쓰기 차단·주소/초안/멱등 키·명시적 복구 조건을 유지한다.

### U2 — 읽기와 조작을 편하게

1. 중요한 배지·행동은 14px 이상, 핵심 본문은 16px을 기준으로 영향 화면을 조정한다. 이 수치만으로 접근성 검수 완료를 주장하지 않는다.
2. 진행/완료/대기/확인 필요를 구분하되 문구·아이콘 또는 형태를 함께 사용한다. Light/Black 모두 대비를 확인한다.
3. 클릭 탐색과 키보드 탐색을 구별해 본문 초점 표현을 조정한다. Tab, Shift+Tab, 본문 건너뛰기, 이동 후 다음 Tab의 시작 위치, 화면 읽는 순서를 검수한다.
4. 빈 상태는 의미 없는 장식을 줄이고 “왜 비어 있는지 / 기다리면 되는지 / 할 일이 있는지”를 짧게 알린다. 보고 없음이 검수 통과나 실패를 뜻하는 것으로 바뀌지 않게 한다.
5. 머리글의 의미와 조작을 유지하며 반복 행을 줄인다. 미리보기 안내 띠를 제품 머리글의 문제로 혼합하지 않는다.

### U3 — 진행·결과의 중복을 줄이기

1. 통합 화면의 프로젝트/실행 선택을 공통 영역 한 곳으로 통일한다. 선택 실행 ID·snapshot·계획 해시·브라우저 뒤로가기·깊은 링크와 G1~G3 카메라/선택/도움말 상태를 유지한다.
2. 결과 맨 위에서 **현재 결론, 남은 일 또는 차단 이유, 내가 할 다음 행동**을 알 수 있게 한다. 이미 완료된 일과 확인되지 않은 일은 섞지 않는다.
3. 0건 역할 그룹을 큰 빈 섹션으로 반복하지 않는다. 한 줄 집계에 0을 보존하고 상세는 접거나 실제 항목이 있을 때 연다.
4. 역할별 상세·원문 코드·검수 근거·전체 문서는 펼쳐 볼 수 있게 한다. 실패·만료·사용자 결정에 필요한 영향을 단순히 접어서 숨기지 않는다.
5. 시스템 집계와 PM 작성 보고를 구분한다. PM 종합 보고가 없으면 시스템 요약만 제공하고, 생성되지 않은 PM 보고를 만든 것처럼 표시하지 않는다.

### 검수와 제출

- U1은 같은 프로젝트/실행/조회 시점/범위를 고정한 기능 검수, U2~U3은 같은 데이터와 상태의 전후 렌더 및 실제 조작으로 판단한다.
- Light/Black × 320/390/1440px, 키보드·확대, 긴 이름·빈 상태·대기·차단·만료·갱신 필요를 변경 영향에 맞게 검수한다. 반복 대형 검사보다 구체적인 위험에 맞춘 회귀를 유지한다.
- 특히 **현재 실행의 상태 파악 → 필요한 승인 발견 → 요청의 실행/영향 확인 → 결과와 근거 열람**을 별도 검수자가 조작한다. 기능 CI만으로 사용성 개선 완료를 선언하지 않는다.
- 결과 높이와 머리글은 같은 입력·뷰포트·테마·펼침 상태에서 비교한다. 높이를 일정 비율 줄이는 것을 목표로 삼아 내용을 삭제하지 않는다.
- 실제 승인 데이터 경계는 임시 API/SQLite를 사용한다. 미리보기 시각 검사와 운영/실기기 검증을 구분한다.
- 기존 혼합 모듈 4조합, 업무 쓰기 차단, R25-2 상태 분류, 같은 실행 연결, 응답 경합, G1~G3를 보존한다. 새 버전 모듈 경계를 도입하면 기존 혼합 조건에서 다시 확인한다.
- 최종 제품/검사/게시 커밋, CI, 전후 캡처, 실제로 개선한 사용자 과제, 미리보기 ZIP/해시와 새 후보의 적용·복구안을 함께 제출한다. 수정 후 기존 `ffb62c3` 이미지와 검수 결과를 새 제품의 증거로 재사용하지 않는다.
- 스킬은 저장소 `ai-company-frontend`를 적용하고, 서버에 설치된 `web-design-guidelines`로 영향 화면을 검토한다. `ponytail`은 불필요한 복잡성을 줄이는 데, `variant-analysis`는 같은 표시 결함의 다른 위치 확인에 사용한다. `property-based-testing`은 상태·범위·시각 경계 조합에 필요할 때, `gh-fix-ci`는 실제 CI 실패가 있을 때 사용한다. 스킬 호출 자체를 완료 증거로 삼지 않는다.

토큰 전체 개편은 후순위로 둔다. U1~U3에서 사용하는 글자·상태색·간격부터 공통 규칙으로 정리하고, 사용하지 않는 영역까지 전면 변경하지 않는다. “색을 몇 종으로 줄였는가”보다 같은 의미가 같은 표현을 쓰는지 검수한다.

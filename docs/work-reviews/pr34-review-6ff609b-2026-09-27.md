## R34-1 · 후속 검수 예약이 생기면 재시작 불가 · P1

### 코드 근거

- `pm_evidence_recovery.py:82~87,247~250`은 원래 E1 소유자의 **모든** 예약·정산과 선행 6건을 동결 장부 전체와 비교한다.
- 같은 파일 `301~302`는 E1 소유자의 예약이 정확히 1건이어야 한다는 독립 조건도 적용한다.
- `evaluate_pm_behavior.py:374~378`의 파생 canary 검증은 매번 위 diagnose를 다시 수행한다. `allow_review_progress=True`는 계획 상태 범위만 넓힌다.
- `tests/test_pm_evaluation_runner.py:977~989`의 추가 검수 후 재개 사례는 diagnose와 verify_saved_recovery를 모두 모의 대체한다. 실제 위 두 조건을 통과했음을 입증하지 못한다.

### 재현과 영향

실제 SharedCallLedger로 선행 6건과 E1 1건을 정산하고 동결 사본을 만들었다. 제품 canary 함수와 장부 조회 함수, diagnose의 두 조건을 AST 그대로 사용했다. 다른 원문 진단 조건은 유효하다고 가정한 좁은 경계 검사다.

```text
후속 검수 전: canary = true
E1 검수 예약 1건 추가·정산 후: canary = false
동결 예약 = 7, 현재 예약 = 8
E1 or predecessor settlement differs from original shared ledger
```

동결 비교만 제외해도 `E1 has additional shared reservations`가 별도로 발생한다. 새 예약은 합성 검수 기록이며 실제 모델 호출은 0건이다.

따라서 정상 검수 호출 후 중단·한도 대기 등으로 평가 실행기를 재시작하면, 원래 E1 성공 근거가 훼손되지 않았어도 진행할 수 없다. 제출 문서의 “검수 호출이 추가된 뒤에도 이어갈 수 있다”는 범위는 현재 수용할 수 없다. 처음 계획 한 건을 복구했다는 기존 결과는 보존한다.

### 수정 기준

1. **최초 복구 검증과 이후 진행 검증을 구분한다.** 최초 복구에는 고정 E1 PM 1건과 선행 6건을 요구한다. 이후에는 이 원본 집합의 예약 ID·소유자·event/result 해시·내용을 계속 재검증한다.
2. 동결한 원본 7건의 불변성을 확인하면서, 이후 승인된 검수·수정 작업의 예약은 별도 실행 계보로 확인한다. 현재 장부 전체가 영원히 7건이어야 한다는 조건으로 묶지 않는다.
3. 추가 예약을 무시하거나 모두 허용하는 수정도 금지한다. 요구사항/계획·실행·역할·세대·정산에 연결되는지 확인하고 호출/실행시간/수정 예산에 계속 합산한다. 미정산·불확실 종료는 기존 대기/조정 규칙을 따른다.
4. 최초 E1 PM 호출 1회 상한을 유지한다. 후속 내용 검수·정상 수정의 예약 증가를 최초 PM 중복 호출로 오인하지 않는다. 새 평가 디렉터리로 예산을 초기화하지 않는다.
5. canary와 파생 검증 revision의 재검증·중복/중단 복구를 함께 수정한다. 원본 실패나 당시 정책을 덮어써 통과시키지 않는다.

### 반드시 추가할 통합 검사

실제 diagnose·verify_saved_recovery·canary 경로를 사용하고 모델 응답만 모의 대체한다. 다음은 최초 실패→수정 성공을 남긴다.

- 파생 E1 저장 → 독립 내용 검수 성공 → 실행기 종료·재시작 → 후속 진행.
- 내용 검수 중 사용량 제한 → 영속 대기 → 재시작 → 기존 job/session 재개.
- REVISE → 허용된 수정/재검수 → 종료·재시작, 기존 전역 수정 상한 유지.
- 원본 7건 중 하나 변조/삭제, 잘못된 추가 예약, 오래된 요청/세대, 예산 초과는 차단.
- 추가 예약이 있어도 원본 E1 중복 호출·중복 계획·중복 정산은 0건.

## R34-2 · 격리 적용의 DB 별칭 경로 미검사 · P2

### 코드 근거와 재현 한계

`pm_evidence_recovery.py:148~154`는 최상위 root를 resolve하고, `_apply:379~391`은 두 root 경로의 같고 다름으로 운영/격리 모드를 구분한다. 아래의 실제 DB가 같은 파일인지는 검사하지 않는다.

임시 경로에서 `copy/E1/sessions`를 `original/E1/sessions`로 연결했다. 서로 다른 root로 apply-isolated를 호출했지만 실제 DB는 같았고, 실제 저장 경로가 원본에 계획 1건을 기록했다.

```text
roots_different = true
same_database = true
apply_isolated_result = saved
plans_in_original = 1
```

이 진단은 실제 _apply·ManagementStore·SQLite를 실행했지만 diagnose는 기존 단위검사처럼 모의 대체했다. 전체 실제 E1 진단을 연결한 재현은 아니다. 실제 diagnose에도 DB 별칭 거부 조건은 없으며 원본/사본 내용 일치 조건은 동일 DB를 거부하지 않는다. 운영 DB가 실제로 변경됐다는 의미는 아니다. 정상 독립 사본에서는 발생하지 않는 오구성 경계이므로 P2로 분류한다.

### 수정·검증 기준

- ManagementStore 초기화·스키마 생성·기록 전에 격리 대상 DB의 실제 경로와 파일 동일성을 확인한다. 원본·동결 증거 사본과 연결된 중간 디렉터리/DB 심볼릭 링크, 같은 파일·하드링크를 격리 대상으로 수용하지 않는다.
- SQLite의 WAL/SHM 및 잠금 위치까지 원본 공간에 쓰지 않는지 확인한다. 검사와 저장 시점 사이 대상이 바뀌면 쓰지 않도록 경로 정책과 잠금 범위를 정한다.
- 정상 독립 사본은 성공, 중간 디렉터리 링크·DB 파일 링크·하드링크·원본 동일 대상은 저장 전에 거부한다. 거부 전후 원본 행·스키마가 그대로인지 검사한다.
- diagnose를 모의 대체한 저장 단위검사에 더해, 실제 진단과 적용을 연결한 사본 범위 검사 1개 이상을 추가한다.

## 알려진 잔여 위험과 적용안 확인

제출한 native 실행 파일의 최종 해시 검사와 실제 프로세스 시작 사이 경로 교체 창은 남아 있다. 저장 E1의 무호출 복구에 직접 적용되는 문제는 아니며 이번 R34-1과 구별한다. 향후 실제 호출 적용안에는 고정 native 경로·해시와 실행 기간 패키지 교체 통제를 명시한다. 이 기록을 보안 위험이 제거됐다는 증거로 사용하지 않는다.

추가로 평가기는 실행 시 clean Git checkout과 HEAD/채택 증빙을 요구한다(`evaluate_pm_behavior.py:770~779`). 복구 명령의 archive marker 지원과는 다르다. 비공개 적용안에서 **복구기·worker·후속 평가기를 각각 어느 고정 경로/코드로 실행할지**와 그 코드·장부 채택 증빙이 일치하는지 확인한다. archive 내부에서 그대로 실행한다고 가정해 Git 검사를 제거하지 않는다. 현재 비공개 명령을 읽지 못했으므로 이 항목을 별도 확정 결함으로 판정하지 않는다.

## 확인한 개선과 남은 범위

- 실행기가 향후 `termination_cause`와 `effective_timeout_seconds`를 기록합니다. 과거 E2 결과에 없는 원인을 임의로 채우지 않습니다.
- 복구 도구는 대상 요청·이전 질문·같은 job/session/attempt·종료·원문·저장소·장부·사용량을 대조하고, 정산과 재개 준비를 단계별로 기록합니다. 재진입 시 중복 정산을 막는 구현을 확인했습니다.
- 평가기는 E2에서 계획 준비 조건을 충족하지 못하면 E3로 넘어가지 않습니다. 정산 완료만으로 사례를 통과시키지 않습니다.
- 실제 운영 E2는 종료 원인 증거가 없다는 서버 보고에 따라 `hold_unknown`입니다. 새로운 기록 필드만 추가해도 과거 사건이 복구되는 것은 아닙니다.
- 제출된 복구 검사는 주로 재개 준비와 큐의 재취득까지 확인합니다. 실제 Dispatcher·Automation을 통한 PM 결과 채택까지 제품 회귀 검사로 제출해야 원래 D 범위를 닫을 수 있습니다.

## R35-1 — 계정의 미래 대기 시각을 복구가 지움 · P2

### 근거

`src/ai_company/timeout_recovery.py`의 초기 안전성 판정은 계정의 `state`·`reason`을 확인하지만 함께 조회한 `resume_at`을 검사하지 않습니다. `guard_cleared` 단계의 계정 복구도 `state`·`reason`만 다시 확인한 뒤 `AVAILABLE`, `resume_at=NULL`로 갱신합니다.

따라서 현재 계정에 남아 있는 미래 대기 시각, 또는 정산 이후 중단된 복구에 새로 추가된 대기 시각을 지울 수 있습니다. 정산 가능 여부와 새 호출 허용 여부는 각각 보존해야 합니다.

### 독립 재현

제출한 `TimeoutRecoveryTests` fixture와 원래 복구·장부 코드를 임시 SQLite/Git 작업 공간에서 실행했습니다. Work 환경에 사용자 systemd가 없어 `service_alive` 두 참조만 `False`로 대체했습니다. 외부 모델·운영 DB·서비스에는 접근하지 않았습니다.

| 합성 경계 입력 | 관측 결과 |
| --- | --- |
| 최초 진단 전, 대상 UNKNOWN 계정의 `resume_at`에 현재보다 1시간 뒤를 저장 | `same_session_retry_preparable` → 적용 `done` → `AVAILABLE`, 대기 시각 삭제 |
| 정산 직후 중단 → 미래 `resume_at` 추가 → 기존 계획으로 재진입 | 중복 정산 없이 `done` → `AVAILABLE`, 대기 시각 삭제 |

두 경우 모두 이후 합성 미시작 예약이 `RESERVED`로 허용됐습니다. 이 예약은 즉시 취소했으며 CLI를 시작하지 않았습니다. [재현 스크립트](repros/pr35-future-cooldown-3ef6fe7.py)를 대상 HEAD 체크아웃에서 `PYTHONPATH=src:. python <스크립트 경로>`로 실행할 수 있습니다.

**이 결과는 주입한 경계 입력에 대한 재현입니다. 실제 운영 E2에 미래 대기 시각이 있었거나 정상 API 호출 순서에서 이 조합이 생겼다는 증거는 아닙니다.** 기존 계정 대기 조건을 보존하라는 복구 계약에 대한 결함으로 분류합니다.

### 수용 기준

1. 최초 진단과 단계 재진입, 실제 계정 해제 직전에 남은 대기·별도 차단 조건을 검사합니다. 같은 계정 그룹의 참조 사이에 미래 시각이나 차단 상태가 다르면 안전하게 대기하고, 한 참조만 보고 전체를 해제하지 않습니다.
2. 미래 대기 시각·해석 불가능한 값·판정 후 바뀐 제한 조건을 임의로 삭제하지 않습니다. 어떤 조건을 기다리는지 기록합니다. 유효하게 만료된 시각과 대기가 없는 정상 경로는 별도 검사합니다.
3. 이미 끝난 정산과 원래 사용량은 보존합니다. 계정 해제가 보류됐다고 정산을 되돌리거나 다시 더하지 않습니다. 재진입 후에도 동일 job/session과 복구 단계가 유지돼야 합니다.
4. 계정의 마지막 확인과 갱신은 같은 트랜잭션의 조건부 변경 등으로 보호합니다. 검사 직후 추가된 제한을 덮어쓰지 않아야 합니다.
5. 위 두 재현을 수정 전 실패→수정 후 성공하는 회귀 검사로 바꾸고, 정산 후·계정 해제 직전 중단 및 그룹 참조 불일치도 관련 검사에 포함합니다.

## 다음 작업 — PR #35 안에서 일괄 완료

### A. R35-1과 같은 복구 단계의 제한 조건 보존

위 수용 기준을 수정·검증하세요. 종료·사용량·세션의 기존 대조를 약화하지 말고 현재 사건의 UNKNOWN을 바꾸지 않습니다. 이 범위의 비운영 수정은 추가 착수 확인 없이 진행합니다.

### B. 실제 제품 경로의 모의 통합 검사를 회귀에 포함

정상 제품 의존성을 설치한 환경에서 실제 Automation·Dispatcher·SessionQueue·공용 장부를 사용하세요. 외부 CLI 경계와 필요시 OS 관측만 통제하고, 제품 경로의 job 생성·회수·정산·결과 채택 메서드를 대신 작성하지 않습니다.

- E2 첫 응답과 후속 요청 → 후속 호출 시간 초과 → UNKNOWN과 누적 사용량 → 승인 적용을 모의한 복구 → 다른 worker의 같은 job/session 재개를 확인합니다.
- 재개 성공 시 정상 출력 검증과 E2 계획 저장까지 확인합니다. 정산만 성공하거나 계획 준비가 안 된 경우 E3는 시작하지 않아야 합니다.
- 정산 후 중단, 재개 준비 후 중단, 복수 worker의 동시 재취득에서 재정산·동시 실행·계획 중복이 없어야 합니다.
- 미래 대기 시각이 있으면 복구 후에도 새 CLI 호출이 시작되지 않고, 허용 시각 이후 원래 작업으로 재개되는지 확인합니다.
- 원본 누적 사용량·남은 실행 예산·전역 수정 횟수와 E1 PASS를 보존합니다. 실제 모델 호출은 필요하지 않습니다.

### C. 과거 E2의 증거 확보 여부를 한 번에 판정

기존 비공개 journal·실행기 기록·stdout/stderr·프로세스/서비스 기록에서 원인을 입증할 독립 증거가 있는지 읽기 전용으로 조사하세요. 원본 응답에 없던 필드를 새 코드로 채우거나 현재 시간으로 과거 사실을 만들지 않습니다.

- 증거가 있으면 정확한 job/attempt·시각·출처·해시에 연결한 별도 복구 증거로 제시합니다. 종료 여부, 종료 원인, 출력 완결성, 외부 효과 확인을 각각 구분하세요.
- 확보할 수 없으면 **“원인 증거 복구 불가”**로 결론을 남기세요. 없는 필드가 나중에 생기기를 기다리는 상태로 보고하지 않습니다.
- 이 경우, 종료·동일성·불완전 출력·효과·사용량·다른 대기 조건까지 별도로 확정할 수 있는지 검토하고, 과거 사건 한 건에 대한 운영자 판단 절차가 가능한지 **설계와 위험·검증 계획만** 제안하세요. `timeout`을 증명한 경로와 같은 판정으로 합치거나 범용 우회 옵션을 먼저 만들지 않습니다.
- 필요한 사실이 계속 불명확하면 HOLD를 유지하고 부족한 근거를 명시합니다. 원인 미확정과 실행 종료 미확정은 같은 사실로 취급하지 않습니다.

### D. 패키징·독립 검수·통합 재개안

R35-1 최초 실패→수정 후 성공, B의 제품 회귀, C의 결론을 하나의 제출 기록으로 묶으세요. 최종 HEAD의 관련 CI·독립 정적 검수·설치 archive 관련 검사를 완료하고 제품 커밋·파일 해시·archive 해시를 다시 고정합니다. 모델 검수는 현재 공용 장부·계정 제한을 우회해 실행하지 않습니다.

조건을 충족한 경우에만 실제 대상 예약·계정·worker·정산·예산·실패 시 보존 조치를 고정한 통합 적용안을 준비합니다. 기존 승인의 재사용 가능 범위를 대조하고, 새 후보·복구 방식이 승인을 벗어나면 그 구체적인 운영 변경만 한 번 확인하세요. 증거가 부족하면 운영 적용 승인 질문으로 넘기지 않습니다.

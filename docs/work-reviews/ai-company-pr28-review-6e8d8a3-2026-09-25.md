## R28-4b · P2 · 한 역할의 추천 상한 초과가 다른 역할의 추천까지 지움

**원인:** [automation.py의 _select_skills](https://github.com/HyungwonPark/ai-company/blob/6e8d8a3d7871b707fae6a0d553924f4eefc99e66/src/ai_company/automation.py) 321~325행에서 후보를 추가한 다음 `len(assignments[role_key]) == 3`을 검사한다.

이미 승인 지침이 3개인 역할에는 공개 후보가 네 번째로 들어간다. 길이는 4이므로 중단 조건도 만족하지 않는다. 뒤의 build_selection이 상한 위반으로 실패하면 fallback이 다른 역할의 정상적인 공개 추천까지 함께 지운다.

**최소 재현 조건**

- impl 역할: 승인된 지침 3개, 추가 역량 performance는 부족.
- qa 역할: 승인 지침 0개, performance 필요.
- PM은 두 역할 모두에 실제 조사 결과에 있는 공개 후보 public-d를 추천.
- 외부 후보는 review_pending이고 selected=false다. 설치·실행·승인된 것으로 간주하지 않는다.

[최소 재현 스크립트](repros/pr28-three-approved-regression-6e8d8a3.py)를 실제 선택기에 연결해 다음 결과를 확인했다. 카탈로그와 입력만 시험 자료로 대체하며 외부 네트워크·모델 호출은 없다.

```text
status: selected
outcome: lookup_failed
reason: 자료 조회 실패: invalid role or too many recommended skills
role_outcomes: impl=review_pending, qa=review_pending
impl의 기존 승인 지침: 3개 유지
qa의 정상 공개 추천: 빈 배열로 사라짐
```

조회는 실패하지 않았는데 조회 실패로 표시되고, 영향을 받지 않아야 할 qa 역할의 추천도 없어진다. 안전상 외부 지침이 자동 실행된 사례는 아니지만 역할별 추천·상태의 정확성 요구를 충족하지 못한다.

## 수정 수용 조건 — 이번 남은 범위

1. 후보를 추가하기 전에 역할별 남은 수를 검사한다. 이미 3개면 자동으로 네 번째를 추가하지 않는다.
2. 기존 승인 지침 3개를 임의로 교체하지 않는다. 부족한 역량과 상한 때문에 후보를 추가하지 못한 이유를 해당 역할에 기록한다. 교체 제안이 필요하면 새 계획의 검토 대상으로 둔다.
3. 한 역할의 상한 처리로 다른 역할의 정상 추천을 삭제하지 않는다.
4. 전체/역할별 상태·사유·실제 후보 목록이 일치해야 한다. 추천 수 제한을 네트워크 조회 실패로 표시하지 않는다.
5. 필수 역량이 부족하면 기존 준비 차단을 유지한다. 역할별 상한을 늘리거나 준비 검사를 약하게 만들어 통과시키지 않는다.

필요한 회귀는 다음 네 가지다.

- 승인 지침 0개 + 유효 후보: 정상 추천.
- 승인 지침 2개 + 후보 여러 개: 전체 3개 이하.
- 승인 지침 3개 + 추가 후보: 기존 선택 보존과 해당 역할의 상한 사유.
- 위 3개 역할과 빈 역할이 한 계획에 함께 있음: 빈 역할의 유효 추천과 역할별 상태 유지.

재현 스크립트는 현재 결함을 관찰하는 자료다. 현재 종료 코드 0을 제품 합격으로 해석하지 말고, 수정 후 올바른 후보 목록·상태를 단언하는 회귀로 전환한다.

## 실제 공개 조회·모의 검증·실제 사용의 구분

- **실제 공개 조회:** [공개 자료 기록](public-skill-research-2026-09-25.md)의 GitHub 고정 커밋 `SKILL.md`·`LICENSE` 2건을 직접 읽고 파일·묶음 해시를 기록했다. 내용 검토와 worker 전달은 하지 않았다. 공개 검색 자동 기능은 단위 검사에서 모의했고, 실제 검색 결과가 곧 승인된 스킬이라는 주장은 하지 않는다.
- **모의 모델·API:** Python fixture와 v2 브라우저는 모의 PM·리뷰어 응답을 사용한다. API 저장/거부, 분리된 세션·계획·실행 ID, 전달 receipt는 실제 제품 코드로 검사한다.
- **실제 모델 평가:** 기존 pilot 허용 파일·예산·모델 적격성과 별개로 PR #28의 PM 지침·스킬을 실제 Astra에 읽기 전용 평가한 기록은 없다. 모델이 필요한 질문과 이견을 올바르게 판단했는지는 미검증이다.
- **실제 마스터/APK·운영:** 마스터 직접 계획 확정, APK 화면, 운영 worker에서의 전달·효과는 미검증이다. 테스트 클라이언트의 확정을 사용자 승인으로 해석하지 않는다.
- **보호 한계:** 한 계획에 담을 질문은 최대 20개다. 누적 미해결 질문이 이를 넘으면 오래된 질문을 조용히 버리지 않고 준비 판정이 막힌다. 이 사례의 정리 방식은 별도 범위 검토가 필요하다.

## 비운영 후보 적용·복구안 — 승인 아님

대상은 같은 소스의 웹과 PM·조정기 worker다. 번역 worker·기존 서비스는 교체하지 않는다. 새 저장소 구성은 관리 DB의 `management_skill_catalogs`, `management_skill_catalog_active` **추가 테이블 2개**, 별도 `skill-research.sqlite`의 영속 조사 작업/조회 테이블이다. 기존 v1/v2 plan/request/approval의 원문·digest는 재작성하지 않는다. 새 v3 PM 지침, v2 계획 검수와 선택적 skill 필드가 생긴다.

1. 적용 전 운영 커밋·이미지 digest, 웹·worker 설정, 계정 한도, 대기 PM 요청/검수/실행, DB 스키마를 비공개로 대조한다. 관리 DB는 SQLite 온라인 백업하고 이전 웹·worker 이미지를 보관한다. 서명키·비밀정보를 공개 문서에 넣지 않는다.
2. 신규 PM·역할 배정만 멈추고 기존 실행의 저장 결과를 대조한다. 동일 후보의 worker를 한 인스턴스로 시작해 DB 테이블 추가·기존 기록 보존을 확인한 다음 웹을 교체한다. 번역 worker와 커플 앱·기존 타이머는 유지한다. 오래된 웹/새 worker 혼합 상태에서는 새 계약의 기술 화면이 빠질 수 있으므로 혼합 구간에 새 계획 확정을 열지 않는다.
3. 로그인·기존 기록·digest, 오래된 미확정 계획의 차단, 새 요청/검수, 필수 지침 누락 차단, 선택적 조회 실패의 계속 진행, 역할별 receipt, 공유 한도·단일 worker를 확인한다. 실제 모델 시험은 현 pilot 권한·예산 안의 별도 승인된 작은 과제로 한다.
4. 새 v3 요청·계획·스킬 선택/조사 작업이 **전혀 생성되지 않았을 때만** 이전 웹·worker 이미지를 함께 되돌린다. 새 기록이 생긴 뒤 필수 검사가 실패하면 신규 자동 실행만 중지하고 관리·보고·승인 읽기 화면 및 DB·큐·모든 실행 이력을 보존한다. 구 worker를 새 요청에 연결하거나 DB를 과거 백업으로 덮어쓰지 않는다. 호환 수정 후보를 새로 검증한다. 별도 조사 SQLite를 제거하거나 예산을 초기화하지 않는다.

미리보기·CI·이미지 digest가 운영 배포 승인은 아니다. 실제 적용 전 운영 후보의 이미지 digest 및 현재값 대조가 필요하다.

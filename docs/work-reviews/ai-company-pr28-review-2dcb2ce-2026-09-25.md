이 재현은 질문·답변 의미를 코드가 완벽히 해석해야 한다는 요구가 아니다. **명시적으로 기재한 질문 출처가 존재하지 않는데도 유효한 근거로 받아들이는 구조 검증 문제**다.

- 명시한 질문 출처가 같은 프로젝트의 실제 요청·계획·수정 질문인지 검사하고 ID를 함께 묶는다.
- 질문에 대한 후속 답변이라고 기록했다면 질문 이후 사용자 메시지여야 한다.
- 사용자가 최초 목표에서 이미 명확히 정한 사항은 “목표에서 주어진 결정”처럼 다른 근거 유형으로 표현한다. 이를 임의의 새 질문에 대한 답변으로 꾸미지 않는다.
- 피드백 저장·계획 생성·새 확정의 공통 검사에서 같은 기준을 사용한다.
- 다른 프로젝트, 없는 질문, 선행 메시지, 재사용된 질문 ID를 거부하고 정상적인 기존 결정의 재사용은 보존한다.

## R28-4 · P2 · 공개 검색 결과가 역할별 조사·추천으로 이어지지 않음

**근거:** automation.py의 `_select_skills`, 239~273행 및 PM 계획 처리 355~357행.

공개 검색 경로는 존재하지만 성공한 저장소의 개수만 계획 결과에 사용한다. 실제 검색 자료는 조사 SQLite에 남아도 계획에는 출처·저장소·후보가 없다. 고정 URL로 미리 넣어 둔 자료만 역할 추천에 들어간다. 검색은 PM의 PLAN_READY 뒤에 수행되어 PM이 새 결과를 판단하는 후속 단계도 없다.

[재현](repros/pr28-skill-search-recommendation-loss.py)은 실제 선택기·조사 저장소를 사용하고 HTTP 응답만 대체한다.

```text
검색 결과: 공개 저장소 1개
outcome: search_found_unpinned
status: no_additional_skill
roles: qa=[], ui=[]
계획 안의 검색 저장소 URL/식별자: 없음
```

이는 공개 자료를 전달하지 않는 보호 조건의 문제가 아니다. 사용자가 요청한 “초기 PM이 검색을 통해 스킬을 찾아 역할에 맞게 추천”하는 연결이 빠진 것이다.

**수정·수용 기준**

- 발견한 저장소/문서 출처와 조회 ID, 미검토 상태를 결과에 유지한다.
- 정해진 예산 안에서 후보의 고정 커밋·SKILL.md·필요 참조·라이선스를 읽고 역할·요구사항별 적합 근거를 만든다.
- 여러 미충족 역할 중 첫 검색어만 처리하고 끝내지 않는다. 처리한 역할과 예산 때문에 조사하지 못한 역할을 구별한다.
- PM이 조사 결과를 읽어 채택/보류를 설명하고, 그 선택을 새 계획 검수 전에 고정한다. 계획·검수·확정의 digest 연결을 유지한다.
- 검토 전 후보는 추천할 수 있지만 실제 지침 전달·설치로 이어지지 않는다.
- “추가 지침 불필요”, “검색 결과 있으나 조사/검토 미완료”, “조회 실패”를 구별한다.
- 실제 공개 자료로 최소 한 번 검색 → 문서 조사 → 역할별 추천까지 연결한 기록을 남긴다. 반복 회귀는 고정 응답으로 수행해 외부 서비스에 의존하지 않는다.

## 검사 범위와 추가 보완

새 v2 API 검사 자체가 서버 확정 검사를 우회하는 것은 아니다. 제어 도우미는 worker 실행·재시작·배정을 호출하며 계획·검수 결과를 DB에 직접 주입하지 않는다. 그러나 `pm_v2_flow.cjs`는 확정 모달·확인 체크·제출 버튼을 누르는 대신 브라우저 문맥에서 직접 HTTP 확정을 요청한다.

수정 후보에는 같은 v2 흐름에서 **계획 검토·확정 버튼 → 모달의 정확한 계획 → 확인 체크 → 제출 → 같은 실행으로 이동**하는 격리 브라우저 검사 1개를 추가한다. 이 자동 조작도 실제 마스터 조작과는 구별한다. 이미 통과한 API 차단 검사를 없애지 않는다.

프로젝트 정책의 `max_repairs`와 PM 자동 수정 최대 2회의 관계도 명시한다. 현재 0으로 설정해도 PM 자동 수정은 2회 수행되고 aggregate repairs는 0인 사례가 관찰됐다. 이 필드가 코드 수정에만 적용되는지 PM 수정까지 포함하는지 계약 정의를 대조해야 하므로 위 수정·보완 5건에 추가하지 않았다. 어느 쪽이든 사용자에게 설명한 상한·누적 예산과 실제 집계가 일치해야 하며, 비용·시간·실행 횟수의 기존 상속을 유지한다.

실제 Astra 판단 평가, 실제 마스터/APK, 운영 적용은 여전히 별도 미검증이다. 이것을 핑계로 위 코드 수정·공개 자료 조회·자동 브라우저 검증을 멈추지 않는다.

PR #28의 기존 브랜치에서 위 5건을 보완한다. PR #26·#27을 다시 만들거나 해결된 R27-1을 되돌리지 않는다. 새 기능 범위를 늘리지 않고 현재 A→D 요구사항의 수용 조건을 완성한다.

1. 질문 기록/계획 확정 담당과 Dispatcher/스킬 조사 담당이 독립 파일 범위에서 병행할 수 있다. automation.py 같은 공통 파일은 통합 담당자를 정한다.
2. R28-1·R28-2를 먼저 고치고 R28-3~5를 같은 후보에 반영한다. 모든 재현을 최초 실패 → 수정 성공의 제품 회귀로 전환한다.
3. 새 질문의 의미 판단과 서버의 출처·순서·권한 검사를 구별한다. 테스트를 통과시키려고 사용자 결정을 합성 승인하거나 검수 단계를 없애지 않는다.
4. 관련 검사와 필요한 기존 회귀, 새 확정 UI 조작, 공개 조사→추천 증거, 독립 검수까지 진행한다.
5. 변경된 제품으로 미리보기·manifest·ZIP을 다시 만들고 같은 최종 HEAD의 CI와 해시를 제출한다. 새 기록 이후 단순 구버전 복귀가 가능한지 적용·복구안을 갱신한다.
6. 보고에는 해결한 지적 ID, 제품/검사/게시 SHA, 최초 실패와 수정 결과, 미실시 범위를 연결한다. 구현자 검수와 Work PM 최종 수용을 구분한다.

비운영 구현·검수·패키징은 단계별 추가 확인 없이 계속한다. 운영 배포·병합·PR #10 pending 변경·서명키·추가 계정/유료 서비스·전역 격리 완화는 포함하지 않는다. 기존 커플 서비스와 운영 기록을 유지한다.

## 재현 실행 방법

기준 소스의 테스트 의존성이 설치된 비운영 checkout에서 아래처럼 실행한다. 각 스크립트는 임시 상태/모의 실행을 사용하고 제품 파일을 수정하지 않는다.

```bash
PYTHONPATH=src:. uv run --frozen python <재현 스크립트 경로>
```

재현 스크립트 4개와 이 기록은 Work 검수용 문서 디렉터리에 보관한다. 원문과 결과가 같다고 확인된 고정 커밋으로 참조하고, 서버에서 수정할 때는 실패 결과를 그대로 합격으로 판단하지 않는다.

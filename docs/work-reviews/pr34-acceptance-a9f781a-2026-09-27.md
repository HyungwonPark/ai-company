## 해결 근거와 검증 범위

### R34-1 — 원본 정산 보존과 정상 후속 예약

`pm_evidence_recovery.py`는 동결된 원본 7건의 예약 ID로 예약 행과 정산 journal을 각각 비교한다. 정상 후속 예약이 추가됐다는 이유만으로 장부 전체가 달라졌다고 거부하던 조건을 제거했다.

후속 예약은 같은 요청·요구사항 버전·목표·설정, 원본 계획부터 이어지는 수정 계보, 실제 task/job/attempt·세대·역할·공용 계정 그룹, 저장 결과와 정산 journal에 연결한다. 무관한 예약·원본 7건 변조·잘못된 세대·예산 초과는 계속 거부한다. 실제 Dispatcher의 기록 형식과 `complete_pm_revision`의 부모·자식 관계도 대조했다.

새 통합 검사 10개는 실제 `diagnose`, `verify_saved_recovery`, canary, `SharedCallLedger`를 연결한다. **후속 검수·quota 재개·REVISE 수정 상태 일부는 SQL로 직접 구성하며, CLI 관찰·설정 검증도 모의 대체한다.** 따라서 증명한 범위는 실제 복구 검증 함수가 합성된 후속 상태를 판별하는 동작이다. 실제 worker가 해당 상태로 진행하거나 실제 모델이 내용을 올바르게 판단했다고 해석하지 않는다. 제출문의 “운영 모델·CLI 호출만 모의 대체”는 이 한계를 함께 읽으며, 다음 보고에서 표현을 바로잡는다. 이 문구 정정만으로 제품 재작업을 요구하지 않는다.

### R34-2 — 격리 사본의 원본 DB 쓰기 방지

DB·디렉터리·보조 파일의 별칭을 검사하고, SQLite 쓰기를 접근 제한된 별도 임시 DB에서 완료한다. 사본 게시에는 최초에 연 디렉터리 FD를 사용한다. 내용 있는 WAL은 보존하며 거부하고, 빈 WAL·SHM 정리는 사본 게시 시에만 수행한다.

Work의 독립 검사에서 제품 `RecoveredPlanTests` 11개를 통과했다. 추가로 최종 검사 이후 게시 직전 사본 경로를 원본 링크로 바꾸어도 원본 DB 바이트·계획 0건이 보존되고 분리된 사본에만 계획 1건이 생겼다. 게시 실패를 강제하면 사본 DB는 그대로였으며 재시도 후 계획 1건이 저장됐다.

이 Work 환경은 LangGraph가 없어 메모리상의 검사 모듈에서 해당 저장 경계에 미사용인 `Automation`·`Dispatcher` import만 제거했고, `diagnose`는 제품 저장 시험과 같이 모의 대체했다. SQLite·파일·링크·FD 동작은 실제 임시 파일에서 실행했다. 제품 소스 파일을 수정하거나 전체 운영 통합 검사를 실행한 것은 아니다. **사본 DB에 다른 접속 없음, 스테이징과 사본이 같은 파일시스템**이라는 적용안 전제는 유지한다.

## 다음 실행 — 한 번의 구체적 운영 승인 후 연속 진행

아래 A~E를 하나의 적용·평가 범위로 권고한다. **현재 사용자 메시지는 검수 제출이며 새 운영 승인으로 간주하지 않는다.** 승인 전에는 읽기 전용 대조·문서 정리만 가능하다. 승인 후 동일 후보·범위·예산이 유지되면 단계마다 다시 승인을 요청하지 않는다.

### A. 적용 직전 대조

1. archive·제품·설치 소스·Python·native CLI 버전과 해시, 현재 릴리스 포인터·유닛·비공개 설정·채택 증빙을 대조한다. 평가 실행기의 깨끗한 Git checkout HEAD와 복구 검증기 커밋은 **제품 `4c3ba4616653196d021ab8b5f8cb48c080a11789`**로 일치시킨다. 제출 문서 HEAD나 archive marker로 이를 대신하지 않는다. 기존 평가 입력의 대상 기준·digest는 바꾸지 않는다.
2. 두 worker의 중지 상태, 단일 실행 잠금, quota 가드·타이머, 기존 대기 작업과 UNKNOWN 계정, 원본 7건·미정산·체크포인트·현재 공용 사용량을 확인한다. 상태가 준비안과 달라졌으면 쓰기 전에 차이를 보고한다.
3. DB·장부·체크포인트의 일관 사본과 현재 포인터를 보존한다. 격리 사본 시험의 다른 접속·파일시스템·WAL 조건을 확인한다. 설치 후보의 기존 무호출 사전 점검을 사용하며 전체 제품 검수를 처음부터 반복하지 않는다.

### B. 고정 릴리스 적용과 E1 무호출 복구

1. PM·조정기 및 번역 worker가 참조하는 릴리스를 위 고정 제품으로 교체한다. 두 worker는 E1 복구가 끝날 때까지 중지 상태로 둔다.
2. `apply-operating-and-canary`로 저장 E1 원문을 재검증하고 파생 계획·revision·canary를 멱등 저장한다. **원래 E1 PM 호출을 다시 보내지 않는다.** 추가 예약이 있다면 수정된 계보 검증으로 분류한다.
3. 저장 계획의 원문 연결·digest·요구사항 버전, 원본 7건 보존, 실제 예약·정산 변화, canary 결과를 대조한다. 원본 응답이 복구 불가하거나 계획이 거부되면 우회하거나 새 E1 PM 호출로 대체하지 않는다.

### C. 실제 내용 검수·제한된 수정·E2~E6

1. 단일 실행과 대기 목록 확인 후 두 worker를 재활성화한다. 승인된 평가·기존 승인 작업만 처리한다. 번역 서비스가 떠도 Claude `UNKNOWN`이면 모델 호출은 계속 대기해야 한다. 계정 확인이나 모델 대체를 임의로 허용하지 않는다.
2. 같은 원본 E1 계보에서 별도 세션의 실제 내용 검수를 수행한다. 정상 `REVISE`는 기존 자동 수정·재검수 정책 안에서 처리한다. 필수 마스터 결정은 대신 답하지 않는다. E1의 고정 통과 조건 충족 후 E2~E6을 이어간다.
3. 고정 평가의 **전역 24호출·1,800초·수정 2회와 사례별 제한**을 유지한다. 기존 7건과 실제 누적 사용량을 포함하고 새 실행 디렉터리로 예산을 초기화하지 않는다. 제출된 약 205.868초는 서버에서 다시 대조한다. 청구액 미확인을 0원으로 보고하지 않는다.
4. 사용량 제한은 영속 대기·종료/정산 확인·같은 job/session 재개 경로를 사용한다. 재개를 새 PM 실행이나 새 수정 횟수로 세지 않는다. 재개로 새 모델 호출이 발생하면 실제 호출 수와 실행시간은 누적 예산에 포함한다. 종료·정산 불명은 추가 호출하지 않는다. 한도 회복 전 반복 호출이나 제한을 우회하는 후보 변경은 하지 않는다.
5. 평가용 계획 생성·내용 검수는 마스터 확정·개발 배정 권한을 주지 않는다. 실제 APK 확정이나 최종 프로젝트 성공으로 보고하지 않는다.

### D. 중단·복구

해시·기록·스키마·CLI 증거·계정·예산 검증 오류, 저장 복구 실패, 예기치 않은 모델 호출 또는 무결성 위반이면 새 호출을 막고 **두 worker를 중지·자동 시작 해제해 `inactive/disabled`를 확인**한다. 수정 한도 내 정상 REVISE와 예약 가능한 quota 대기를 공통 환경 오류와 구별한다. E1이 허용된 수정 후에도 통과하지 못하면 E2~E6은 시작하지 않고 두 worker를 `inactive/disabled`로 전환해 실패 근거를 보존한다.

파생 계획·revision 등 운영 쓰기나 새 예약이 생긴 뒤에는 DB·장부·체크포인트를 과거 사본으로 덮거나 구형 worker를 다시 켜지 않는다. 포인터 복구는 운영 쓰기가 없고 호환 조건이 확인된 단순 포인터 전환에만 적용한다. 종료·정산을 확인하지 못한 실행은 불명 상태를 보존한다.

## 유지할 범위와 남은 위험

웹·커플 서비스, 전역 CLI, quota 타이머 일정, 기존 승인·기록과 PR #10 `pending`을 유지한다. 제품 병합, APK 마스터 조작 대행, 서명키 작업, 별도 상용화 설계는 이번 운영 범위가 아니다. 기존 CLI 최종 해시 검사와 실행 사이의 경로 교체 가능성은 앞선 적용안의 잔여 위험으로 보존한다. 실행 중 설치본을 갱신하지 않는 조건과 실제 경로·권한 대조를 유지하며 이번 수정으로 제거됐다고 주장하지 않는다.

서버의 두 worker `inactive/disabled`, quota 타이머 `active/enabled`, 현재 운영 E1 계획 0건·정산 7건·미정산 0건은 제출 보고에 따른 상태다. Work는 비공개 서버에 접속해 확인하지 않았다. 이번 Work 변경은 검수·지시 문서뿐이며 문서 게시가 서버 수신·착수·운영 승인·실제 모델 평가 완료를 뜻하지 않는다.

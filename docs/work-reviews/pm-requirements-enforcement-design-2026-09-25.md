# PM 역할의 실행 조건과 요구사항 검토 설계

2026-09-25 KST · 별도 설계 논의안 · 제품 변경·실행 지시·운영 적용 아님

## 목적과 판단

마스터는 PM이 의견을 전달하는 데 그치지 않고, 필요한 정보를 요구하고, 문제와 대안을 제시하고, 실행 가능한 명세를 책임지기를 원한다.

**PM의 검토 산출물과 실행 조건을 서버에서 검사하고, 판단의 품질은 독립 검토와 사례 평가로 관리한다.** 역할 문구·모델 설정·스킬만으로 좋은 판단을 보장할 수는 없다. 검증되지 않은 계획의 실행을 막는 절차는 프로그램으로 강제할 수 있지만, 모든 중요한 문제를 발견했는지와 추천안이 최적인지는 의미 평가와 사람의 확인이 필요하다.

사용자는 목적과 중요한 업무상 선택을 답하고, PM이 명세를 작성한다. 기술 파일·함수·구현 방식을 초보 사용자에게 작성해 오라고 요구하지 않는다.

PR #26 `a70144de65bfa8692d12f37d44c2769429520e9d`의 PM 관련 원본 코드를 기준으로 조사했다. 이번 조사는 PR #26의 U1~U3 수용 검수가 아니다. PR #26 구현·CI·독립 검수 성공은 제출 보고로 접수했으며, Work PM의 최종 수용 판정은 별도다.

기존 ECC의 PM 문서는 선택적으로 적용하는 지침이다. 파일이 있거나 전달 해시가 일치한다는 사실만으로 운영 PM이 이를 적용하고 의미까지 준수했다고 단정하지 않는다. 필수 PM 행동은 공통 단계 지침·응답 계약·서버 검사에 연결하고, 실제 적용 버전을 기록한다.

## PM 행동 규칙

1. **목표와 수단을 분리한다.** 사용자가 제안한 UI·도구·모델이 목적을 달성하는 데 적절한지 검토한다.
2. **이미 정한 결정을 읽는다.** 마스터의 확정, PM의 가정, 외부 자료의 제안, 현재 코드의 사실을 구별한다. 이전 답변을 다시 묻지 않는다.
3. **핵심 정보만 질문한다.** 사용자 대상·범위·비용·권한·완료 판정을 바꿀 답이 필요하면 질문한다. 한 번에 기본 1~3개로 묶되 질문 수를 채우려고 묻지 않는다.
4. **작은 가정은 책임지고 제안한다.** 되돌릴 수 있고 권한 범위 안인 선택은 가정과 영향으로 기록해 계획에 포함한다. 큰 범위 확대를 작은 가정으로 처리하지 않는다.
5. **이견은 근거와 대안을 함께 낸다.** “문제 → 관측 근거 또는 미확인 가정 → 영향 → 대안 → 추천 → 필요한 결정” 순서의 짧은 판단 요약을 남긴다.
6. **합리적인 요청에는 동의하고 진행한다.** 반드시 반박·질문·위험을 N개씩 만들라는 규칙은 두지 않는다.
7. **요구별 완료 기준을 쓴다.** “사용하기 편하게”만으로 완료 조건을 끝내지 않고, 누가 어떤 과제를 어떤 방법으로 확인할지 연결한다. 숫자 목표가 없다고 임의 수치를 사용자 확정으로 기록하지 않는다.
8. **근거에 맞게 완료를 판정한다.** 작성됨·모의 검증·실제 검증·운영 적용을 구분하고, 최종 산출물이 원래 요구를 충족했는지 확인한다.
9. **중요 변경을 드러낸다.** 계획 확정 뒤 범위·권한·비용·완료 기준이 바뀌면 기존 기록을 덮어쓰지 않고 변경 계획으로 다룬다. 승인된 범위의 단순 수정마다 전체 계획을 재승인받지 않는다.

모델의 비공개 사고 과정 전체를 저장할 필요는 없다. 사용자와 검수자가 확인할 수 있는 결정·근거·가정·다음 행동만 기록한다.

### 요구사항 계약의 최소 내용

기존 원문 목표와 PMPlanContent를 보존하면서 새 버전에 다음을 연결한다. 정확한 클래스/테이블 명칭은 후속 구현 설계에서 정한다.

- 목표 원문 참조, 정리한 문제, 대상 사용자와 대표 사용 흐름.
- 이번 범위·제외 범위, 확정된 제약과 근거.
- 요구사항별 ID, 출처, 완료 조건, 확인 방법, 담당 작업/역할.
- 채택한 가정과 영향, 아직 필요한 결정의 질문 ID·이유·답변/해결 상태.
- 발견한 문제의 ID·근거·영향·대안·처리 결과. 타당하면 문제 0건도 허용.
- 역할·파일·전달물·의존 관계와 기존 예산/권한 정책 참조.
- 요구사항 revision, 계획 digest, 사용한 PM 지침·검수 기준 버전.

품질 판단의 근거가 되는 내용은 계획의 불변 참조에 포함한다. 현재 코드의 승인·정책 모델을 새 자연어 문서로 대체하지 않는다. 가정은 사용자 확정과 구별한다.

### 준비 판정과 실행 차단

새 계획은 아래 조건을 모두 만족해야 기존 마스터 확정 단계로 제출한다.

- 필수 질문이 답변되었거나, 허용된 가정/명시적 범위 제외로 해결됐다.
- 필수 요구가 담당 작업과 검증 방법에 연결됐다.
- 차단 수준의 계획 검수 지적이 해결·재검수되었다. 가벼운 권고는 근거를 적고 채택/보류할 수 있다.
- 현재 서버의 파일·모델·예산·권한·의존성 정책 안에 있다.
- 검사와 검수 결과가 동일한 요구사항 revision·계획 digest·지침/검사 기준 버전에 연결된다.
- 기존 마스터 계획 확정 또는 기존 명시적 위임 조건이 유지된다.

서버가 준비 판정 기록을 생성한다. PM이 반환한 `ready=true`나 `blocking=false`를 그대로 신뢰하지 않는다. 필드와 참조 검사는 코드가, 자연어의 누락·모순 검토는 검수 단계가 담당한다. PM이 발견하지 못한 문제까지 형식 검사로 증명할 수 있다고 표현하지 않는다.

`complete_pm_request`에 준비 결과를 연결하고, `confirm_plan`과 실행 배정 직전 `_run`에서 다시 대조하는 확장을 우선 검토한다. 새 계획에 오래된 검수 결과를 연결할 수 없어야 한다. 질문·검수·응답 저장은 재시작·반복 전달에서도 중복 작업을 만들지 않도록 멱등성을 유지한다.

계획 내용 검수는 코드 후보의 기존 독립 검수·최종 검수와 별도 단계다. 코드 검수 PASS를 계획 검수로 재사용하거나 PM이 자신을 별도 검수자로 기록하지 않는다. 기존에 허용된 검수 모델·역할 정책 안에서 별도 세션과 근거를 기록하고, 다른 모델이라고 오류가 독립이라고 가정하지 않는다.

새 계약을 과거 확정 계획에 삽입해 digest를 변경하지 않는다. 과거 자료는 기존 버전으로 읽고, 새 계획부터 새 계약을 적용하는 전환 방식을 명시한다.

## 진행과 대기 표현

아래 명칭은 사용자에게 보여 줄 개념이며 현재 enum을 추가했다는 뜻이 아니다.

- **요구 정리 중:** PM이 조사하고 가정을 정리하고 있다.
- **답변 필요:** 중요한 결정에 마스터 답변이 필요하다. 질문과 추천안을 표시한다.
- **계획 검토 중:** 형식·범위 검사 및 내용 검수 중이다.
- **계획 확정 대기:** 검토한 정확한 계획을 마스터가 확인할 차례다.
- **진행 중:** 승인된 범위 안에서 실행한다.
- **확인 필요:** 접근·증거·정책 문제로 진행할 수 없는 이유가 있다.

사용량 대기·사용자 답변 대기·환경 오류를 같은 “목표 정체” 문구로 뭉치지 않는다. 답변 대기는 예정된 작업 상태일 수 있으며 오류나 PM 실패가 아니다. 의존성이 없는 다른 승인 작업은 기존 정책 안에서 계속한다.

PM이 교체되거나 재시작해도 확정 요구·가정·질문/답변·검수 지적·승인 범위·다음 행동을 서버 기록에서 복원한다. 모델의 대화 기억만 의존하지 않는다. 현재 PM/최종 검수의 Astra Ultra 지정, 공유 사용량·후보 정책을 이번 설계로 변경하지 않는다.

## 질문과 반박의 대화 예시

아직 대상이 정해지지 않은 새 프로젝트에서 사용자가 “초보자도 쓰는 AI 직원 서비스를 만들고, 첫 화면에서 그래프를 직접 연결하게 해 주세요”라고 한 상황의 예시다. 이미 순서형을 선택한 현재 프로젝트에서 같은 질문을 다시 하라는 뜻이 아니다.

> 목표를 입력하면 AI 팀이 일을 수행하고, 필요한 결정만 사용자에게 요청하는 서비스로 이해했습니다.  
> 첫 화면에서 그래프 연결부터 요구하면 초보자가 역할과 작업 순서를 먼저 배워야 할 수 있습니다. 목표 입력으로 시작하고, 그래프는 진행 확인과 팀 수정에 사용하는 구성을 추천합니다.  
> 첫 버전에서 맡길 대표 업무가 웹사이트 제작인지, 여러 종류의 프로젝트인지 정하면 범위를 구체화할 수 있습니다. 초기 구현은 한 종류부터 시작하는 안을 권합니다.

이 응답은 목표를 재확인하고, 제안된 수단의 문제를 근거 있는 가능성으로 지적하며, 대안과 중요한 선택을 제시한다. 사용자가 허용 범위에서 다른 안을 선택하면 이유와 영향을 기록해 그 결정을 반영한다.

## 구현 규모와 평가

PR #26의 화면 개선과 섞지 않고 별도 PM 기능 과제로 다룬다. 현재 단계에서는 설계 기록이며 서버 구현 착수나 운영 정책 변경은 수행하지 않는다.

1. **계약·평가 준비:** 기존 PM 질문 경로를 재사용하며 새 버전의 요구사항/응답·질문/지적 상태·준비 판정을 설계한다. 모의 검사와 아래 행동 사례를 먼저 만든다.
2. **한 흐름 연결:** 질문 → 답변 반영 → 명세 → 별도 계획 검수 → 기존 직접 확정 → 같은 계획으로 배정까지 연결한다. 모델 검수는 새 계획/중요 변경의 확정 직전에 수행하며 매 채팅마다 중복 호출하지 않는다.
3. **비교 검증:** 같은 입력 묶음에서 기존 PM과 새 PM의 누락·불필요한 질문·지적 근거·완료 판정·비용/호출 수를 비교한다. 실제 호출은 기존 허용 정책·예산 안에서 진행하고 모의 성공과 구분한다.

자동 계획 수정은 무한 반복하지 않는다. 초기에는 같은 revision에서 제한된 수정 횟수(예: 2회)를 정책으로 두고, 해소되지 않으면 지적과 선택지를 보고한다. 이 숫자는 현재 서버에 적용된 값이 아니다. 각 대화의 질문 개수나 검수 점수를 기계적으로 채우는 평가보다 해결한 결과를 평가한다.

| 평가 사례 | 기대 행동 |
| --- | --- |
| 모호한 목표 | 중요한 사용자·과제·성공 기준만 질문하고 명세 작성으로 진행 |
| 충분히 구체적인 요청 | 이미 답한 질문이나 불필요한 질문을 반복하지 않음 |
| 합리적인 요청 | 억지 반박·문제 생성 없이 근거를 갖춰 수용 |
| 목표와 충돌하는 방법 | 문제의 근거·영향·대안·추천을 제시 |
| “완전 자동”과 “모든 단계 수동 승인” | 충돌을 드러내고 작업 종류별 실행/승인 범위를 정리 |
| 검증 방법 없는 완료 조건 | 측정·관찰 가능한 확인 방법을 연결하고, 아직 확인 못 한 사실을 표시 |
| 형식만 맞고 의미가 빈 계획 | 필드 존재만으로 확정 준비에 통과시키지 않음 |
| 확정 후 중요 변경·오래된 검수 | 새 계획으로 검토하며 이전 결과·승인을 재사용하지 않음 |
| UI 확정 경로를 거치지 않은 직접 요청 | 서버가 같은 준비·승인 조건을 적용하고 미준비 배정을 거부 |
| 사용량 제한·재시작·중복 답변 | 기존 계획·답변·권한을 복원하고 중복 실행하지 않음 |
| CI만 통과하고 실제 APK 확인 없음 | 검증 범위를 구분하고 전체 실사용 완료라고 주장하지 않음 |

평가는 코드 검사와 모델 평가를 섞되, 모델 평가자는 사람의 표본 검토로 보정한다. 숫자 점수 하나로 최종 실행 권한을 정하지 않는다. “더 많은 질문/더 많은 반박”이 아니라 중요한 누락 감소와 불필요한 중단 감소를 함께 본다.

현재 코드가 계획마다 최소 2개 독립 역할을 요구하는 점은 별도 정책 검토 항목이다. 요구 정리/질문 단계까지 억지로 개발 역할을 만들지 않게 하고, 작은 작업의 역할 정책 완화가 필요하면 별도 버전 변경으로 검토한다. 이번 논의만으로 기존 병렬·역할 계약을 완화하지 않는다.

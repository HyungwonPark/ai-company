# 순서형 작업실 야간 구현·통합 검수 지시

기준일: 2026-09-24 KST · 버전: 1.0

## 목표와 완료 지점

마스터가 한 번 지시한 뒤 쉬는 동안, 기존 계획을 비운영 제품 후보로 구현하고 검수·수정·배포 준비까지 이어갑니다. 사용자의 이번 요청은 오래 걸리더라도 필요한 구현과 전체 검수를 묶어 진행하는 것입니다.

**목표: 순서형의 읽기·쓰기 동선과 G1~G3를 연결한 동일 후보, 독립 검수 결과, 미리보기, 적용·복구안을 아침에 검토할 수 있게 만듭니다.** 특정 시간까지 전부 완료된다고 보장하거나 일을 늘려 시간을 채우지 않습니다.

[PR #24 연결 계획](https://github.com/HyungwonPark/ai-company/blob/75227480d27d3eb1cd57fa43a07a0ab986be3eb5/docs/product-experience/journey-product-integration-plan-2026-09-24.md)과 [계획 검수](ai-company-pr24-plan-review-7522748-2026-09-24.md)를 기준으로 **A→C뿐 아니라 조건 충족 후 D·E까지** 진행합니다. 제품 구현은 서버 Codex가 담당하고 Work는 명세·검수를 담당합니다.

## 1. 중간 확인 없이 이어갈 범위

- 별도 작업 공간과 개발 브랜치에서 제품 코드·검사·문서 수정, 필요한 기존 의존성 환경 사용, 임시 시험 DB·API, 격리 브라우저 검증, 초안 PR 갱신을 진행합니다.
- 검수에서 발견한 이번 범위의 결함은 수정한 뒤 해당 회귀와 최종 통합 검증으로 이어갑니다. 단계별 완료 보고를 할 때마다 새 사용자 답변을 기다리지 않습니다.
- 임시 시험 DB의 가상 사용자로 계획 확정·후보 결정을 수행해 실제 API 계약을 검사할 수 있습니다. 이것을 마스터의 운영 승인·직접 APK 확정·PR #10 결정으로 기록하지 않습니다.
- 기본 배치는 순서형입니다. 같은 선택을 다시 묻거나 사용자 비교 양식 제출을 개발 조건으로 두지 않습니다.

운영 웹·worker·DB·프록시·도메인·큐·타이머·전역 격리 설정은 교체하지 않습니다. 운영 API로 프로젝트·계획·승인·모델 실행을 새로 만들지 않습니다. 병합·배포·PR #10 pending 변경, 새 계정·유료 API·요금제 추가, 서명키 사용·내보내기·외부 백업, ECC 활성화·새 모델 로그인 연결은 이번 자동 실행 범위에 넣지 않습니다. 기존 커플 서비스를 유지합니다.

## 2. 시작 시 고정할 것

1. 현재 브랜치·커밋·미커밋 변경과 저장소 지침을 확인하고 기존 작업을 보존합니다. PR #24의 기준과 새 변경이 있으면 차이를 기록하고 별도 작업 공간에서 시작합니다. 무조건 과거 커밋으로 되돌리지 않습니다.
2. 읽기/쓰기 UI와 그래프가 함께 쓰는 프로젝트·실행·계획 식별자, URL 전달·선택 변경 계약을 짧게 고정합니다.
3. 현재 자원과 진행 중인 작업을 확인하고 저장소의 동시 실행 제한을 지킵니다. 에이전트 수와 CPU를 많이 쓰는 브라우저·빌드 동시 개수를 구별합니다. flow의 기존 최대 두 실행 제한 등을 임의로 늘리지 않고, 부족하면 무거운 검사는 직렬 또는 기존 원격 CI로 실행합니다.
4. 원본 공개 fixture와 수정 전 핵심 실패·계산 기준을 고정합니다. 운영 데이터·인증 정보는 공개 검증 자료에 넣지 않습니다.
5. 기존 사용량 대기·재개 장치가 이번 개발 세션에도 적용되는지 확인합니다. 제품 내부 작업 큐의 자동 재개를 서버 Codex 자신의 세션 자동 재개와 혼동하지 않습니다. 연결되지 않았다면 자동 재개가 보장된다고 보고하지 않고 체크포인트와 재개 지시를 남깁니다. 이를 위해 운영 timer를 임의로 바꾸지 않습니다.

## 3. 작업 묶음과 진행 순서

| 묶음 | 실제 작업 | 넘어가는 조건 |
| --- | --- | --- |
| A. 순서형 첫 연결 | 프로젝트 찾기·실행 선택·진행·결과·승인 요청 탐색. 실제 GET 데이터, 정확한 실행 URL, 없는 대상 안내, 늦은 응답 거부 | 기존 PM·확정·승인 경로가 유지되고 읽기 탐색으로 실행·승인이 생성되지 않음 |
| B. 그래프 G1~G3 | 주요 노드 중앙·가독성·전체 보기·카메라 유지, 국소 이관/반환선·선 선택·경로 안정성, 사용법·상세·초점 보존 | 같은 fixture의 전후 계산과 실제 브라우저 조작으로 각각 확인 |
| C. 첫 통합 | A/B를 같은 후보에서 임시 실제 API에 연결. 실행 왕복·갱신·모바일·키보드 검수와 발견 결함 수정 | 첫 읽기 동선과 그래프의 핵심 계약 통과 |
| D. 쓰기 동선 재배치 | 기존 PM 대화·명세 저장·계획 확인/직접 확정·후보 결정 UI를 순서형으로 연결. 원문/한국어 읽기 유지 | 임시 DB에서 실제 기존 API 계약·권한·버전·중복 처리·대상 연결 검증 |
| E. 후보와 배포 준비 | 최종 통합 회귀·독립 검수, 미리보기·해시·웹 이미지 후보·서비스워커 갱신 시험·APK 호환 검토·적용/복구안 | 동일 최종 코드 후보의 근거와 미완료 항목을 묶어 제출 |

A와 B는 계약을 먼저 정하고 **서로 다른 파일**에서 병렬로 진행할 수 있습니다. 그래프 파일은 한 담당자가 G1→G2→G3 순서로 수정합니다. A와 D는 `app.js` 등 겹치는 파일이 많으므로 해당 파일의 작업권을 명시적으로 넘기며 동시에 편집하지 않습니다.

독립 검수 담당은 수용 조건·실패 시나리오·기존 근거 대조를 병행할 수 있습니다. 구현자가 만든 성공 시나리오만 되풀이하지 않습니다. 각각의 분기 성공을 합쳐 최종 성공이라고 부르지 않고 통합 후보를 다시 검수합니다.

## 4. D의 구체적인 보존 조건

- 자연어 목표와 실제 PM 요청 상태를 연결합니다. 고정 예시 PM 답변·실행·후보·단계 재생을 운영 데이터처럼 이식하지 않습니다.
- 대화 전송·명세 저장·계획 생성·사용자 직접 확정을 구별합니다. 기존 메시지 API에 없는 멱등 보장을 새로 있다고 설명하거나 실패한 전송을 자동 반복하지 않습니다.
- 오래된 목표·대화·하네스·실행 명세·카탈로그의 계획 확정을 거부하고 원래 digest 검증을 유지합니다.
- 중복 클릭·동시 재요청에서 같은 프로젝트나 실행·결정을 중복 생성하지 않습니다. 실제 계약이 없는 행동은 불확실성을 표시하고 원래 정책을 따릅니다.
- 후보 결정은 프로젝트·실행·계획·후보·원문 digest·만료·pending과 일치해야 합니다. 다른 프로젝트·실행·권한으로 접근하거나 오래된 대상을 확정하려는 실패도 검사합니다.
- 원문과 한국어 읽기를 구별합니다. 번역본으로 실행 필드·digest·승인 권한을 새로 만들지 않습니다. 번역 전환 후 재확인 동작을 유지합니다.
- 로그인 만료·권한 부족·서버 오류·연결 끊김·처리 결과 불확실 상태에서 입력과 다음 행동을 일관되게 보여 줍니다. 인증·CSRF·Host/Origin 검사를 완화하지 않습니다.
- 시험용 승인 결과는 임시 DB에만 남깁니다. 실제 사용자 조작이 필요한 항목은 별도로 미실시 표시합니다.

## 5. 통합 전체 검수의 범위

여기서 “전체 검수”는 이번 제품 후보의 핵심 동선과 관련 회귀, 기존 요청의 누락 점검을 뜻합니다. 무관한 저장소나 서버 전체를 재설계하는 작업은 아닙니다.

| 분야 | 확인할 내용 |
| --- | --- |
| 데이터·권한 | 프로젝트/실행/계획/후보 혼입, 늦은 응답, 없는 실행, 과거 실행에 최신 보고 재사용, 중복 생성, 원문/번역·권한 보존 |
| 사용 흐름 | 목표→PM→계획 확인·직접 확정→병렬 진행·대기/이관→보고→결정. 임시 API와 필요한 시험 응답을 사용하며 실제 모델 완료와 구별 |
| 그래프 | G1~G3, 정확한 관계 선택, 실제 드래그 문턱을 넘은 1px 왕복, 장애물 재탐색, 누락 대상 안내·닫기·초점 |
| 화면 | Light·Black × 320/390/1440px, 장문·빈 화면·대기·실패·오프라인, 키보드·확대·포커스·모바일 조작 |
| 갱신·배포 준비 | 기존 코드→새 코드의 정적 자원·서비스워커 전환, 오래된 탭·새로고침·로그아웃·캐시 정책, 이전 웹 후보로 되돌리기 |
| 요구사항 누락 | 아래 전체 목표 표에 기존 근거·이번 변경·남은 일을 연결 |

전체 목표 표에는 순서형·한국어/번역, PM 대화와 명시적 확정, 역할별 병렬 흐름·하네스, 사용량 이관·영속 대기/재개, 보고와 승인 분리, 모델 연결 현황, 도메인·TWA/APK, 서명키 복원, ECC·Archify 관련 기존 요구를 포함합니다. 이미 검증한 과거 사실은 보존하고 최신 상태를 확인하지 않은 항목은 “현재 미확인”으로 구별합니다. 누락 항목이 발견됐다는 이유로 새 모델 로그인·서명키·운영 작업까지 이번 구현 범위를 넓히지 않습니다.

개발·검수 에이전트는 기존 허용 계정·모델·한도 안에서 사용합니다. 제품 검증에서 고정 PM/CLI 응답을 쓰면 모의임을 표시합니다. 새 유료 API 호출이나 운영 PM 루프 실행을 자동 추가하지 않습니다. 계획에 필수인 최종 모델 검수가 불가능하면 다른 모델로 조용히 합격 처리하지 않습니다.

이번 영향 범위의 권한·데이터 보존 문제, 핵심 동선을 막는 기능 결함과 시각·조작 결함은 수정합니다. 새 서비스·새 권한 모델·대규모 엔진 교체가 필요한 문제는 근거와 후속안으로 남깁니다. 같은 성공 검사를 이유 없이 반복하거나 검사 수를 늘리는 것을 작업 목표로 삼지 않습니다.

## 6. 스킬과 검수 담당

기존 `ai-company-frontend`와 설치된 5개 스킬의 실제 지침을 읽고 필요한 단계에 적용합니다.

- `ponytail`: 기존 모듈·API·상태 계약을 재사용하는 단순한 구현.
- `web-design-guidelines`: 한국어 가독성·접근성·조작·초점·터치 검수.
- `property-based-testing`: 의미 있는 불변 조건과 입력·이벤트 조합, 재현 seed 보존.
- `variant-analysis`: 발견한 원인이 영향 범위의 다른 경로에도 있는지 조사.
- `gh-fix-ci`: 실패한 커밋·작업·시도·로그를 대조하고 원인을 수정. 단순 재실행 성공과 구별.

모든 스킬을 억지로 매 단계 호출하지 않습니다. 사용한 지침·적용 범위·실제 검증 결과를 구별합니다. 독립 코드 검수와 독립 시각/조작 검수는 같은 최종 후보를 대상으로 합니다.

## 7. 차단·사용량·복구 시 계속하는 방법

- 오류가 발생하면 유형·대상 작업·마지막 유효 결과·다음 가능한 작업을 기록합니다. 해당 가지가 막혀도 관련 없는 문서·코드·검사 준비는 계속합니다.
- 사용량 한도는 기존 공유 계정·역할 적격성·최종 검수 정책을 지키며 이관하거나 영속 대기합니다. 같은 계정의 모델명만 바꿔 한도가 회복됐다고 판단하지 않습니다.
- 인증·권한·격리 실패를 일반 코드 오류처럼 반복하지 않습니다. 기존 자격 증명을 출력하거나 보호 설정을 낮추지 않습니다.
- 사용자 부재 중 새 승인 없이는 할 수 없는 운영·계정·서명·실기기 단계는 그 항목만 대기로 두고 가능한 범위를 마무리합니다.
- 기존 최대 시도·시간·비용 제한을 유지합니다. 한도 확대나 무한 재시도를 하지 않습니다. 정해진 한도에 도달하면 현재 후보·검증 상태·차단 근거와 재개 지시를 영속 기록합니다.
- 작업 묶음 완료와 중요한 차단 시 안전한 코드·검사·문서를 커밋하고 초안 PR을 갱신합니다. 손상된 후보를 완료로 표시하지 않습니다. 모든 후보가 한도에 도달하면 무조건 계속 실행된다고 약속하지 않습니다.

## 8. E의 패키지·갱신 검증

웹 이미지 후보 빌드와 로컬/기존 격리 경로의 미리보기는 준비할 수 있습니다. 운영 컨테이너 교체나 새 공개 포트·도메인 연결은 하지 않습니다. 빌드 부하와 디스크를 확인하고 운영 파일·이미지를 임의 정리하지 않습니다.

서비스워커 시험은 운영과 다른 격리된 출처에서 이전 후보→새 후보 전환을 확인합니다. 운영 도메인 캐시를 시험 목적으로 비우지 않습니다. 이전 후보 복구 시 오래된 자원이 남는지도 함께 확인합니다.

최종 제품 코드 커밋에 웹 이미지 digest·정적 자원/서비스워커 버전·미리보기 파일/fixture 해시·CI/attempt/artifact·검수 결과를 연결합니다. 검수 뒤 제품 코드가 바뀌면 영향 검사를 다시 수행하고 후보 식별자를 갱신합니다. 기록만 추가한 커밋과 실제 제품 코드 커밋을 구별합니다.

기존 APK의 진입 URL·manifest·도메인 연결 계약과 새 웹의 호환성을 점검합니다. 실제 기기가 없으면 APK 조작은 미실시입니다. 기존 서명키·앱 ID를 바꾸거나 새 서명 APK를 임의로 배포하지 않습니다. 새 APK가 꼭 필요하면 필요 사유와 준비 범위를 보고합니다.

## 9. 핵심 목표 완료 후 남는 시간

핵심 통합 검증이 끝난 뒤에는 전체 목표 표에서 후속 항목의 기존 구현·증거·차이를 읽기 검수하고 우선순위를 정리합니다. 모델 연결 화면·추가 제공자 같은 범위는 필요한 데이터 계약·사용자 조작·미확인 사항을 다음 명세 초안으로 정리할 수 있습니다. 공식 지원 방식과 정책을 확인하지 않고 로그인/API 가능 여부를 단정하지 않습니다.

이 후속 조사 때문에 완료된 후보를 다시 크게 바꾸거나 핵심 검증을 미루지 않습니다. 작업과 충분한 검증이 끝나면 멈추고 인수인계를 작성합니다.

## 10. 최종 제출물과 아침 보고

1. 통합 후보 초안 PR과 제품 코드 커밋, 주요 변경 파일·설계 이유.
2. 같은 후보의 검사·CI·독립 코드 검수·실제 화면/조작 근거와 실패/재시도 이력.
3. 접근 가능한 미리보기 ZIP 또는 기존 비운영 검수 경로, Light·Black 대표 캡처, 해시.

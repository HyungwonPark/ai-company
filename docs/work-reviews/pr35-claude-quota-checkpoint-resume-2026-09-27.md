## 소스에서 확인한 제한

`scripts/review_pr_with_claude.py`의 `terminal_children_stopped`는 result 이벤트가 정확히 하나일 때만 종료를 인정한다. 이 판정은 한도 회복 시각 해석과 정산·재시도 경로에도 영향을 준다. 보고서 추출은 마지막 result, 실행 시간 추출은 첫 result를 사용하므로 여러 결과의 의미를 먼저 통일해야 한다.

현재 `--resume-quota`는 종료·정산·동일 대상 등을 확인하고 이전 시도 디렉터리를 보존한 뒤 **새 검수 시도**를 만든다. 실행 옵션에 `--no-session-persistence`가 있어 모델 세션이나 검토 진행 상태를 이어받는 기능으로 설명하면 안 된다.

`claude_control.py`는 첫 result 후 설정 조회를 보내고 그 응답 후 표준입력을 닫는다. 복수 result와 Workflow에서 설정 조회·종료 관측 시점이 적절한지도 함께 검증한다. 이는 코드상 확인이며 이번 사건의 원인을 확정한 것은 아니다.

## A. 지금 진행할 조사와 복구 준비 — 추가 모델 호출 없음

1. 이번 시도의 원본 이벤트·입력 전달 사실·설정 응답·프로세스 종료·예약·사용량·보고서와 해시를 보존한다. PR/head/base/전체 패치와 attempt/session/task 식별자를 연결한다. 비공개 원문과 계정 정보는 공개 저장소에 게시하지 않는다.
2. 두 result가 주 호출 결과와 작업 알림인지, 반복 전달인지, 서로 충돌하는 별도 결과인지 실제 설치 CLI의 이벤트 계약과 식별자로 분류한다. 첫 것 또는 마지막 것만 임의로 고르거나, 개수 조건을 1개 이상으로 완화해 통과시키지 않는다.
3. 주 프로세스와 관련 자식·Workflow 작업의 종료, 늦게 도착한 결과, 설정 조회의 시점을 확인한다. 프로세스 종료와 검수 완료를 구분한다. 안전하게 종료됐어도 검수 범위가 남으면 검수는 미완료다.
4. 사용량이 호출별 값인지 누적 스냅샷인지 대조해 중복 합산을 막는다. 저장 증거로 확정할 수 있는 것과 없는 것을 구분한다. 불명확한 사용량을 0으로 간주하지 않는다.
5. 기존 증거가 충분하면 정산·한도 대기 전환의 구체적인 복구안을 준비한다. 부족하면 필요한 증거와 다음 조사 방법을 적고 NEEDS_RECONCILIATION/UNKNOWN을 유지한다. 관측되지 않은 종료 사유·Workflow 완료를 만들어 채우지 않는다.

## B. 검수기 보완과 회귀 검증 — 비운영 후보

- 호출·세션·작업 관계를 반영한 결과 해석을 만들고, 종료 판정·한도 사유·회복 시각·사용량·보고서가 같은 해석을 사용하게 한다. 전체 원문은 남기고 정규화한 결과를 별도 저장한다.
- 같은 이벤트의 중복 전달은 확인 가능한 안정적 식별자로 처리한다. 내용이 비슷하다는 이유만으로 별도 결과를 제거하지 않는다.
- 이전 시도의 정산은 예약당 한 번만 반영하고, 중단·재실행·늦은 이벤트에서 중복 정산이나 새 계정 제한 삭제가 없는지 검사한다.
- 저장된 사건 재생과 합성 경계 검사로 주 결과+작업 알림, 중복·상충 결과, 미종료 자식, 한도 중단, 누적 사용량, 설정 조회 순서, 정산 직후 중단을 검증한다. 실제 한도를 다시 소진해 오류를 재현하지 않는다.
- 현재 PR #35 검수 대상을 계속 바꾸지 않도록 검수기 수정은 별도 후속 후보로 분리한다. PR #35에는 미완료 사유와 후속 후보 링크를 남긴다.

## C. 검수 진행을 보존하는 체크포인트

검수기를 처음부터 반복 호출하는 것으로 완료 처리하지 않는다. 검토한 범위와 남은 범위를 저장하는 경로를 함께 구현한다.

- 체크포인트에는 대상 head/base/전체 패치 해시, 검토한 파일·요구사항, 남은 범위, 지적과 근거, 다음 행동, 실제 모델·설정 증거, 시도/세션 계보와 예약·정산 참조를 기록한다.
- 적절한 검토 단위마다 유효한 진행 기록을 남긴다. 저장된 출력만으로 검토 범위를 확정할 수 없으면 미확인으로 남긴다. 임의의 토큰·달러·턴 상한을 추가하지 않으며 기존 30분 실행 제한은 유지한다.
- 같은 세션 재개는 실제 설치 CLI가 지원하는 방식과 저장 조건을 확인한 경우에만 사용한다. 현재 no-session-persistence 경로로 가능한 것처럼 표현하지 않는다.
- 같은 세션을 이어갈 수 없으면 **새 세션에 이전 체크포인트·전체 패치·남은 범위를 전달**하고 새 시도임을 기록한다. 이전 근거를 대조할 수 있어야 하며 요약만 전달해 전체 패치 검수 조건을 잃지 않는다.
- 대상 head/base/패치가 바뀌면 기존 검수의 적용 범위를 무효화하거나 변경 범위를 명시해 새 검수 대상으로 묶는다. 이전 PASS를 새 후보에 복사하지 않는다.
- 각 호출의 실제 Opus 5.5·Ultracode 적용 근거를 확인한다. Workflow 호출 관측과 결과 수집·완료를 구분한다.
- 전체 대상 검토와 지적 정리가 끝나기 전에는 부분 결과를 최종 PASS로 표시하지 않는다. 충분한 근거가 있는 최종 REVISE도 검수 완료 결과로 제출하되 PR 수용으로 처리하지 않는다.

## D. 한도 회복 후 자동 재개

1. 상태를 최소한 “종료·정산 확인 필요”, “한도 회복 대기”, “재개 가능”, “검수 중”, “검수 완료”로 구분한다. 현재 사건은 먼저 종료·정산 확인이 필요하다.
2. 재개 예약에는 공급자가 실제 표시한 회복 시각, 다음 점검 시각, 대상 버전·체크포인트·이전 예약 참조를 영속 저장한다. 5시간 sleep을 유지하지 말고 짧은 worker 실행으로 조건을 확인한다.
3. 현재 사건은 2026-09-28 02:00 KST 전 새 모델 호출을 하지 않는다. 이후에도 이전 실행·관련 자식 종료, 한 번의 정산, 계정의 현재 제한, 동일 대상·체크포인트, 공용 장부 예약, 중복 실행 잠금이 모두 맞을 때만 재개한다.
4. 조건이 충족되면 기존에 승인된 검수 범위 안에서 남은 작업을 이어간다. 같은 범위의 단계마다 다시 승인을 묻지 않는다. 다시 한도에 걸리면 새로 관측한 회복 시각을 저장한다. 회복 시각이 없으면 읽기 전용 확인을 예약하고 추측한 시각에 모델을 반복 호출하지 않는다.
5. 한 작업에 활성 시도는 하나만 허용한다. 타이머 중복 실행·worker 재시작·한도 반복에서도 원래 진행과 시도 계보를 유지한다. 오류를 무조건 시간 대기로 바꾸지 않는다.
6. 기존 검수 실행 경로에 예약 재개가 가능한지 먼저 확인한다. PM·번역 worker 전체를 켜거나 구형 quota 호출 경로를 우회해 검수를 실행하지 않는다. 새 서비스·타이머가 필요하면 검수 전용의 작은 적용안을 준비한다.
7. 상태 변화가 없으면 반복 보고하지 않는다. 재개·새 지적·완료 또는 마스터 결정이 필요한 장애를 보고한다. 사용자 취소 시 재개 예약을 중단한다.

## E. 이번 작업 묶음과 완료 기준

A~D의 조사·비운영 구현·관련 검사·독립 검수·CI·고정 패키지·적용/복구안까지 한 묶음으로 진행한다. 한도 대기 동안 가능한 비운영 작업은 계속한다. 원인 확인에 필요한 범위를 넘어 PR #35 제품을 다시 설계하지 않는다.

신뢰 경로 설치본 변경·현재 미정산 예약의 정산/계정 상태 쓰기·새 타이머 설치가 기존 승인 범위를 벗어나면 실제 변경 파일·대상 예약·검증 근거·실패 복구를 고정한 뒤 필요한 추가 범위만 한 번 요청한다. 이전 한 파일 복원 승인을 모든 후속 변경의 포괄 승인으로 확대하지 않는다. 이미 승인되고 검증된 동일 범위는 재승인 없이 진행한다.

제출할 결과:

- 두 result의 의미와 종료·사용량 판단 근거 또는 남아 있는 구체적 불확실성.
- 저장 원문 재생의 실패→수정 성공, 한도 중단→worker 종료→재기동→남은 검수 재개의 검사. 모의·실제 범위를 구분.
- 새 세션/동일 세션 여부, 검토 완료·남은 범위, 체크포인트·시도 계보와 중복 방지 증거.
- 현재 사건의 정산 여부, 계정 제한, 다음 점검·재개 예정 시각과 차단 사유.
- 고정 대상의 실제 Claude 최종 보고·설정·전체 검토 범위·종료·정산을 확인한 뒤에만 최종 검수 완료로 제출.

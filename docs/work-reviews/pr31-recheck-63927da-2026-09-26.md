## R31-4b — 시작한 두 번째 자동 수정의 제한 회복 재개가 막힘

**P2 · 평가 실행기 · 실제 평가 전 수정**

위치: [evaluate_pm_behavior.py](https://github.com/HyungwonPark/ai-company/blob/63927dad0ac38e9417dca4263b1553a2aeede402/scripts/evaluate_pm_behavior.py)의 global_usage() 175–193행과 run_case() 327–340행.

global_usage()는 시작한 pm-revise 작업을 각각 한 번 센다. 두 번째 수정이 이미 호출됐다가 quota로 종료되면 repairs=2가 맞다. 그러나 run_case()의 다음 조건은 **새 수정 생성과 기존 수정의 재개를 구분하지 않는다**.

```python
if calls >= MAX_CALLS or needs_repair and repairs >= MAX_REPAIRS or next_timeout <= 0:
    return {'state': 'budget_wait', ...}
```

재현 조건:

1. 첫 번째 자동 수정이 완료됐다.
2. 두 번째 pm-revise 작업은 이미 시작했으며, 동일 session/job의 한도 종료·정산이 확인됐다.
3. 현재 계획은 auto_revision_attempt=1, needs_revision/automatic이다. 해당 두 번째 작업은 WAITING_PM, 세션은 WAITING_QUOTA다.
4. reset이 지났고 실제 장부에서 같은 계정의 예약 가능성을 확인했다. 종료 미확인 호출은 없다.
5. 호출·시간 예산은 충분하지만 평가 실행기는 repairs=2만 보고 같은 작업을 막는다.

Work 재현 출력:
```text
calls=2, repairs=2, reserved_seconds=2
next_call_timeout_seconds=30
quota_expired=true
shared_account_capacity_available=true
state=budget_wait
model_ticks=0
```

이 재현은 **고정 후보 평가 함수·실제 SharedCallLedger·SQLite 집계**를 사용한다. PM overview/worker와 사례 예산 설정은 명시적으로 모의했다. 실제 모델, 전체 Automation, 운영 상태를 재현한 결과는 아니다. 임시 파일 외에는 변경하지 않는다.

[휴대 가능한 진단](repros/pr31-second-repair-resume-63927da.py)을 아래처럼 실행한다.

```bash
python docs/work-reviews/repros/pr31-second-repair-resume-63927da.py /path/to/63927da-checkout
```

이 스크립트의 성공 종료는 **현재 결함을 확인했다**는 뜻이다. 수정 후에도 같은 결함 출력이 나와야 하는 회귀로 복제하지 않는다.

## 서버 수정 지시와 수용 조건

기존 PR #31에서 R31-4b만 최소 수정한다. 이미 해결한 R31-1~4를 다시 구현하거나 UI·프레임워크·모델 범위를 늘리지 않는다.

1. **새 자동 수정 작업을 시작하는 경우**와 **이미 횟수에 반영된 동일 수정 작업을 재개하는 경우**를 안정된 task/job/session·계획 연결·장부 시작 사실로 구분한다.
2. 두 번째 수정의 quota·허용된 일시 오류 재개는 새 수정 횟수로 세지 않는다. 기존 세션/시도 계보와 사용량을 보존하며 호출 횟수·실행시간·계정 cooldown·호스트 슬롯·종료 확인 조건은 계속 검사한다.
3. 새로운 세 번째 수정은 계속 차단한다. `>=`를 `>`로 바꾸거나 수정 횟수 상한을 제거하는 방식으로 해결하지 않는다.
4. 횟수에 반영된 작업인지 증명되지 않는 경우, 다른 계획/작업으로 바뀐 경우, 종료·정산이 불확실한 경우에는 새 호출을 막는다. 원래 로그 삭제·새 trial-root·빈 커밋·새 세션 발급으로 우회하지 않는다.
5. 같은 입력으로 다음 통합 회귀를 제출한다.
   - 첫 수정 완료 → 두 번째 수정 quota 종료 → 프로세스/실행기 재시작 → reset 회복 → **동일 두 번째 수정이 한 번 재개** → 재검수.
   - repairs=2에서 아직 시작하지 않은 **세 번째 수정은 차단**.
   - reset 전, 미정산/미확인, 호출/실행시간 예산 소진은 차단.
   - 동시 재개는 한 worker만 실행, 중복 정산과 수정 횟수 추가 없음.
   - 기존 결과가 이미 저장됐으면 reconcile만 하고 모델을 중복 호출하지 않음.
6. 이 경계의 최초 실패→수정 성공, 관련 회귀, 독립 검수, 새 최종 HEAD CI를 제출한다. 실제 공급자 한도를 소진하여 재현하지 않는다.
7. 새 후보의 설치 파일·두 unit·비공개 설정 키·카탈로그 보존·과거 사용량 및 제한 대조·신규 장부·복구 기준을 고정한다. 이후 해당 운영 연결 범위만 승인 요청한다.

## 적용 범위와 보존 조건

다음 운영 연결 후보의 범위는 기존대로 worker 코드, PM·조정기/번역 **두 서비스 유닛**, 기존 카탈로그 경로를 보존한 비공개 설정, 과거 사용량·제한을 대조한 공용 장부, 신뢰 경로의 runner·relay·shared_calls.py다. 공개 웹 이미지 교체·추가 서비스·병합·서명키 작업은 포함하지 않는다.

- 대조가 맞지 않거나 미확인 호출이 있으면 새 호출을 막고 적용을 멈춘다.
- 신규 공유 예약 전의 복구와 신규 예약/결과가 생긴 이후의 조정 절차를 구분한다. 이후에는 구형 worker 단순 재시작이나 과거 DB 복원으로 되돌리지 않는다.
- 모든 관리 호출자의 동일 장부 참여와 계정 제한 회복을 확인한 후 실제 Astra E1–E6·Claude 검수를 수행한다. Claude PASS와 실제 PM 판단 평가는 별개다.
- 기존 USD·턴 제한 제거, 30분 검수 종료, 동일 HEAD 중복 방지, 순서형, 커플 서비스·운영 기록·PR #10 pending을 유지한다.
- 시험 UI와 직접 조작 준비 전에는 마스터에게 현재 운영 APK에서 새 흐름을 확정하라고 요청하지 않는다.

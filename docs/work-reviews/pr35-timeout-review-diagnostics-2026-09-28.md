# PR #35 수동 검수 시간 초과와 후속 진단·보완 지시

기준: 2026-09-28 17:48 KST 사용자 전달 보고 · Work PM 소스 대조 · v1.0

## 현재 판정

**실제 Claude 검수 한 건은 실행됐으나 30분 제한으로 중단됐고 최종 검수는 미완료다. 현재 새 예약과 연결 계정은 UNKNOWN이며 재호출하지 않는다. 다음 작업은 추가 검수 호출 없이 종료·사용량 증거와 검수기 완료 계약을 진단하고 필요한 최소 보완·적용안을 준비하는 것이다.**

GitHub에서 제품 대상 PR #35 `1d54d3a0ea5a21c7c2dc588f824c6567231829b4`와 검수기 후보 PR #36 `7ab76818758ef7cfa4828fd3578217da1d1dc257`가 유지됨을 확인했다. [직전 설치·정산 완료 보고](pr36-applied-manual-review-ready-2026-09-28.md)는 이전 예약에 대한 사실로 보존한다. 그때의 READY와 정산 완료를 이번 새 예약의 현재 상태로 적용하지 않는다. PR #36의 기존 R36-1~4 해결을 이번 timeout만으로 취소하지 않는다.

## 소스로 확인한 경계

Work가 읽은 runner·tick·claude_control·shared_calls의 SHA-256은 기존에 검증한 7ab7681 패키지 4파일과 모두 일치했다. 아래는 코드 동작 확인이며 이번 서버 실행의 상세 원인 확정과 구분한다.

1. **timeout은 quota와 다르다.** runner의 `invoke()`가 시간 초과를 기록하면 최종 처리에서 자동 정산 대신 `shared.uncertain()`으로 간다. 현재 `effective_receipt()` 사후 기록과 `quota_resume_verified()`, 계정 조정은 quota·429·회복 시각 증거 전용이다. 이번 timeout에 기존 quota 재개 명령을 그대로 쓰거나 quota로 재분류하지 않는다.
2. **중간 완료 인정이 종료 후 설정 증거에 묶여 있다.** `checkpoint_from_events()`는 before/after 설정과 응답 모델 검증이 모두 통과해야 이번 시도의 진행 선언을 완료로 인정한다. relay는 활성/background 작업이 없는 result 이벤트에서 after 조회를 보낸다. result 이후 작업 완료 알림만 온 경우에는 그 알림 자체로 after 조회를 시작하지 않는다. 따라서 종료 후 설정이 없으면 올바른 중간 선언이 있어도 이번 완료 인정이 0이 될 수 있다. 읽기 관측과 완료 인정의 구분은 유지한다.
3. **Workflow 정상 완료 형태의 처리 범위를 확인해야 한다.** 현재 `result_interpretation()`은 task_started를 포함한 단일 result를 거부하고, 두 result의 경우 마지막 429로 끝나는 한정 형태를 허용한다. 최종 검수 완료는 single 형태만 허용한다. 종료 형태만 정상 완료로 바꾼 합성 Workflow 입력도 거부되는 동작을 확인했다. 실제 CLI 2.1.283의 정상 Workflow 이벤트가 이 형태인지, 이번 30분 중단과 관련 있는지는 저장 원문으로 추가 확인해야 한다.
4. **시간 초과와 검수 불충분 사유를 함께 보존해야 한다.** 결과 요약의 `incomplete_reason`이 뒤에서 `review_scope_unverified`로 덮일 수 있다. 원래 timeout과 최종 설정 미검증·범위 미검증을 별도로 대조한다.
5. **종료 확인·비용 확인·계정 해제는 별개다.** 프로세스 그룹 종료만으로 모든 Workflow/하위 실행 종료가 입증되는 것은 아니다. 장부의 `settle()`는 비용 null과 cost_unknown을 지원하지만 기존 UNKNOWN 계정을 자동 해제하지 않으며, 동일 정산을 다른 값으로 다시 기록하는 것도 거부한다. 이 기능만으로 이번 timeout의 사후 정산·재개 경로가 준비됐다고 간주하지 않는다.

좁은 합성 재현에서는 동일한 성공 Read와 진행 선언에서 after 설정만 제거하면 읽기 관측은 유지되지만 완료 인정은 1 → 0이 됐다. 이는 방어 조건의 동작을 확인한 것이며, 해당 조건을 제거하거나 과거 완료를 소급 인정하라는 뜻이 아니다. 이번 원문에 진행 선언이 실제로 있었는지는 미확인이다.

## 서버의 다음 작업 묶음

다음은 기존 기록·복제 환경을 이용한 비운영 조사·재현·필요한 코드 보완·검사·문서·패키징 범위다. 관련 작업을 한 번에 처리하며 파일별로 착수 승인을 반복 요청하지 않는다.

1. **종료와 시간 흐름:** 원본을 보존하고 별도 복제본에서 시작·마지막 정상 응답·Workflow 시작/종료·설정 조회·진행 선언·30분 종료 시각을 연결한다. 대기한 대상과 마지막으로 진행한 작업을 표시한다. 실행기·CLI·하위 작업의 식별자와 현재 종료 상태를 각 증거에 묶고, 미확인은 미확인으로 남긴다.
2. **사용량과 정산 준비:** USD 4.46의 출처·포함 범위를 확인한다. 부모/하위 사용량이 별도 값인지 이미 누적된 값인지 확인해 중복 합산을 막는다. 저장 기록에서 총사용량을 복원할 수 없으면 관측 부분 비용과 총비용 미확정을 분리한다. 0이나 4.46을 임의 총비용으로 넣지 않는다. 종료가 확인돼도 비용이 불명인 경우의 정직한 기록 방식·후속 보완·중복 정산 방지를 포함해 timeout 한 건의 정산/계정 복구안을 준비한다.
3. **완료 계약 진단:** REVIEW_PROGRESS_JSON의 존재·형식·HEAD/패치·읽기와의 연결, before/after 응답, Workflow별 이벤트 순서를 대조한다. 진행 선언이 최상위 assistant 텍스트인지 자식 작업 결과에만 있는지도 확인한다. 마지막 result 이후 작업 완료/목록 비움·추가 result·after 요청 여부를 시간순으로 연결한다. 중간 선언 부재, 형식 거부, 설정 증거 부재, Workflow 미종료, 정상 이벤트 형식 미지원 중 확인된 원인을 구분한다. 정상 Workflow 기록이 있으면 기존 성공 기록을 사용하고 진단용 모델 호출을 추가하지 않는다.
4. **재현과 최소 보완:** 확인된 결함이나 필요한 미지원 경로만 고정 후보와 분리된 후속 브랜치/PR에서 보완한다. 정상 Workflow 종료·quota·timeout의 증거 조건을 분리하고, 관측 진행·검증된 부분 완료·최종 판정을 구분한다. 중간 완료를 검증하려면 해당 범위와 설정·모델 증거를 안전하게 연결하는 방안을 제시하며 최종 after 요구를 단순 삭제하지 않는다. 모델의 자기 주장·파일 읽기만으로 완료를 인정하지 않는다.
5. **관련 검증·적용안:** 모델을 모의 처리한 좁은 재현에서 정상 완료, 하위 작업 미종료, 설정 증거 누락, 중간 선언 오류, 부분 비용, 원본 변조, 중복 정산을 확인한다. 기존 quota 복구와 고정 패치·원본 계보 조건을 보존한다. 안정화한 후보의 필수 검사·CI·변경 해시·설치 차이·복구안을 함께 제출한다. 실제 Claude 검수가 불가능하면 필수 검수 대기로 명시한다.

실제 원문 진단에서 코드 결함이 확인되지 않은 항목은 추정으로 남기고 불필요한 기능을 만들지 않는다. 합성 입력을 근거 없이 공급자의 정상 계약으로 채택하지 않는다. 준비 결과에는 실제 확인한 원인과 아직 모르는 원인, 이 보완이 다음 검수를 완료 가능하게 만드는 근거를 구분한다.

## 이번 범위와 완료 조건

- 추가 모델·시험 호출·tick·자동 재시도는 실행하지 않는다. 진단을 위해 세션을 초기화하지 않고, 30분 제한 확대나 모델/Ultracode 하향을 임의 해결책으로 적용하지 않는다.
- 이번 수동 검수 요청에 포함된 종료·증거 기반 정산·보고 승인은 유지한다. 기존 지원 경로와 그 승인 범위 안에서 정산 조건이 입증된 작업에 반복 승인을 요구하지 않는다. 다만 현재 quota 전용 경로를 timeout에 전용하거나, 새로운 timeout 사후 처리·계정 UNKNOWN 해제·신뢰 코드 설치까지 승인된 것으로 해석하지 않는다. 우선 비운영 진단·복제 재현으로 지원 범위와 증거를 확인하고 필요한 추가 운영 변경만 대상·영향·복구안과 함께 한 번에 확인받는다. 이번 진단 지시 자체가 운영 권한을 넓히지는 않으며 실제 검수 재호출도 기존 별도 수동 요청 조건을 따른다.
- 원본 receipt/events/checkpoint·비공개 결과·이전 정산·현재 UNKNOWN·과거 E2·두 worker 중지·기존 타이머·서비스·PR #10 pending을 보존한다. 원본 재작성, 새 ID로 중복 제한 우회, 과거 DB 복원은 하지 않는다.
- 결과는 실행 시간 흐름, 모든 관련 작업의 종료 근거, 사용량의 확인 범위, 완료 인정 실패 원인, 재현/보완/검사 결과, 정산·적용/복구안, 다음 호출의 선행 조건으로 짧게 보고한다. 새 코드 검수 대상과 PR #35 고정 검수 대상을 구분한다.

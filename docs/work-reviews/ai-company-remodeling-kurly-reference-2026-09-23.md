# AI Company 작업실 재설계 — 컬리 글 검토와 적용 제안

작성일: 2026-09-23 · 버전: 1.0 · 상태: 설계 제안, 구현·배포 승인 아님

## 1. 결론

초보자용 작업실 재설계에 참고한다. 다만 개발자가 많은 세션을 직접 관리하는 사용법을 초보자에게 그대로 요구하지 않는다. 마스터는 PM과 목표·범위·완료 조건을 정하고, 승인과 결과 확인에 집중한다. 역할별 병렬 작업은 보이되 세션 운영은 시스템이 맡는다.

기존 `ai-company-graph-ui-review-spec-2026-09-23.md`의 가독성·선택·상태 유지 검수 기준은 보존한다. 그 문서는 기존 그래프의 결함 수정 기준이며, 이 문서는 제품 전체 흐름과 화면 재설계의 보충 제안이다. 기존 기준을 폐기하거나 제품 코드를 이미 수정했다는 뜻이 아니다.

원문 요약: 저자는 외부 지식 기록·검색, 사전 계획, 의존성에 따른 구현 병렬화(Task DAG), 발견한 문제의 분리 조사(Branch Hunt), 구현·검증 반복(Ralph Loop), 독립 세션과 중앙 결과 수집을 설명한다. 반복 실패에는 중단 조건을 둔다.

이하 내용은 원문을 복제한 설계가 아니라, 우리 프로젝트의 기존 요구와 검수 결과를 바탕으로 작성한 적용 제안이다. 원문의 처리 시간·세션 수를 우리 제품의 성능 목표나 보장으로 사용하지 않는다. 도구별 하위 에이전트의 컨텍스트 처리 방식도 같은 것으로 가정하지 않는다.

## 3. 사용자에게 보여줄 제품 구조

| 위치 | 사용자 질문 | 우선 표시할 내용 |
| --- | --- | --- |
| 프로젝트 | 어디서 이어 하나요? | 프로젝트 이름, 마지막 진행, 지금 필요한 행동, 새 프로젝트 |
| 계획 | 무엇을 어떻게 만들 건가요? | PM 대화, 확정 사항·미정 사항, 역할과 완료 조건, 계획 확정 |
| 진행 | 지금 누가 무엇을 하나요? | 짧은 상황 요약, 업무 흐름, 역할별 담당, 구체적인 대기 이유 |
| 승인 | 제가 무엇을 결정해야 하나요? | 요청 대상, 이유, 영향·비용, 승인/거절 후 결과 |
| 결과 | 무엇이 완성됐나요? | 실행 가능한 결과물, 변경 사항, 검증 근거, 남은 제약, 수정 요청 |

계획·진행·승인·결과는 선택한 프로젝트 안의 화면이다. 프로젝트 이름과 현재 단계는 이동해도 보존한다. 결과물을 찾으려고 긴 PM 대화를 거슬러 올라갈 필요가 없게 한다.

AI 연결은 공통 설정에서 관리하고, 계획에 실제 연결이 필요할 때 안내한다. 목표를 적기 전에 모든 모델·추론·인증 설정을 끝내도록 강요하지 않는다. 실제 로그인/API 연결 기능의 구현은 별도 계약·권한 검토 후 진행한다.

## 4. PM과 계획을 정하는 방식

- 목표부터 받는다. 처음부터 기술 항목을 모두 입력하는 양식을 내밀지 않는다.
- PM은 기존 코드·기록에서 알아낼 수 없는 중요한 질문을 소수씩 묻는다. 작은 작업에도 고정된 장시간 인터뷰를 강제하지 않는다.
- 대화 옆이나 아래에 ‘확정한 내용 / 아직 정할 내용 / 완료 기준’을 갱신한다. AI의 추정은 확정 사항과 구별한다.
- 초보자에게 DAG·브랜치 전략을 선택하게 하지 않는다. PM이 작업 분해와 병렬 실행 방식을 제안한다.
- 계획 확정 화면에는 결과물, 역할, 작업 범위, 금지 사항, 예산 상한, 검증 기준을 요약한다. 사용자의 명시적 확정 전 개발 실행을 시작하지 않는다.
- 실행 중 범위·예산·권한이 커지는 변경은 계획 변경으로 표시한다. 원래 승인 범위 밖 작업을 자동 확정하지 않는다.

## 5. 그래프의 의미부터 분리한다

### 5.1 기본 화면: 업무 흐름

기본 노드는 모델 이름이 아니라 실제 할 일로 표시한다. 예를 들어 ‘Astra 개발자’만 쓰는 대신 ‘로그인 화면 만들기’를 제목으로, ‘화면 개발 · Astra’를 담당 정보로 표시한다. 이는 문구 예시이며 실제 생성된 업무·배정 정보를 사용해야 한다.

- 역할별 영역을 두어 병렬 작업이 드러나게 한다. 작업 중심으로 바꾼다고 회사처럼 역할을 나누려는 기존 요구를 없애지 않는다.
- 기본 선은 선행 작업과 결과물 전달 등 현재 진행을 이해하는 데 필요한 관계를 표시한다. 모든 세션 메시지를 기본 선으로 그리지 않는다.
- 연결선이나 작업을 선택하면 출발·도착, 필요한 결과물, 기다리는 이유, 실제 전달 증거를 확인한다.
- 계획상 예정된 연결과 이미 발생한 전달은 시각적으로 구별한다.
- 완료 작업 개수와 제품 완성도를 동일시하지 않는다. 범위가 바뀌면 분모·기준 변경을 표시하고, 근거 없는 진행률을 만들지 않는다.

### 5.2 보조 화면: 팀과 실행 기록

- ‘팀’에서는 PM·개발·검사·독립 검수·최종 검수 역할과 배정된 모델을 본다.
- ‘기록’에서는 실제 전달, 담당 이관, 재시도, 수정 반환의 시간순 내역을 본다. 기본 업무 흐름에 이 모든 선을 중첩하지 않는다.
- 모델이 바뀌어도 같은 업무는 같은 업무로 남는다. 업무 ID·역할 ID와 실행 시도·세션 ID를 구별한다.
- 조사 중 발견한 새로운 업무는 담당 이관과 구별한다. 필요한 경우 별도 작업 노드로 제안하고 범위·의존성·승인 필요 여부를 표시한다. 모든 새 분기를 이관 이력으로 숨기지 않는다.
- 사용자가 이관 이력을 열면 이전 담당, 새 담당, 이유, 이어받은 결과물을 확인할 수 있어야 한다. 보기에서 단순화했다고 원본 이력을 삭제하지 않는다.
- 원본 자료가 역할 수준뿐이라면 화면이 작업 단위를 임의로 만들어내지 않는다. 필요한 조회 명세의 추가 여부부터 검토한다.

### 5.3 반복 수정과 의존성을 혼동하지 않는다

작업의 선행 조건과 실제 발생한 수정 이력은 다른 정보다. 의존성 그래프를 채택한다면 선행 조건의 순환을 검사한다. 수정 반환은 같은 작업의 새 시도나 명시적인 후속 작업으로 기록하고, 표현 규칙을 정한다. 화면에서 선을 지운 것만으로 실제 실행 의존성이 해결됐다고 판단하지 않는다.

처음 가운데 배치, 읽을 수 있는 크기, 정확한 선 선택, 도움말 유지, 1px 왕복 안정성은 기존 그래프 검수 기준을 이어받는다. 새 표현 방식 때문에 필요 없어지는 검사도 근거와 대체 검사를 제시해야 한다.

## 6. 대기·복구·보고를 사람이 이해하도록 표현한다

화면에는 대기 이유와 다음 행동을 함께 표시한다.

| 실제 상태 | 화면 표현의 방향 | 시스템 측 확인 조건 |
| --- | --- | --- |
| 사용자 결정 필요 | 무엇을 확인해야 하는지와 해당 화면 버튼 | 유효한 승인 요청과 현재 계획 연결 |
| 선행 작업 대기 | 어떤 결과가 도착하면 시작되는지 | 실제 작업 의존성·필요 결과물 |
| 사용량 한도 대기 | 기다리는 대상과 확인 가능한 재개 예정 | 공급자가 제공한 정보 또는 명시된 추정 |
| 담당 변경 | 같은 일을 다른 담당자가 이어받는 이유 | 실제 이관 성공·현재 유효한 담당 |
| 반복 검증 실패 | 실패 내용, 자동 수정 횟수, 필요한 결정 | 검증 로그와 중단 정책 |

‘목표가 정체됨’ 하나로 모두 표시하지 않는다. 확인되지 않은 재개 시각이나 진행 상황은 만들지 않는다.

중앙 결과 수집은 사용자에게 모든 메시지를 읽히는 방식이 아니라 PM 요약·관련 근거·필요한 결정으로 표현한다. 그러나 오류와 미검증을 요약 과정에서 숨기지 않는다. 사용자와 직접 대화하는 주체는 PM으로 유지하되, 사용자는 개별 역할의 근거를 열람할 수 있다.

## 7. 운영 엔진에서 별도로 점검할 사항

아래는 이번 글을 계기로 점검할 항목이다. 현재 제품에 없다고 단정하지 않으며 이미 구현·검증된 기능은 재사용한다.

1. **명세에 따른 작업 투입:** 선행 결과가 준비된 작업만 시작하는지, 완료 보고에 필요한 검증 증거가 있는지 확인한다.
2. **문제 조사 분리:** 발견한 문제를 독립적으로 조사할 수 있되 중복 이슈·파일 충돌·범위 확대를 관리한다. 새 작업이 기존 승인 범위 밖이면 재승인 대상으로 둔다.
3. **한도와 자원 관리:** 같은 계정의 한도를 공유하는 모델 사이를 옮기는 것을 한도 해결로 취급하지 않는다. 가능한 후보가 없으면 영속 대기하고 독립 작업만 계속한다. PM의 사용량이 소진돼도 승인된 범위의 진행·대기·보고 상태는 모델 추론 없이 보존돼야 한다.
4. **제한된 자동 수정:** 작업별 시간·비용·반복 상한을 둔다. 인증·격리·승인 문제는 일반 코드 실패처럼 반복 실행하지 않는다. 특정 글의 재시도 횟수를 모든 실패에 그대로 적용하지 않는다.
5. **결과 수집의 신뢰성:** 중복·늦은 결과, 보고 없이 종료된 작업을 구별하고 같은 작업의 유효한 결과를 한 번만 반영하는지 확인한다.
6. **이관용 기록:** 확정된 결정, 범위, 완료 기준, 현재 산출물, 실패 이유와 근거를 이어받는다. 요약은 원본 승인과 검증 기록의 대체물이 아니다.
7. **최종 검수 정책:** 역할별 모델·추론 조건을 담당 이관 과정에서 조용히 완화하지 않는다. Astra 최종 검수가 필수인 계획에서는 다른 모델의 검토로 해당 관문을 통과 처리하지 않는다. 정책 변경이 필요하면 별도 승인 대상으로 둔다.

작은 서버에서 많은 세션을 동시에 실행할 수 있다고 이 글만으로 판단하지 않는다. 현재 자원과 동시 실행 부하를 별도로 측정한다. 당장은 새로운 검색 인프라나 오케스트레이터 설치를 UI 재설계의 선행 조건으로 만들지 않는다.

## 8. 프로젝트 기억과 검색의 도입 순서

첫 단계는 기존 프로젝트 기록을 정리해 출처와 연결하는 것이다. MD 결정 기록, 승인된 계획, 검증 근거, 사건 기록을 각각 식별하고 PM이 필요한 자료를 참조하게 한다. 의미 검색이 실제로 필요한지 확인한 뒤 검색 도구를 검토한다. Obsidian·QMD 설치 자체가 제품 목표는 아니다.

기억의 기본 단위는 ‘모델이 말한 내용’이 아니라 출처와 상태가 있는 기록이다. 사용자 확정, 검증됨, 제안, 폐기됨을 구별하고 오래된 결정의 대체 관계를 남긴다. 향후 상용화 시 다른 사용자의 프로젝트를 검색 결과나 모델 입력에 섞지 않는 요구를 별도로 검증한다. 로컬 검색을 사용해도 그 결과를 외부 모델에 전달하는 단계는 별도의 데이터 흐름이다.

## 9. 구현 전에 검수할 시안

제품과 분리된 클릭 가능한 시안에서 다음 한 사이클을 먼저 확인한다.

1. 처음 들어온 사용자가 프로젝트를 만들고 목표를 적는다.
2. PM 질문에 답하고 확정 내용과 미정 사항을 구별한다.
3. 본인이 계획을 확정한 후에만 실행 단계로 넘어간다.
4. 역할별로 병렬 작업 중인 내용과 기다리는 작업을 구별한다.
5. 담당 이관이 일어나도 같은 일을 계속 보고 있음을 이해한다.
6. 승인이 필요한 항목을 찾아 영향과 범위를 확인한다.
7. 결과물을 열거나 내려받고, 미완료·미검증을 확인한다.

모든 시안 데이터와 실행은 예시라고 표시한다. 실제 모델 호출·승인·배포로 연결하지 않는다. 초보 사용자 관찰에서 막힌 위치와 도움을 받은 횟수를 기록한다. 자동 검사는 화면 기능을 확인할 수 있지만, 사람이 쉽게 이해했다는 증거를 대신하지 않는다.

PC·모바일에서 동일 목표로 확인하고, 현재 단계·다음 행동·대기 이유를 사용자가 자신의 말로 설명할 수 있는지 검수한다. 화면 합격 후에 실제 조회 데이터와의 연결 및 필요한 최소 명세 변경을 설계한다.

## 10. 다음 서버 작업의 범위

다음 구현 지시는 ‘새 도구 설치’가 아니라 다음 산출물 순서로 작성한다.

1. 현재 기능 재사용 목록과 확인이 필요한 차이 목록.
2. 프로젝트→계획→진행→승인→결과의 화면 구조와 상태별 문구.
3. 업무 흐름·역할 배치·실행 이력을 구별한 클릭 가능한 시안.
4. 초보자 조작 검수와 수정 기록.
5. 검수된 시안의 제품 연결 계획 및 필요한 조회 명세 변경안.

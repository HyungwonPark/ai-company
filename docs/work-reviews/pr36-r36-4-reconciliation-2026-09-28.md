# PR #36 R36-4 · 사후 정산 뒤 수동 재개

이번 후보는 **비운영 코드와 적용 준비**다. PR #35의 고정 대상은 `1d54d3a0ea5a21c7c2dc588f824c6567231829b4`, 패치 SHA-256은 `87bf1835f73f9ff95cd83a0219438fd3c4d4d9bb09199942d83a561b76d9e71b`이다. R36-1~3과 이전 원문·실패 기록은 그대로 둔다.

## 원인과 수정

이번 저장 형식에서 `receipt.json`·`interpretation.json`은 호출 종료 시 정산 이벤트 `null`을 기록했다. 사후 정산은 원본을 덮어쓰지 않고 `reconciliation.json`에 새 이벤트를 묶는다. 기존 재개 검사는 이 새 이벤트를 원본 `interpretation.json`의 `null`과 비교해 `NEEDS_RECONCILIATION`으로 차단했다.

`effective_receipt`가 원본 정산값과 사후 정산값을 구분해 전달하도록 수정했다. 재개 검사는 **원본 interpretation ↔ 원본 receipt**의 이벤트·체크포인트·예약 연결을 확인하고, 별도 사후 정산 증거 ↔ 실제 장부의 이벤트·예약·분류·회복 시각을 확인한다. 원본 비교나 장부 비교를 생략하지 않는다. 이전 두 결과의 종료 분류, 모델 설정 판정, 체크포인트 계보는 변경하지 않았다.

## 검증 경계

- 현재 형식의 UNKNOWN 시도 → 임시 장부에서 한 번 정산 → 출처 해시에 묶인 사후 기록 → 계정 제한 조정 → tick의 **검사 함수만** READY 확인 → 모의 실행기에서 새 예약 한 건·검수 완료를 통합 검사했다. 수정 전 검사는 `NEEDS_RECONCILIATION`으로 실패했고 수정 후 통과했다. 중복 정산에서 사용량을 다시 더하지 않는 것도 확인했다.
- 출처 receipt 해시·예약 번호·정산 이벤트·회복 시각 불일치, 원본 interpretation/체크포인트 변경, 미정산 계정과 새로운 UNKNOWN 제한, 더 늦은 cooldown은 각각 재개를 차단했다.
- 서버의 저장 원문과 운영 장부의 **복제본**을 읽기 전용 원본과 대조했다. 복제본에서는 정산 전 `NEEDS_RECONCILIATION`, 정산 후 계정이 여전히 UNKNOWN이면 `NEEDS_RECONCILIATION`, 정확한 제한 조정 후 READY였다. 원문 13파일의 읽기 사실과 완료 인정 0파일·남은 13파일을 유지했다. 복제본의 정산은 운영 장부에 반영하지 않았다.
- 관련 Python 검사 39개가 통과했다. 별도 정적 검수자는 변경된 실행기·tick·두 검사 파일에서 추가 차단 결함을 찾지 못했다. 검수 범위는 코드·모의 검사이며 실제 relay/모델·운영 장부는 실행하지 않았다. 최종 후보의 필수 CI는 PR의 최종 HEAD에서 확인한다. Claude 코드 검수와 실제 PR #35 PASS/REVISE는 **미완료**다.

## 후속 적용·복구안 — 이번에는 실행하지 않음

1. 적용 직전에 패키지·신뢰 설치본·전환 기록·PR #35 HEAD/base/패치·원문 해시·예약·계정·다른 진행 중 호출을 비공개 manifest와 대조한다. 새 제한이나 차이가 있으면 중단한다. 두 worker 중지, 기존 quota 타이머와 과거 E2 UNKNOWN을 유지한다.
2. 변경 전 `runner.py`, `tick.py`, 전환 기록을 비공개 백업하고, 동일 해시의 `claude_control.py`·`shared_calls.py`는 그대로 둔다. 새 runner·tick만 원자적으로 교체하고 전환 기록의 runner 해시를 갱신한다. 설치본 4파일과 패키지를 다시 대조한다. 검수 전용 타이머는 설치하거나 활성화하지 않는다.
3. 종료·자식 작업·최종 누적 사용량·공급자 회복 시각을 원문으로 확인한다. 다른 예약이나 더 늦은 계정 제한이 없을 때만 이 예약을 장부에서 **한 번** 정산한다. 원본 receipt/interpretation/checkpoint/events를 바꾸지 않고 출처 해시·예약·이벤트·reset에 묶인 사후 기록을 별도로 쓴다. 장부와 대조한 한정 계정 조정 뒤 검사 함수로 준비 상태를 확인한다. 이 단계에서도 tick과 모델은 호출하지 않는다.
4. 설치 검증이 실패하고 새 예약이 없다면 백업한 신뢰 코드·전환 기록만 복원한다. 이미 정산했다면 현재 장부·원문·사후 기록을 보존하고 호환성이 확인되지 않은 구버전으로 단순 복귀하지 않는다. 새 예약 이후에는 DB를 과거 백업으로 덮어쓰지 않으며 수동 검수를 중지한 채 기록을 조사한다.

이 코드 후보와 정산·계정 조정의 운영 적용은 별도 범위 확인 전까지 보류한다. 07:10 KST 경과만으로 UNKNOWN을 해제하거나 모델을 호출하지 않는다. 다음 실제 검수는 승인된 설치·정산·현재 제한·고정 대상·중복 실행을 다시 확인하고 **별도의 수동 요청**을 받은 뒤 한 건만 실행한다. 기존 worker·quota 타이머·운영 기록·PR #10 `pending`과 병합 금지를 유지한다.

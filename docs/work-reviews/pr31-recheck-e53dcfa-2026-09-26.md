## R31-4b 잔여: 사례 간 전역 두 번째 수정 (P2)

평가의 자동 수정 상한 2회는 E1–E6 전체에 적용된다. 다음 순서는 현재 실행기의 순차 처리와 양립한다.

1. E1의 첫 자동 수정을 완료하고 다음 사례로 넘어간다.
2. E2의 첫 자동 수정이 시작된 뒤 사용량 제한으로 종료·정산되고 같은 job/session으로 대기한다. 이 작업이 전체 평가의 두 번째 수정이다.
3. 제한 회복 뒤 E2를 다시 평가한다. 새 수정은 요청하지 않았다.
4. 호출·실행시간 예산이 남고 미정산 호출도 없지만 `budget_wait`로 종료한다.

원인은 [평가 실행기](https://github.com/HyungwonPark/ai-company/blob/e53dcfacccf03e4f7fe9f6d89dcaa63ea59c45a4/scripts/evaluate_pm_behavior.py#L201-L256)의 `resumable_second_repair()`다. 이 함수는 원래 계획의 `auto_revision_attempt == 1`, 대상 작업의 내부 번호 `2`만 인정한다. 반면 호출부의 `repairs == MAX_REPAIRS`는 여러 사례를 합친 값이다. E2의 첫 수정은 원래 계획 번호 0·대상 작업 번호 1이므로, 이미 전역 횟수에 포함됐어도 거절된다.

Work에서 독립 재실행한 진단은 E1의 4개 정산 호출 뒤 E2 예산을 실제 함수로 고정했다. E2의 첫 수정까지 정산한 결과는 호출 7회·수정 2회·실제 실행시간 7초·미정산 0건·다음 호출 timeout 30초였다. 그런데도 결과는 `budget_wait`, `worker.run_once()` 호출은 0회였다.

사례 예산 계산도 E1의 수정 1회가 끝난 후 E2에 남은 수정 1회를 고정하도록 되어 있다. 따라서 E2 내부 번호를 2로 바꾸는 수정이나 전역 한도 증액으로 해결하면 안 된다.

[재현 스크립트](repros/pr31-cross-case-repair-resume-e53dcfa.py)는 실제 모델·운영 자료를 사용하지 않는 격리 진단이다. 합성 fixture의 PM 제안·검수·수정 정산 기록은 실제 모델이나 전체 Automation 실행 이력을 대신하지 않는다. 스크립트의 종료 코드 0은 기존 결함 재현에 성공했다는 뜻이며 제품 검증 PASS가 아니다. 모델 호출 없이 예산 판정의 결함을 좁혀 확인하며, 실제 Automation 경로 검사는 아래 수용 조건으로 요구한다.

## 서버 Codex 실행 지시

기존 PR #31에서 평가 실행기와 필요한 회귀 검사만 최소 수정한다. 별도 기획 승인이나 추가 기능 설계를 기다리지 않고 다음 비운영 작업까지 완료한다.

1. **새 수정을 시작하는 경우와 이미 전역 수정 횟수에 포함된 현재 작업을 재개하는 경우를 구별한다.** 현재 계획에 연결된 실제 다음 수정 번호를 기준으로 task를 찾고, 그 task가 이미 시작·정산된 동일 작업임을 증명한다. 사례 내부 번호 2를 전역 두 번째 작업의 필수 조건으로 쓰지 않는다.
2. 기존 계획·요청·목표·task·job/session 연결, 대기 분류, 종료·정산 증명과 중복 실행 방지를 유지한다. 호출 24회·실제 실행시간 1800초·전역 자동 수정 2회·호스트 병렬 2개 상한을 늘리지 않는다. 미정산 또는 출처가 다른 작업은 계속 막는다.
3. E1 첫 수정 완료 → E2 첫 수정 한도 대기 → worker 종료 → 회복 → 동일 job/session 재개를 **실제 Automation·Dispatcher·SQLite·공용 장부와 모의 모델**로 검사한다. 사례별 예산 고정은 실제 계산을 사용한다. 기존 코드에서 실패하고 수정 후 성공하는 기록을 남긴다.
4. 같은 사례의 두 번째 수정 재개도 계속 통과해야 한다. 사례 간 재개 이후 새로운 전역 세 번째 수정은 막혀야 한다. 이 경계와 직접 관련된 중복 재개·예산·정산 검사를 유지하고, UI 개편이나 다른 기능으로 범위를 넓히지 않는다.
5. 독립 검수, 필수 회귀와 최종 HEAD CI를 완료하고 검증·적용/복구안을 수정 SHA에 맞춘다. 공용 장부 운영 연결 전 실제 Claude 재호출은 수행하지 않는다.

완료 보고에는 최종 SHA, 실패→성공 근거, 동일 job/session 유지, 전역 수정 횟수 2 유지, 세 번째 수정 차단, 최종 CI를 간결하게 제시한다. 기술 수용 뒤의 실제 모델 평가·마스터 직접 확정·운영 적용은 각각 별도 상태로 보고한다.

## 다음 단계와 운영 경계

이 한 건까지 고친 동일 후보로 적용 패키지를 고정하고 운영 연결 승인 단계로 넘기는 순서를 유지한다. 구현·검수와 별도로 서버의 실제 릴리스 파일 또는 이미지 해시, 두 유닛, 비공개 환경 설정·카탈로그 유지, 과거 사용량·제한 상태 대조 및 새 장부 생성·복구 절차를 준비한다. 기존 배포 형태가 파일 기반이면 불필요하게 새 이미지 체계로 바꾸지 않는다.

그 뒤 승인할 대상은 준비된 worker·유닛·비공개 설정·공용 장부·신뢰 검수기 연결의 구체적 적용 범위다. 이 문서는 그 운영 변경을 승인하지 않는다. 웹 교체·병합·PR #10 pending 변경·서명키 작업은 포함하지 않는다. 새 장부 예약이나 결과가 생긴 뒤 과거 DB로 덮어쓰거나 구형 worker를 무조건 재시작하지 않는 기존 복구 조건도 유지한다.

문서 게시와 서버 작업 착수는 다르다. Work는 제품을 수정하거나 서버에서 실행하지 않았으며, 실제 모델·운영 검증을 완료로 처리하지 않는다.

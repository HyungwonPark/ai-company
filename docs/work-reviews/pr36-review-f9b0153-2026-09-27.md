## R36-1 · 고정한 검수 대상이 runner 호출까지 전달되지 않음 · P1

**위치:** `scripts/review_claude_quota_tick.py` 185~191, `scripts/review_pr_with_claude.py` 573~604 및 869 이후 대상 조회.

timer는 기존 attempt의 HEAD/base/패치를 manifest와 대조하지만 runner에는 PR 번호와 `--resume-quota`만 전달한다. runner는 checkout·원격 PR에서 대상을 다시 정하며, 그 HEAD의 이전 시도가 없어도 `resume_quota=True`에서 새 디렉터리를 만들어 실행을 허용한다.

따라서 이전 대상이 READY인 상태에서 checkout과 원격 PR이 함께 다른 HEAD로 바뀌면, 승인한 대상 대신 새 HEAD의 모델 호출로 넘어갈 수 있다. 호출 뒤 manifest 불일치를 발견해도 이미 생긴 호출을 되돌리지 못한다.

**재현:** 실제 `reserve_attempt`에 이전 시도가 없는 새 대상과 `resume_quota=True`를 넣으면 previous=None으로 정상 진입했다. 별도 실제 `main()` 실행에 Git·GitHub·CLI 사전 조회만 합성하고 모델 호출 함수 직전에 멈춘 결과, 새 HEAD `bbbb…`의 예약과 invoke 경계에 도달했다. timer→실제 모델 전체 실행은 하지 않았으며, timer가 고정 값을 넘기지 않는 코드와 두 경계 재현을 함께 근거로 한다.

**수용 기준:**

- manifest의 PR/URL/HEAD/base/전체 패치 해시/이전 시도·예약 연결을 runner 사전 검사와 예약·프롬프트 전달까지 유지한다.
- `--resume-quota`에 일치하는 이전 시도가 없으면 최초 검수로 취급하지 않는다.
- checkout 또는 원격 HEAD/base/패치가 바뀌면 새 예약·프롬프트 전달·모델 호출 모두 0건이다.
- timer 검사 후 runner 시작 전 변경도 포함해 검사한다. 호출 직전 대상 변경을 사후 판정으로만 막지 않는다.

## R36-2 · 재개 후 체크포인트를 다시 읽을 수 없음 · P2

**위치:** `scripts/review_pr_with_claude.py` 269~279, 931~936.

생성기는 “이전 체크포인트:”를 설명 문장 중간에 붙인다. 재구성기는 줄 시작의 `^이전 체크포인트: `만 읽는다. 새 실행은 이전 범위를 상속해 저장하지만 다음 검증에서는 상속을 놓쳐 저장된 체크포인트와 달라진다.

**재현:** 실제 main을 두 번 실행하고 임시 공용 장부·예약·정산·체크포인트·tick 판정을 사용했다. Git/GitHub 사전 검사와 외부 CLI 응답은 합성했다.

| 합성 실행 | 실제 제품 경로에서 확인한 결과 |
| --- | --- |
| 첫 한도 종료 → 재개 후 PASS | runner 반환 0·완료 true, 저장 검토 파일 2개·계보 2개. 다음 tick은 NEEDS_RECONCILIATION |
| 첫 한도 종료 → 재개 후 다시 한도 종료 | 사용량 정산·회복 시각 경과 후에도 다음 tick은 NEEDS_RECONCILIATION |

두 경우 모두 줄 시작 체크포인트 검색 결과 0개이며 `saved checkpoint differs from bound event replay`로 재구성을 거부했다.

**수용 기준:**

- 체크포인트 전달·파싱 계약을 일치시킨다. 가능하면 설명 문장과 별도인 구조화 자료로 묶고 원문·대상·이전 시도 해시를 검증한다.
- quota→PASS/REVISE는 최종 내용·전체 범위·종료·정산 확인 후 DONE, quota→quota는 새 회복 시각의 WAITING_QUOTA와 이후 READY에 도달한다.
- 3회 이상 이어지는 진행·미해결 지적·정산 참조도 보존한다. 기존 helper 결과를 수동으로 조립하는 검사에 그치지 않고 실제 main이 만든 prompt/checkpoint/receipt를 다음 tick이 읽게 한다.
- 과거 프롬프트·영수증·사건 원문을 고쳐 통과시키지 않는다.

## R36-3 · 이전 시도 보관 후 자동 재개가 고착됨 · P2

**위치:** `scripts/review_claude_quota_tick.py` 31~35·94, `scripts/review_pr_with_claude.py` 573~587·945~951.

한도 시도를 `-quota-…` 디렉터리로 옮겨도 예약 owner는 원래 디렉터리다. runner의 기존 검증은 원래 경로를 계산하지만 tick은 보관 경로와 owner를 직접 비교한다.

용량 거절, 보관 직후 중단, 미시작 예약 복구로 원래 디렉터리가 없어지면 tick이 보관된 정상 정산 시도를 선택하더라도 거부한다.

**재현:** 기존 원본 검사의 정상 quota 기록에서 READY를 확인한 뒤 보관 디렉터리로 이동한 재시작 상태를 만들었다. 예약·정산은 그대로인데 tick은 `NEEDS_RECONCILIATION / ValueError`가 됐다. 실제 CLI는 호출하지 않았다.

**수용 기준:**

- 보관된 시도와 원래 예약 owner를 검증 가능한 동일 식별 기준으로 대조한다. 다른 PR·HEAD·예약의 보관 기록은 거부한다.
- 용량 거절→다음 tick, 보관 직후 중단→재시작, 미시작 예약 취소→다음 tick을 timer→runner→공용 장부 경로로 검사한다.
- 기록 보관은 유지하고, 현재 프로세스·미확인 예약을 임의 취소하거나 원본 경로를 새 시도로 덮어쓰지 않는다.

## A. 원본 증거 보존과 실패 재현

1. 현재 worker·릴리스·유닛·CLI·설정·공용 장부의 상태를 읽기 전용으로 대조한다. 보고 시점과 다르면 차이를 먼저 기록한다. 기존 실행 중인 프로세스나 기록을 이번 재현을 위해 바꾸지 않는다.
2. 기존 E1의 구조화 응답, stdout/stderr, 해당 세션 rollout, job/attempt/session/reservation, claim·종료 시각, 실행 설정·요구사항·정책·기준 커밋·전송 스키마 해시를 비공개 사본으로 고정한다. 원문 존재 여부와 누락 항목을 명시한다.
3. 계정 인증 파일을 증거로 수집하거나 출력하지 않는다. 공개 검증용 자료는 별도 비식별 fixture로 만들고 원문 자체와 구별한다. 운영 원문은 Git에 게시하지 않는다.
4. 실제 기록에서 무엇이 버전이고 무엇이 현재 turn 설정인지 확인한다. 세션 생성 당시 CLI 버전과 현재 resume 실행 파일 버전이 같다고 가정하지 않는다. 확인할 수 없는 필드는 미확인으로 남긴다.
5. 기존 코드에서 실제 비식별 fixture가 실패하는 지점과 세 경로의 조건을 재현한다. 모델 본문이나 요청 옵션을 관측 증거로 바꿔 재현을 통과시키지 않는다.

완료 기준: 원본 보존 목록, 실패 이유, 실제 fixture/합성 fixture 구분, 모델 호출·새 예약·운영 DB 쓰기 0건을 제출한다.

## B. Codex 증거 계약과 버전 호환 검사 통합

1. 세 경로가 같은 호환 프로필과 검증 결과를 사용하게 한다. 필요한 범위의 공통 모듈로 정리하되 새 범용 프레임워크를 만들 필요는 없다.
2. `0.154.0`의 기존 근거와 의미를 유지한다. `0.157.0`은 실제 기록 형식·필수 필드·정상/오류 fixture를 검증한 뒤 별도 지원 근거로 추가한다. 버전 상수를 바꾸거나 모든 상위 버전을 허용하는 방식은 사용하지 않는다.
3. 버전 지원과 내용 유효성을 따로 검사한다. 알려진 버전이어도 session, 작업 경로, 실행 시간, turn, 할당 모델·effort, 상충하는 실행 정보가 맞지 않으면 차단한다. 기존 경로·심볼릭 링크·크기·범위 검사를 유지한다.
4. 현재 실행 파일의 식별·해시·버전과 rollout 형식 프로필을 분리한다. 이전 버전에서 시작한 세션을 새 CLI로 재개하는 조합은 실제 근거가 있는 범위만 지원하고, 미지원 조합은 호출 전에 구체적인 이유로 차단한다.
5. CLI 설정 증거와 공급자 내부의 실제 실행 모델 증거를 혼동하지 않는다. `backend_model_verified=False`의 의미와 모순 정보 거부를 유지한다.
6. `unsupported_cli_version`, `missing_configuration_evidence`, `configuration_mismatch`처럼 실패 범주를 구분한다. 구체적 이름은 기존 계약에 맞춰 정하되 사용자가 볼 문구는 원인·다음 행동을 한국어로 표시한다. 원래 증거와 실패 기록을 번역해 덮어쓰지 않는다.

완료 기준: 같은 입력에 대해 증거 수집·Dispatcher 채택·화면 표시가 일관되며, 지원 추가가 기존 미확인 증거의 자동 승격으로 이어지지 않는다.

## C. 실제 worker 환경의 호출 전 호환 검사

1. 서비스가 실제 사용하는 PATH·실행 파일·실제 네이티브 실행 코드·필요한 세션 저장 경로와 증거 프로필을 사전에 확인한다. 셸에서 찾은 다른 설치본의 버전으로 대신하지 않는다. 전체 환경변수·인증정보를 출력하지 않는다.
2. 호출 없는 `--version`·필요한 도움말 조회와 기존 기록 fixture 검증을 사용한다. 이것을 실제 모델 수용 또는 응답 품질 검사로 보고하지 않는다.
3. 서비스 사전 검사와 각 실제 배정 경계에 연결한다. 미지원 버전·프로필·변경된 실행 파일이면 모델 프로세스와 프로젝트/공용 예약을 만들기 전에 차단한다. 이미 생긴 과거 예약·사용량은 수정하지 않는다.
4. 검사 후 실행 사이 실행 파일이 바뀌는 경우도 다룬다. 승인된 서비스 전용 고정 경로나 재검증으로 실행 대상을 묶는다. NPM 진입 스크립트의 해시만 같고 실제 바이너리가 바뀐 경우를 놓치지 않는다. 전역 CLI 다운그레이드나 교체는 이번 비운영 구현에 포함하지 않는다.
5. 서버에 설치할 고정 archive로 새 릴리스를 만들어 실제 worker 권한·Python·실행 경로와 같은 격리 환경에서 검사한다. 준비 상태, 서비스 가동 상태, 계정/한도 대기, 실제 모델 검증 상태를 따로 보고한다.

완료 기준: 모의 버전 변화에서 호출 0·예약 0으로 차단되고, 지원 프로필과 실제 고정 실행 파일이 맞을 때만 무호출 준비 검사가 통과한다. 원래 스키마 호출 전 검사도 유지한다.

## D. 이미 정산된 E1의 무호출 재검증·안전한 재처리

먼저 진단 모드를 구현하고 격리 사본에서 검증한다. 기존 평가기의 `run_case` 또는 일반 worker를 진단 수단으로 실행하지 않는다. 이 경로는 실제 호출로 이어질 수 있다.

1. 원문이 충분하면 현재 후보 검증기로 저장 응답과 설정 증거를 재검증한다. `unavailable`로 축약된 값만으로 설정을 추정하지 않는다. 원문 누락·불일치이면 복구 불가 이유를 보고한다.
2. 원본 job·result·정산·실패 이유·당시 정책을 바꾸지 않고 파생 검증 revision을 추가한다. 원본 reservation/job/attempt/session, 원문 해시, 원래 요구사항·스키마·정책·커밋, 검증기 코드/프로필을 연결한다. 새 버전으로 과거 명세를 바꿔 합격시키지 않는다.
3. 재검증 대상은 원래 응답이 원래 승인된 계약을 만족하는지다. 응답 내용·요구사항·모델 설정을 수정해야 한다면 재사용 합격으로 처리하지 않는다. 낡은 목표·요청·대체된 generation의 결과는 현재 계획으로 승격하지 않는다.
4. 격리 사본에서 검증된 결과를 계획으로 저장하는 명시적 전이를 구현한다. 원래 차단 이력과 새 파생 저장의 관계를 감사 기록에 남긴다. 일반 실행 상태를 강제로 PLAN_READY로 바꾸거나 canary 결과 파일을 수동 생성하지 않는다.
5. 같은 원문·검증기·대상 revision의 중복/동시 실행·중간 종료에서 파생 결과와 계획이 각각 한 번만 저장되도록 한다. 진단과 계획 저장 어느 경로도 자체적으로 PM 검수 모델·개발을 호출하거나 마스터 확정을 만들면 안 된다.
6. E1 성공 검사도 파생 근거·저장 계획·현재 요청·기존 정산을 다시 검증하도록 한다. 오프라인 진단 PASS만으로 E1 후속 검수나 E2~E6을 열지 않는다. 실제 다음 실행은 F의 적용 조건을 따른다.
7. 선행 6건과 E1 1건의 정산·호출 수·실행 시간·자동 수정 횟수를 후속 평가 계보에 계속 포함한다. 원문 재처리를 새 모델 호출로 세거나 기존 호출을 지우지 않는다. 기존 최대 24호출·1800초·자동 수정 2회는 원래 승인된 평가 범위이며 새 제한을 추가하는 의미가 아니다. 확인하지 못한 토큰·청구액을 0으로 만들지 않는다.

완료 기준: 격리 사본에서 추가 모델 호출·예약·정산 0건, 원본 7건과 원본 결과 해시 불변, 검증된 파생 계획 최대 1건을 입증한다. 실제 서버 E1의 재사용 가능 여부는 별도 결과로 제출한다. 원문이 부족하면 미완료를 정확히 남기고 다른 A~E 작업은 계속한다.

| 사전 검사 | 실제 서비스 경로 사용, 검사 후 파일 변화, 모의 미지원 CLI에서 모델/예약 0건 |
| 저장 응답 | 최초 실패→새 검증기 성공의 파생 기록, 원본 실패/정산 불변, 원문 없으면 복구 불가 |
| 중복과 재시작 | 재처리 2회·동시 처리·저장 중 종료 후 재개에서 중복 계획·추가 정산·모델 호출 없음 |

| 기존 회귀 | PR31 재개 경계·공용 한도/UNKNOWN·PR33 스키마·첫 PM 호출 상한 보존 |

최종 코드의 독립 검수와 필수 CI를 확인한다. Claude 모델 검수는 현재 UNKNOWN과 기존 공용 장부·호출 조건을 충족할 때만 가능하며, 대기라면 독립 정적 검수와 구분한다. 대기 때문에 가능한 코드 검수·고정 패키징까지 중단하지 않는다.

후속 초안 PR에는 제품 커밋·최종 HEAD·archive/설치 파일 해시·호환 프로필·최초 실패/수정 후 결과·무호출 증거·남은 불확실성·적용/복구안을 묶는다. UI는 이번 원인/재처리 상태 표시의 필요한 부분만 검증하며, 별도 디자인 개편으로 범위를 넓히지 않는다.

## F. 다음 운영 적용에 사용할 통합안 준비

이번 지시는 A~E의 비운영 구현·사본 검증·패키징까지다. 앞선 고정 제품 승인만으로 새 후보를 적용하거나 worker를 켜거나 E1을 다시 호출하지 않는다. 다음 두 분기의 구체적 적용안을 완성한 뒤 새 후보 범위만 한 번에 확인한다. 이후 마스터가 승인하면 그 범위 안의 단계별 확인은 반복하지 않는다.

- **저장 E1 복구 가능:** 새 고정 릴리스와 검증된 재처리 경로를 적용하고, 기존 E1 결과의 파생 계획 저장·정산/계보 대조를 먼저 한다. 추가 E1 PM 호출은 하지 않는다. 통과하면 승인된 잔여 예산과 같은 평가 revision 근거로 E1 내용 검수·후속 사례를 진행한다.
- **저장 E1 복구 불가:** 이유와 누락 증거를 제시하고 새 후보의 사전 검사 후 E1 PM 호출 1건을 포함한 적용안을 준비한다. 기존 7건을 합산하며, 첫 새 호출의 설정 증거·전송/저장 계약·종료 정산을 확인하기 전에는 후속 호출을 열지 않는다.

예상된 한도 대기와 기술 실패, PM 내용의 정상 REVISE를 구분한다. 배포/증거/정산/기록 보존 검사 실패나 뜻밖의 호출이면 새 예약 유무와 무관하게 두 worker 중지·자동 시작 해제를 수행하고 inactive/disabled를 확인하는 복구안을 유지한다. 과거 DB·장부 백업 덮어쓰기와 구형 호출 경로 재가동은 금지한다. 이미 PR33에서 새 예약이 생겼으므로 현재 후보 포인터를 보존하는 원칙을 지키며, 미래 포인터 전환/복구는 새 쓰기와 호환성 근거에 맞춰 구체화한다.

quota 가드·타이머, 웹·커플 서비스, Claude UNKNOWN, PR #10 pending과 기존 사용자 기록을 보존한다. 운영 DB 스키마나 서비스 전용 실행 파일 추가 배치가 필요하면 실제 적용 항목과 사본 호환/복구 결과를 빠짐없이 명시한다. 병합·서명키·마스터 대신 계획 확정은 포함하지 않는다.

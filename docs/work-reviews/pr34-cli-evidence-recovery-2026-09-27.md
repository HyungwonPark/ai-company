## 변경과 실패 경계

1. `0.154.0` 기존 계약을 유지하고, 실제 형식을 확인한 `0.157.0`을 별도 프로필로 추가했다. 수집·Dispatcher 채택·화면 표시가 같은 판정 함수를 사용한다. 미지원 버전, 세션·turn·시간·작업 경로·모델·추론 수준 불일치와 상충 실행 정보를 차단한다. 과거 `unavailable` 저장값을 자동 승격하지 않는다.
2. worker는 실제 PATH가 가리키는 네이티브 CLI의 버전·해시·재개 세션 버전을 **프로젝트/공용 예약 전**에 확인하고 실행 직전 다시 확인한다. 지원되지 않은 혼합 버전 재개와 변경된 실행 파일은 호출 없이 차단한다. 설치 네이티브 SHA-256은 `2e43362b5064a4d40e6a8f9fe00d6438c5447c20f41ed1659cc2e71258efd21f`이다. 재검사와 `systemd-run` 실제 실행 사이의 아주 짧은 경로 교체 가능성은 독립 검수에서 남긴 P2이며, 향후 운영 적용 시 고정 경로·해시 대조를 유지한다.
3. E1 복구는 원본 DB·job·실패 이유·정산을 수정하지 않는다. 원본·동결 사본·선택한 사본의 요청/작업/job/이벤트와 두 장부의 예약/정산 journal을 대조한다. 새 검증기 코드 트리 해시·프로필·원문/정책/스키마/원본 커밋으로 파생 revision을 만든다. 별도 `pm_recovery_revisions` 기록과 계획 1건을 저장하며, 두 저장 사이에 중단돼도 재검사 후 한 번만 완성한다. 이 경로는 PM 재호출, 독립 내용 검수, 개발 배정, 마스터 확정을 수행하지 않는다.
4. E1 canary는 파생 revision·계획·현재 요청·기존 한 건의 정산을 다시 검증한 후 코드가 원자적으로 기록한다. 단일 E1 PM 호출 뒤 검수 호출이 추가되거나 원래 계획이 `proposed`·수정 상태로 바뀐 후에도, 최초 호출을 다시 증명하며 이어갈 수 있다. 끊긴 canary 파일은 보존하고 재검증 후 교체한다. 수동으로 canary 파일을 만들어 통과시키지 않는다.

## 후속 통합 적용·복구안 — 이번 PR에는 적용 권한 없음

**선택할 분기: 저장 E1 재사용.** 실제 원문은 현재 후보에서 재사용 가능하므로, 새 E1 PM 호출을 계획하지 않는다. 적용 직전 원본 manifest·릴리스/CLI 해시·요청 세대·원본 job/스키마/정산 7건·중단 프로세스·worker 상태가 하나라도 달라지면 적용을 멈춘다. 비공개 실행 절차에는 정확한 파일 경로와 검사 명령을 고정한다.

새 승인을 받으면 두 worker를 `inactive/disabled`로 유지하고 DB·장부·체크포인트의 **일관 사본**을 남긴 뒤, 설치한 위 archive 해시·Python·네이티브 CLI를 대조한다. 현재 릴리스 포인터를 보존하고 **PM·조정기/번역 두 worker가 사용하는 코드 포인터만** 새 릴리스로 전환한다. `apply-operating-and-canary` 한 명령이 worker 조정 잠금과 평가 잠금 아래 원본 E1을 재검사하여 `pm_recovery_revisions` 테이블·파생 계획·canary를 중복 없이 저장한다. 이 명령은 두 worker가 계속 `inactive/disabled`인지 전후 확인한다. 저장 계획·현재 요청·7건 장부·추가 예약 0건, 기존 운영 대기 목록, 새 릴리스에 묶인 공용 장부 채택 증빙을 확인한 뒤에만 두 worker를 단일 실행으로 재활성화한다. 승인 범위 밖 대기 작업이 있다면 재활성화하지 않는다. 그다음 같은 평가 계보·잔여 예산에서 E1 **별도 내용 검수**와 후속 E2~E6을 진행한다. 계획 확정·개발을 대신 수행하지 않는다.

저장 원문이 적용 시점에 달라져 재사용이 불가능하면 **자동으로 재호출하지 않는다.** 차이·누락 증거를 보고하고, 기존 7건을 합산한 새 E1 PM 한 건부터 시작하는 대안 범위를 별도로 판단한다. 이 분기의 첫 새 호출도 전송/설정 증거·계획 저장·종료 정산이 확인되기 전에는 후속 호출을 열지 않는다.

적용 전 해시·로그인·장부·기록 보존 검사 실패, 원치 않은 호출, E1 저장/검수 실패 또는 공통 요청 오류가 나면 예약 유무와 무관하게 두 worker를 중지·자동 시작 해제하고 각각 `inactive/disabled`를 확인한다. 새 쓰기 전의 단순 포인터 변경만 이전 릴리스로 되돌릴 수 있다. **파생 계획이나 새 예약 등 DB 쓰기가 생긴 뒤에는 구형 worker를 재가동하거나 DB·공용 장부·체크포인트를 과거 백업으로 덮지 않는다.** 현재 포인터와 증거를 보존해 조사한다. quota 가드와 일정, 웹·커플 서비스, 기존 기록·계정 `UNKNOWN`, PR #10 `pending`은 그대로 둔다. 한도 대기와 내용 검수 `REVISE`는 기술 실패로 오인하지 않는다.

## 최초 실패 → 수정 후 성공

실제 `Automation`·`Dispatcher`·SQLite·공용 장부를 사용하고 모델 결과만 모의한 회귀를 추가했다. E1에서 첫 기술 수정을 완료한 뒤, 실제 `case_budget_config()`가 E2에 **남은 수정 1회**를 고정했다. E2의 첫 `pm-revise`가 quota로 정산되고 worker를 닫은 다음, 회복 시각 이후 같은 사례를 다시 열었다.

`e53dcfa` 코드에서는 E2 내부 수정 번호가 1인데도 전역 수정 2회에 도달해 있었다. 재개 검사가 내부 번호 2만 찾으므로 예상 `plan_ready` 대신 `budget_wait`가 나왔다. 실패 시 증거는 **공유 예약 7건, 전역 수정 2회, 정산 실행시간 7초, 다음 호출 허용시간 180초**였다. 호출·시간 소진 때문이 아니다.

수정 후 재개 검사는 현재 계획의 `auto_revision_attempt + 1`로 실제 작업 ID를 찾고, 그 작업의 계획·요청·목표 바인딩, 동일 job/session, quota 대기 분류, 공용 장부의 시작·정산 결과를 유지해 확인한다. E2는 **내부 첫 수정·전역 두 번째 수정**으로 같은 job의 두 번째 시도를 완료했다. 작업 수 1건, job/session 동일, 최종 전역 수정 횟수 2회, 개발 실행 0건을 검사했다. 이후 다른 계획으로 시작할 새 전역 세 번째 수정은 `budget_wait`이고 `run_once()`는 호출되지 않았다. 기존 E1 내부 두 번째 수정 재개와 변경된 계획·세션·대기 분류·미정산·호출/시간 상한 검사는 그대로 통과했다.

평가 실행기 SHA-256은 `b919a961ffb904fa78af54d47f35adf9aaeca939769340f4bd4d9d680d8bfb52`, 회귀 파일 SHA-256은 `a5c682e505797fecbb73d8a8b36d0798c4da82eb73347248a104198cdf890ea5`이다. 검수기·relay·공용 장부·worker 유닛 2개의 유지된 해시와 [전체 적용·복구 절차](shared-call-evaluation-candidate-2026-09-26.md)는 같은 후보 기준으로 대조한다. 운영은 파일 기반 릴리스이므로 새 웹 이미지/이미지 체계가 필요하지 않다. **실제 설치될 릴리스 파일의 해시, 비공개 설정·카탈로그, 계정별 과거 사용량·cooldown, 미정산 호출은 운영 적용 직전에 다시 고정해야 한다.** 이 코드 커밋만으로 운영 연결은 승인되지 않는다.

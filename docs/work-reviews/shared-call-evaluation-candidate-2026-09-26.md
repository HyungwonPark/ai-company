# 공용 호출 장부·PR 검수 재개·PM 평가 후보

## 범위와 기준

이 문서는 **비운영 후보**의 적용·복구안이다. PR #29 `f7354be`의 수용된 검수 근거를 보존하고, PR #30의 E1–E6 고정 입력을 포함한다. 운영 worker, 웹, 번역 기록, PR #10 승인, 서명키는 변경하지 않았다. 실제 Astra 평가·Claude 재호출·마스터 조작은 아직 수행하지 않았다.

공용 장부 `SharedCallLedger`는 기존 DB와 별도의 **명시적으로 지정한 비공개 SQLite 파일**이다. 등록된 `(provider, credential_ref) → quota_group`을 검사하고, `BEGIN IMMEDIATE`로 같은 계정의 호출 1개와 전체 호스트 슬롯 2개를 함께 예약한다. `RESERVED`·`STARTED`·`UNKNOWN`은 모두 슬롯을 차지한다. 시간 경과만으로 해제하지 않는다. 종료가 확인된 결과는 고정 event ID로 한 번만 정산한다. 다른 결과를 같은 ID로 다시 기록하면 거부한다. 등록되지 않은 계정, 손상된 장부, 불확실한 자식 프로세스는 실행을 막는다. 이 파일에는 비밀번호·토큰을 넣지 않는다.

이 후보의 진입점은 `service_worker`의 PM·조정기와 번역 worker, `flow`·`automate` CLI, 독립 번역 CLI, 신뢰 경로에 설치할 PR 검수기다. 별도 `session worker` CLI는 계정 식별자가 없는 과거 경로여서 **운영 전환 시 실행 금지**로 분류한다. `AI_COMPANY_REQUIRE_SHARED_CALLS=1`을 설정하면 직접 `run_session`·구형 Dispatcher·번역 worker가 공유 예약 없이 실행할 수 없다. 과거 서비스에는 이 환경변수를 적용하지 않았다. 수동으로 `claude`/`codex` 바이너리를 호출하는 행위까지 이 애플리케이션 장부가 통제한다고 주장하지 않는다.

### R31-1~4 보완 후의 필수 경계

- **한도 거절과 복구 시각을 분리한다.** 원시 provider 이벤트가 `rejected`인데 `resetsAt`이 없거나 양의 유한 Unix 시각이 아니면 종료·사용량 사실을 한 번만 정산하되 계정은 `UNKNOWN`으로 보존한다. 수신 시각보다 5분 이상 오래된 값도 증명되지 않은 reset으로 본다. 유효한 reset만 `COOLDOWN`과 새 시도 예약의 근거가 된다. 영수증에는 거절 사실·reset 검증 여부·정산 분류를 함께 남기고 원시 이벤트를 보존한다. 인증 실패는 quota 복구 근거로 취급하지 않는다.
- **미시작 취소 뒤 동일 큐 시도를 재개할 수 있다.** 취소를 증명한 기존 예약 행을 별도 `:cancel:` 행으로 보존하고, 원래 예약 ID를 다시 `RESERVED`로 만들기 전 계정 상태·다른 큐의 선점·호스트 2슬롯을 한 트랜잭션에서 재검사한다. `STARTED`·`UNKNOWN`·`SETTLED`는 이 경로로 다시 열지 않는다. 장부 스키마는 기존 버전 2를 유지하며 운영 DB에 새 테이블을 만들지 않는다.
- **PM 평가 완료는 현재 요청의 현재 계획으로 판정한다.** 기술 지적의 자동 수정이 예정되면 별도 `pm-revise` 작업과 두 번째 계획 검수가 끝날 때까지 평가를 계속한다. 답변 필요·마스터 결정 대기·수정 2회 도달·환경 문제·계획 준비를 각각 구분하고, 과거 계획의 대기나 승인 사실을 현재 계획에 적용하지 않는다. 평가 실행기는 마스터 답변이나 계획 확정을 대신하지 않는다.
- **평가 1800초는 실제 호출 시간으로 계산한다.** 같은 시험 루트에 귀속된 장부 정산의 `duration_seconds`를 합하고 미정산 예약은 각 호출 timeout 전량을 보수적으로 예약한다. 제한 대기 2시간과 프로세스가 꺼진 시간은 누적 실행 시간에 더하지 않는다. 미정산 예약은 새 호출을 막고 `reconciliation_wait`로 남긴다. 최초 시작 시각 파일은 감사 기록으로 보존하지만 예산 계산에는 사용하지 않는다. 시험 루트에는 단일 실행 잠금을 걸고, 사례가 시작될 때 전역 잔여 호출·수정·시간을 파생 설정과 SHA-256으로 고정한다. 제품 Dispatcher의 프로젝트 예산이 실제 프로세스 timeout을 잔여시간으로 줄인다. CLI의 종료 정리·cgroup 확인 시간을 감안해 다음 사례의 프로세스 예산에는 전역 잔여시간보다 60초 적게 부여한다. 비정상적인 OS 지연의 절대 상한은 증명할 수 없으므로 실제 정산 시간이 1800초를 넘으면 추가 호출 없이 조정 대상으로 둔다. 호출 24회·수정 2회·호스트 2슬롯과 개별 timeout은 유지한다.
- **R31-4b: 시작한 전역 두 번째 수정은 재개하고 새 세 번째 수정은 거부한다.** 평가기는 일반적인 계획 검수 작업의 `usage.repairs`를 자동 수정 횟수에 중복 합산하지 않는다. 수정 횟수 2회에 도달한 뒤에는 **현재 사례의 다음 수정 번호**로 실제 `pm-revise` 작업을 찾는다. E1의 첫 수정 다음 E2의 첫 수정도 전역 두 번째 수정이므로, E2 내부 번호를 2로 강제하지 않는다. 해당 작업의 ID·요청/계획/목표 버전·job/session과 공용 장부의 시작·정산 사실을 대조한다. `WAITING_QUOTA`와 quota/rate-limit, 또는 `WAITING_RETRY`와 transient-network가 일치하는 **기존 작업**만 재개한다. 공용 정산 뒤 로컬 집계 직전 중단도 기존 Dispatcher의 결과 복구에 맡기며 새 호출로 세지 않는다. 사실이 불완전하거나 계획이 달라지면 보수적으로 대기한다. 호출·실행시간·미정산 예약·계정·호스트 제한은 그대로 적용하고 새로운 세 번째 수정은 차단한다.

추가 검사: 독립 큐의 동시 계정 예약, 별칭 계정 우회 거부, 세 번째 호스트 슬롯 거부, 재시작 후 미확인 실행 보존, 중복 정산, quota 이전·이후 대기, 다른 PR HEAD 거부, 번역 로컬 저장 실패 후 중복 호출 차단. 기존 Dispatcher와 번역·Claude 검수 회귀를 함께 실행한다. 실제 모델 요청과 격리 시험은 별도 결과로 기록한다.

## PM 행동 평가 실행기

`scripts/evaluate_pm_behavior.py`는 PR #30의 E1–E6 원문과 제품 기준 커밋을 고정해서 읽는다. 준비 모드는 호출 0건으로 사례별 최종 메시지·설정 해시와 E5 공개 조사 설정을 보여준다. 실행 시작 때 이 결합 해시를 시험 디렉터리에 고정해 재시작 후 입력 변경을 거부한다. 실제 모드는 운영과 다른 사례별 상태 디렉터리에서 **제품의 `Automation` → `Dispatcher` 경로**를 사용한다. 마스터 확인이나 개발 배정 API를 호출하지 않는다. E2 답변은 같은 사례의 두 번째 메시지로만 보내고, E4 검수 지적과 E6 외부 발췌는 평가 자료라고 명시한다. E5는 신뢰 설정 `skill_search_terms=(python, testing)`, `skill_public_sources=()`를 사용한다. 기존 조사 구현의 상한은 검색 2회·파일 4회·6초이며 공개 자료를 설치하거나 실행하지 않는다.

전체 사례의 장부 예약 수를 합산해 호출 24회, 누적 1800초, 수정 2회, 병렬 최대 2개의 기존 상한을 넘기지 않는다. 평가 실행기는 실제 호출 전에 **모든 호출 경로가 동일 장부를 사용하거나 금지된 사실을 담은 비공개 운영 전환 기록**을 요구한다. 이 기록은 현재 존재하지 않으며 실제 평가를 시작하지 않는다. 각 사례의 원시 세션·구조화 응답·설정 관측·사용량·질문/지적/계획 버전과 독립 내용 판정은 추후 별도로 제출한다. 합성 테스트를 실제 Astra 판단 PASS로 표시하지 않는다.

## 운영 현황과 전환 전 필수 대조

2026-09-26 읽기 전용 확인: `ai-company-automation.service`와 `ai-company-translation.service`는 `active/running`이었다. 기존 세션 DB에는 quota group 2개(둘 다 AVAILABLE), flow task 7개, 관리 세션 9개(완료), 번역 job 26개(완료 18·실패 8)가 있었다. 이 숫자는 **그 시점의 관찰**이며 실제 전환 직전에 다시 읽어야 한다. 과거 사용량의 미관측 비용 표시도 보존해야 한다. 신규 장부의 `initialize()`는 이미 있는 파일을 덮어쓰지 않고, 검토한 계정별 과거 호출 수·시간·금액·금액 미확인 표시를 필수 입력으로 요구한다. 두 시험 큐만 새로 만들어 AVAILABLE을 부여하는 방식은 금지한다.

적용 직전에는 최종 HEAD, 위 파일 해시, 후보 릴리스 파일의 digest를 **실제로 설치할 결과**와 대조해야 한다. 이 표는 이미 운영에 설치됐다는 증거가 아니다.

1. 기존 상태 DB·worker 설정·유닛·신뢰 설치 검수기를 **비공개 경로에 백업**하고 해시·서비스 PID·활성 호출/guard를 기록한다. 진행 중 호출이 있으면 새 호출만 멈추고 종료·정산까지 기다린다. 불확실한 호출이 있으면 전환을 중지한다.
2. 과거 flow/번역/검수 시도를 중복 제외해 계정별 누적 사용량과 cooldown·인증 상태를 대조한다. 불명확한 양은 `cost_unknown=1`, 불명확한 실행은 `UNKNOWN`으로 표시한다. 원본 DB·시도 파일은 수정하지 않는다. 검토한 10필드 계정 목록으로 비공개 공용 장부를 **새 파일에만** 생성한다.
3. PM·조정기와 번역 worker를 **같은 최종 코드·공용 장부 경로**로 함께 교체한다. 후보 유닛은 `deploy/systemd/ai-company-automation.service`, `deploy/systemd/ai-company-translation.service`이며 두 `ExecStart` 모두 `--shared-call-ledger ${AI_COMPANY_SHARED_CALL_LEDGER}`를 받는다. **현재 PM 유닛의 `--execution-catalog`도 유지**하고, 비공개 `worker.env`의 `AI_COMPANY_EXECUTION_CATALOG`에 기존 카탈로그의 같은 절대 경로를 연결해 고정 해시를 대조한다. 비공개 `worker.env`에 장부의 절대 경로와 `AI_COMPANY_REQUIRE_SHARED_CALLS=1`을 함께 넣고, 두 유닛과 릴리스 포인터를 백업·해시 대조한 뒤 두 worker만 정상 종료, 파일 교체, `systemctl --user daemon-reload`, 재시작 순으로 적용한다. 기존 `session worker` 직접 경로 및 다른 구형 호출 경로는 중지/비활성임을 확인한다. PR 검수기는 최종 검수 뒤 저장소 밖 신뢰 경로에 runner·relay·`shared_calls.py`를 함께 설치하고 해시를 검증한다. 비공개 전환 기록의 코드 커밋과 이 세 파일의 SHA-256이 일치해야 실행한다. USD·턴 상한을 새로 넣지 않고 기존 30분 종료·동일 HEAD 중복 방지를 유지한다.
4. 서비스가 단일 인스턴스로 가동되고 로그인이 되는지, PM/번역 대기 목록과 원본 기록·PR #10 pending이 그대로인지, 장부의 계정/슬롯 상태가 DB 사실과 일치하는지 확인한다. 두 시험 큐의 동시 예약·중단 복구는 먼저 격리 사본에서 반복한다. 실제 평가 호출은 모든 진입점의 일치가 확인된 **이후** 별도 시험 상태에서만 허용한다.

R31 수정 후보를 적용하기 전에는 장부 **스키마 버전 2**와 기존 예약·정산 event 수를 백업 사본에서 대조하고, `CANCELLED` 예약의 동일 ID 재예약이 계정/호스트 선점을 우회하지 않는지 격리 사본에서 확인한다. reset 없는 기존 provider 거절이 발견되면 이를 `AVAILABLE`로 이관하지 않고 `UNKNOWN`으로 표시해 수동 조정 대상으로 남긴다. 평가 시험의 기존 `started-at.json`은 삭제하거나 재설정하지 않으며 동일 입력/설정 결합 해시로만 재개한다. 정산된 호출의 실행 시간이 없는 사례는 원시 호출 결과와 timeout 정책을 대조하기 전 실제 평가를 시작하지 않는다.

R31-4b 적용 전에는 격리 사본에서 **E1 첫 수정 완료 → E2 첫 수정의 한도 대기 → 회복 → 동일 job/session 재개**와 같은 사례의 두 번째 수정 재개, 공용 정산 후 로컬 집계 복구, 새로운 전역 세 번째 수정 거부를 다시 확인한다. 계획 버전이나 job/session 근거가 없으면 자동으로 재개하지 않는다. 평가 상태 디렉터리와 장부를 개별적으로 백업하되 이전 실패·사용량을 지우거나 과거 백업으로 덮지 않는다. 새 예약/결과가 없는 단계에서만 이전 worker 릴리스·유닛·환경 설정 복원을 허용한다. 이미 새 예약/결과가 있으면 자동 호출을 멈추고 현재 DB·장부·평가 기록을 보존해 조정한다.

**실패 판정:** 계정 매핑·기존 누적 사용량/한도 차이, 미확인 실행, 세 번째 슬롯 허용, 중복 정산, 기록 불일치, 서비스/인증 실패 중 하나라도 발생하면 새 모델 호출을 중지한다. 신규 공유 예약에 연결된 실행이 하나도 없다면 두 worker를 중지하고 백업한 릴리스 포인터·유닛·환경 파일의 해시를 확인해 원래 버전으로 돌린 뒤 `systemctl --user daemon-reload`와 원래 활성 상태의 두 worker 재시작을 수행한다. 신규 공유 예약이나 새 계획/번역 결과가 생겼다면 구형 worker를 단순 재시작하지 않는다. 두 worker만 중지하고 관리·보고 화면과 모든 DB/장부를 보존한 채 각 실행을 조정한다. **운영 DB와 승인 기록은 과거 백업으로 덮어쓰지 않는다.** 커플 서비스·기존 타이머·웹·PR #10 pending은 건드리지 않는다.

PR #30의 오래된 quota 시도는 원본 `facts.jsonl`·`events.jsonl`·`receipt.json`을 보존한다. 현재 장부 이전의 호출이므로 과거 사용량/한도 이관을 먼저 검증해야 한다. 해당 원본 receipt의 SHA-256·계정 그룹·reset을 운영자가 검토해 장부 초기화 시 `legacy_review_imports`에 명시적으로 포함하지 않으면 재호출을 거부한다. 새 검수 시도는 공용 장부의 기존 예약이 같은 계정·owner·quota 결과로 정산된 경우에만 reset 이후 재개한다. 빈 커밋이나 기록 삭제로 새 검수를 유도하지 않는다. same-session 재개는 기존 `--no-session-persistence` 때문에 증명되지 않았고, 신중한 새 시도만 검토한다.

읽기 전용으로 저장된 PR #30 시도를 대조했을 때 provider의 `rejected` 이벤트·최종 `api_error`·자식 0건 완료 증거는 확인됐다. 검사 시각에는 reset 시각이 아직 지나지 않았고, 현재 **공용 장부와 과거 호출 이관 증거가 없으므로 reset 이후에도 재개 불가**다. **실제 새 모델 호출은 0건**이다. 현재 PR HEAD·기준 커밋·전체 패치 바인딩과 운영 전환을 모두 대조해야 한다.

이 문서와 코드의 단위/격리 검사는 **모의 검증**이다. 실제 Astra E1–E6 응답·내용 판정, 공개 검색의 현재 결과, 새 신뢰 검수기의 실제 Claude 판정, 운영 전환, APK 마스터 직접 조작은 별도 미검증 항목이다. 운영 전환은 이 문서 작성이나 초안 PR 개설로 승인되지 않는다.

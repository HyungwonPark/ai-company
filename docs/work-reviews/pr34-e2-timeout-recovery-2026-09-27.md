### A. E1 완료 보존과 E2 사건 대조

서버의 기존 비공개 인수인계를 시작점으로 읽기 전용 사건표를 작성한다.

- E1의 원본 응답·파생 계획·검수 결과·계획 digest·요구사항 버전·job/session·정산을 연결한다. E1 재호출이나 재확정 없이 후속 실행의 시작 조건으로 고정한다.
- E2의 초기 질문, 고정 답변 메시지, 요청 revision, plan/task/역할, job/session/attempt/generation, 예약 ID·공용 계정 그룹을 대조해 **정확히 어느 호출이 시간 초과했는지** 확인한다. 고정 평가 답변 외의 사용자 결정을 만들지 않는다.
- 시작·마지막 출력·240초 종료·정리 완료·worker 중지 시각을 같은 시간대와 가능하면 단조 시계의 실행시간으로 비교한다. stdout/stderr·CLI 세션 기록·종료 코드·설정 관측·최종 보고서 완결성을 보존한다.
- `boot_id`, PID·시작 tick·PGID, systemd 실행 unit·cgroup, 자식 프로세스, guard, 저장소 snapshot을 정확한 시도에 연결한다. PID가 없다는 사실 하나나 시간 경과만으로 종료 확인을 만들지 않는다.
- 원본 7건, E1 별도 검수, E2 각 시도, 현재 계정 사용량·cooldown·미정산 예약을 표로 대조한다. 이미 정산한 사용량을 다시 누적하거나 청구액 미확인을 0으로 바꾸지 않는다.
- 운영 서비스의 중지 상태와 별도 실행 unit/자식 종료 여부를 구별한다. 다른 프로젝트의 프로세스·계정 상태는 수정하지 않는다.

### B. 시간 초과 원인과 한도 전달 확인

240초 값을 일괄 증액하지 않는다. 실제 고정 config, PM 제한, retry 제한, task·사례 잔여 예산, 공용 예약, 실제 `run_session` 전달값과 외부 감독기 제한을 비교한다. 모델 응답 대기와 프로세스 정리 대기를 구분한다.

현재 평가기의 `next_timeout`은 기록값이고, 실제 강제는 사례 예산 고정 → Automation 명세 → Dispatcher의 잔여 task·프로젝트 예약 시간 → `run_session` 경로에 있다. 기록값만 바꾸거나 이 값이 직접 전달되지 않는다는 이유만으로 제한이 무시된다고 판정하지 않는다. 실제 executor에 전달된 값으로 검증한다.

원인별 최소 조치를 제안한다. 필요하면 시간 초과 사유·종료 확인·응답 완결성·후속 조치가 구별되도록 구조화한 기록을 추가한다. `timeout = quota`, `timeout = success`, `stopped=True = 재실행 가능`으로 일괄 변환하지 않는다. 제한 변경이 필요하면 대상 역할·단계·새 값·근거·전체 예산 영향과 새 구성 버전을 고정한다. 기존 실행 명세·digest·기록은 덮어쓰지 않는다.

### C. 종료·결과·계정 대조 및 복구 도구

기존 신뢰 경로로 충분히 처리되는지 먼저 확인한다. 부족한 부분만 기본 읽기 전용인 진단·복구 도구로 구현하고 비운영 사본에서 검증한다. 최소한 다음 판정을 분리한다.

| 관측 증거 | 허용할 다음 준비 |
| --- | --- |
| 종료·시도 식별·저장소 영향이 불명 | UNKNOWN과 guard 보존, 부족한 근거 출력, 새 호출 금지 |
| 종료 확인·일치하는 완전한 최종 응답·결과 계약 충족 | 원래 실패 기록을 보존한 파생 채택·정산안을 생성. 실제 쓰기는 적용 범위와 별도 대조 |
| 종료 확인·최종 응답 불완전 또는 없음·영향 대조 완료 | 성공으로 만들지 않고 소비 시간·비용 미확인과 중단을 기록. 정확한 세션·단계에서의 재개 가능성을 별도 판정 |
| 프로세스 미시작을 입증 | 기존 미시작 취소 계약 사용. 이미 실행된 E2를 미시작으로 처리하지 않음 |

복구안은 제품·원문 해시·예약/job/session/attempt·계정 그룹·기대 이전 상태에 묶는다. 기존 행 직접 수정이나 guard 파일 삭제를 절차로 삼지 않는다. 정산·job 결과·guard 해제·계정 가용성 복구가 여러 저장소에 걸리면 중단 후 재적용 가능한 순서를 고정하고, 모두 검증되기 전까지 새 실행을 차단한다. 부분 진행·중복 적용·다른 관리자의 동시 실행·오래된 증빙은 안전하게 거부하거나 이미 완료된 동일 결과로 처리한다.

**예약 정산과 계정 재개 가능 여부는 별도다.** 해당 Codex 그룹의 모든 관련 큐·활성/불명 예약과 차단 사유를 대조한 후, 이번 E2 때문에 추가된 차단만 해제할 수 있는 근거를 요구한다. 기존 인증 차단·다른 UNKNOWN·남은 cooldown을 보존하며, 별개인 Claude 계정 UNKNOWN은 그대로 둔다. 종료 증거 확인을 위해 새 모델 호출을 보내지 않는다.

### D. 실제 제품 경로의 좁은 통합 검사

가능한 최소 가짜 CLI·임시 DB로 아래 조건을 검사한다. 이번 핵심인 시간 초과→세션 저장→공용 장부→대조→재개 경로는 SQL로 정상 상태를 직접 만드는 검사만으로 대신하지 않는다. 기존 합성 검사도 유지하되 증명 범위를 구별한다.

1. 시간 초과와 정상 정리, 정리 실패·분리 자식, guard·세션 불일치 각각에서 UNKNOWN 보존 여부를 확인한다.
2. 완전한 terminal 응답이 이미 저장된 뒤 감독기가 시간 초과한 경우와 부분 JSON·늦은 응답·다른 session 응답을 구별한다. 파생 결과·계획·정산은 각각 한 번만 채택된다.
3. 정산 후 중단, guard 처리 전후 중단, 계정 상태 반영 전후 중단, 두 복구 프로세스 동시 실행에서도 새 호출이 먼저 시작되지 않으며 사용량이 두 번 더해지지 않는다.
4. UNKNOWN 그룹의 다른 활성 예약·기존 인증/계정 차단·cooldown이 있으면 계정을 열지 않는다. Claude 차단과 원본 7건·E1 PASS가 유지된다.
5. E1 완료·E2 중단 상태에서 같은 평가 root와 idempotency key로 재개한다. E1 새 호출 0건, E2 답변 중복 0건, 실제 재개 시도만 새 예약·실행시간에 누적, 수정 횟수·계보 유지, E2 조건 충족 전 E3 호출 0건을 확인한다. 현재 `main`의 순회는 `environment_problem`도 다음 사례 진행 대상으로 포함한다. 미정산 해소만으로 실패한 E2를 건너뛰지 않도록 이번 단계별 진행 조건을 명시하고 검사한다. E3·E4 등에서 요구하는 정상 질문·결정 대기를 전부 계획 PASS로 강제하지 않으며, 기존 사례별 기대 조건을 유지한다.
6. 잔여 예산이 240초보다 짧거나 한도에 도달한 경우 실제 executor 인수가 줄어들거나 실행이 거부됨을 확인한다. 대기시간은 실행시간에 넣지 않고 실제 실행·정리 비용은 기존 계약대로 누적한다.

동일 worker 권한·격리·systemd 환경의 종료 검사와 일반 CI 모의 검사를 구분한다. 새 실제 모델 호출은 이 비운영 검사에 포함하지 않는다.

### E. 검수·고정 패키지·대조 모의 실행

관측한 원인별 실패→수정 성공, 기존 R34-1·R34-2와 평가 예산 회귀, 독립 코드 검수, 최종 HEAD의 필수 CI를 제출한다. 이번 변경과 관련 없는 전체 UI를 새로 개편하지 않는다. 실제 모델 검수가 계정·한도 때문에 막히면 정적 검수와 구별한다.

제품·의존성·실행 파일·구성·복구 도구·archive 해시를 고정하고, 일관된 운영 사본에서 **모델 호출 없이** 현재 E2의 정산·복구 계획을 생성한다. 사본 alias·WAL 보호를 유지한다. 서버 전체 경로·원문·인증·계정 식별자는 기존 비공개 기록에 보존하고 공개 요약에는 필요한 판정과 비밀정보 없는 해시만 남긴다.

### F. 실제 재개에 필요한 한 번의 적용안

기존 승인 제품에서 이미 검증·허용된 복구 절차로 해결된다면 그 근거와 적용 범위를 대조하고 기존 승인을 중복 요청하지 않는다. **새 제품·신규 정산 도구의 운영 쓰기·계정 차단 해제·실행 제한 변경이 기존 고정 승인을 벗어나면**, A~E를 끝낸 뒤 정확한 변경·대상 E2 시도·계정·예산·중단 조건을 묶어 한 번만 승인 요청한다. 이 지시 문서 자체가 운영 UNKNOWN 해제나 모델 재호출을 승인하지 않는다.

실제 적용안에는 아래 순서를 포함한다.

1. 중지 상태에서 실제 기록과 고정 복구안을 다시 대조한다.
2. 승인된 대상만 멱등 대조·정산하고 계정·guard·미정산·예산 상태를 확인한다. 종료·결과·영향이 불명이면 멈춘다.
3. E1 완료를 보존하며 동일 E2 요청·답변·계획 계보·가능한 동일 세션에서 재개한다. 새 세션이 필요하면 별도 인수인계 근거·권한을 요구한다. 빈 평가 root나 다른 계정으로 문제를 우회하지 않는다.
4. E2의 고정 행동 조건 충족 후 기존 승인된 E3~E6을 이어간다. 고정된 질문/답변과 평가 목표는 바꾸지 않는다. 전역 24호출·1,800초·수정 2회 및 사례 한도에 원본 7건과 이후 모든 시도를 포함한다. 이는 코드상 최대치이며 기존 승인 구성·사례 예산이 더 작으면 그 한도를 유지한다. 이 문서로 예산을 늘리지 않는다. 예산이 남지 않으면 대기/미완료로 제출한다.
5. 기술 실패·불명 상태·예기치 않은 호출이면 두 worker 중지·자동 시작 해제, 현 DB·장부·체크포인트 보존을 적용한다. 과거 DB로 되돌리거나 구형 worker를 켜지 않는다. 정상 quota 대기·필수 질문·마스터 결정 대기·허용된 REVISE는 기술 실패로 처리하지 않고 기존 한도와 사례별 조건을 따른다.

실제 평가 완료 전 마스터 APK 확정이나 임의 개발 실행을 요청하지 않는다. 기존 웹·커플 서비스·quota 일정·승인·PR #10 pending·서명키를 유지하며 병합하지 않는다.

## 제출할 보고

한 보고서에 **E1 보존 근거 / E2 정확한 실패 단계와 확정 원인·미확정 원인 / 종료·정산·계정 상태 / 수정·검사 / 고정 후보 / 실제 적용 필요 여부 / 남은 평가와 예산**을 정리한다. E1 복구·내용 PASS, E2 재개 가능, E2 실제 PASS, E3~E6 완료를 각각 구별한다. 자료 부족이면 필요한 항목을 구체적으로 적고 다른 비운영 준비는 완료한다.

# 저장 번역 재검사

기준 `69471e8` · 2026-09-16 · **구현·복사본 검증 완료, 운영 미적용**

두 번역의 실제 저장된 원문과 출력 각 8문장을 대조했다. 추가 모델 호출은 0건이며 운영 DB는 `mode=ro`로만 읽었다. 원래 실패한 두 작업과 그 이전 실패·사용량·공유 한도·승인 기록을 수정하지 않았다. 이번 검사는 기존 개발 검수의 PASS나 마스터 직접 UI 확정을 다시 수행한 것이 아니다.

## 판정

| 저장 결과 | 보호검사의 오탐 | 의미 검토 | 복사본 결과 |
|---|---|---|---|
| `40ceb1f71da649fd9cf909fd4891bad9` · 독립 검수 | `not` → ‘아닙니다’를 인식하지 못함 | Authorization을 ‘인증’으로 옮겨 승인 권한과 로그인 인증을 혼동하게 함 | **거부**. 원래 실패 결과를 계속 선택하고 검토 기록만 추가 |
| `1a381d1e9def4e32bbaec70331406e3d` · 최종 검수 | 위 부정 표현과 `pending` → ‘미결’을 인식하지 못함 | 검사 8개, 동일 후보와 원격·독립 검수의 연결, 위임받은 검증과 실제 UI 확정의 구분, 미결 사항 없음, 파일·검사 미변경, 원격 증거 미재조회와 최종 설정 검증 조건을 보존 | **통과**. 원본과 별개의 읽기용 결과 1건 생성 |

‘아닙니다’·‘미결’이 있으면 모든 번역이 정확하다고 판단하는 방식은 아니다. [의미 검토 원장](evidence/translation-saved-review-2026-09-16.json)은 작업 ID·원문 digest·실제 stdout SHA-256·분절 출력 digest에 결합한다. 통과 판정은 빈 지적 목록, 거부 판정은 구체적인 지적을 요구한다. 문구를 바꾸거나 새 번역을 생성하지 않는다. 독립 검수 문서의 오역은 남아 있으며 추가 수정된 읽기 자료는 별도 검토 대상이다.

## 구현

기존 `translation-json-v2/v3`와 기본 worker 설정은 유지한다. 별도 `translation-json-v4-saved` 검사에서 완결된 ‘아닙니다’와 ‘미결 항목/사항/상태/검토’만 기존 부정·대기 검사에 추가한다. 조건·`only if`·예외·한도·숫자·경로·코드 보존 검사는 그대로다. v4는 일반 번역 동기화 설정으로 예약할 수 없다. 이 경로는 종료 확인된 v3 실패의 원시 출력을 다시 읽으며 모델·도구 실행이나 추가 시도 등록 기능이 없다.

`translation_saved_rechecks`에 검토와 판정을 새로 기록한다. 통과한 경우만 `translation_jobs`에 완료 결과를 추가하고, 정확한 원문·현재 실패 선택에 해당하는 `translation_links` 한 행을 교체한다. 원래 실패 작업의 설정·상태·원문·attempts·spent_seconds·native 비용은 그대로 보존한다. 새 결과는 소진된 사용량을 그대로 상속한다. 정상 동기화는 이 원문과 기존 설정에 결합된 v3→v4 이력을 인식하여 새 선택을 유지한다.

거부된 검토는 실패 작업을 바꾸지 않으며 자동 재시도도 등록하지 않는다. 같은 입력과 검토를 다시 적용하면 동일 재검사·결과를 반환한다. 다른 원문·다른 저장 출력·변경된 검토·이후의 다른 표시 선택은 임의로 덮어쓰지 않는다. 재검사는 권한 있는 운영자용 Python 기능이며 HTTP·PM·모델 도구로 노출하지 않는다.

## 검증 근거

[검증 기록](evidence/translation-saved-recheck-2026-09-16.json)에 원시 출력 해시, 복사본 결과 ID, 검사 코드 해시와 보존 테이블을 기록했다. 결과 ID는 **복사본에서 만든 ID**이며 운영에 존재하는 새 결과로 안내하면 안 된다.

- 번역 회귀 47개 통과. 신규 검사 8개는 표현의 긍정·반례, 기존 parser 유지, 승인 문맥 오역 거부, 정확한 원문·출력·검토 결합, 누락된 부정을 PASS 검토로 우회하지 못함, 동시·반복 적용, 재시작과 정상 동기화, 복구 및 구버전 거부를 확인한다.
- 실제 운영 DB의 일관된 SQLite snapshot을 새 비공개 복사본으로 만들었다. 2건 재검사 후 통과 결과 1건·거부 기록 1건을 얻었고 재실행 결과는 동일했다. subprocess 호출을 금지한 검증도 통과했다.
- 기존 모든 `translation_jobs.document`는 바이트 단위로 같았다. 기존 테이블 중 추가·변경된 것은 복사본의 `translation_jobs`, `translation_links`, 해당 변경 이벤트뿐이었다. 사용량·계정 한도·승인·세션·작업·프로젝트 등 나머지 테이블은 같았다.
- 새 worker 동기화가 v4 선택을 유지함을 실제 복사본에서 확인했다. 표시 링크만 v3 실패로 되돌린 뒤 `69471e8`의 구버전 동기화를 실행해 그 선택과 모든 산출물의 보존을 확인했다.
- 운영 원본을 마지막으로 읽었을 때 두 실패 작업의 전체 digest는 제안 작성 시점과 같고 상태는 모두 `failed`, 추가 예약은 없다. 운영 표시에 새 통과 결과가 적용됐다는 뜻이 아니다.

## 적용안

새 버전의 웹·worker 패키지를 고정하고 별도 운영 승인 범위와 대조한 뒤 적용한다. 이 문서만으로 서비스 재시작이나 운영 링크 교체를 수행하지 않는다. 현재 가동 worker에 이 코드가 설치되지 않았다면 실행기가 적용을 거부한다. 기본 미리보기는 읽기 전용이며 복사본은 새 파일만 만든다.

비공개 제안 파일은 새 작업트리의 `.ai-company/translation-saved-recheck-20260916/proposal.json`에 고정했다. SHA-256은 `5d4fa5b4c1a4583d40c1b276958dc01ce8908e18e860e60d0495c80568a78420`이다. 제안은 위 두 실패의 전체 digest·원시 출력·검토 해시·통과/거부 판정을 포함하며 새 모델 호출 상한은 0이다. 운영 상태가 달라지면 새 제안으로 차이를 대조한다.

1. 새 release의 설치 소스가 검증한 `translations.py`·`adapters/translation_cli.py`와 일치하는지 확인한다. 기존 적용 경계에 따라 번역 worker가 실제로 그 release와 대상 DB를 사용하는지 확인한다. 구버전이면 재검사를 적용하지 않는다.
2. `scripts/recheck_saved_translations.py --proposal <위 고정 제안> --expected-proposal-sha256 5d4fa5b4c1a4583d40c1b276958dc01ce8908e18e860e60d0495c80568a78420 --apply --candidate-release <실제로 가동 중인 검증된 새 release>`를 실행한다. release 경로는 패키지 고정 단계의 실제값으로 채워야 하며, 준비되지 않은 경로를 완료된 적용안처럼 사용하지 않는다.
3. 원래 작업 2건과 원장 불변, 재검사 2건·새 읽기 결과 1건, 해당 링크 1개, 후속 동기화·새로고침에서 선택 유지 여부를 대조한다. 첫 문서는 오역으로 계속 실패 표시한다. 출력된 `result_job_id`가 실제 운영 결과이며 복사본 ID를 재사용하지 않는다.
4. 중간 종료 후에는 같은 제안으로만 이어간다. 개별 작업의 기록·링크는 원자적으로 반영하며 완료된 항목을 중복 생성하지 않는다. 원본이나 선택이 바뀌면 거부한다.

## 복구안

**구버전 worker를 먼저 시작하면 안 된다.** 구버전은 v4 연결 이력을 이해하지 못해 최초 v2 실패를 다시 선택하는 것을 별도 복사본에서 재현했다. 새 작업의 실행을 멈춘 뒤, 아직 새 코드가 있는 상태에서 `TranslationStore.restore_saved_selection(recheck_id, expected_result_job_id=실제_운영_결과_ID)`로 해당 표시 링크만 v3 실패로 복구한다. 이 함수는 재검사·원본 digest·완료 결과·현재 선택을 대조하며 새로 선택된 다른 자료를 덮어쓰지 않는다. 같은 복구의 반복은 추가 변경이 없다.

복구 후 v3 실패 선택과 기존 산출물·재검사·사용량·승인 보존을 확인하고 구버전 worker로 전환한다. 원래 실패, 새 완료 자료, 재검사 표와 이벤트를 삭제하지 않는다. DB 파일이나 실행 이력을 snapshot으로 덮어쓰지 않는다. 복구 함수가 이후의 다른 선택을 발견하면 자동으로 진행하지 않고 해당 차이를 검토한다.
